Aba 1 · Definição de banco de dados

Sua missão é entender o que é um banco de dados (coleção organizada de dados guardada de forma persistente, que pode ser consultada e alterada por programas) e por que ele é o coração de quase toda aplicação back-end. Você vai distinguir o banco de dados do SGBD (Sistema Gerenciador de Banco de Dados; o software que administra o banco) e conhecer as duas grandes famílias: relacionais (dados em tabelas com linhas e colunas) e não relacionais (NoSQL, dados em documentos, pares chave-valor, grafos ou colunas).

📚 Banco de dados versus SGBD

Uma planilha do Excel (programa de planilhas da Microsoft) guardada no seu computador já é uma coleção de dados, mas não é um banco de dados de verdade: falta controle de acesso simultâneo, integridade, recuperação de falhas e consulta eficiente. Um banco de dados de verdade oferece:

  • Persistência: os dados sobrevivem ao desligamento da máquina e ao fim do programa.
  • Compartilhamento: vários usuários e programas acessam ao mesmo tempo, sem corromper nada.
  • Integridade: regras impedem dados impossíveis (idade negativa, pedido sem cliente).
  • Consulta eficiente: encontrar um registro entre milhões em milissegundos, graças a índices (estruturas que aceleram a busca).
  • Recuperação: voltar a um estado consistente depois de uma queda de energia.

Quem entrega tudo isso é o SGBD (Sistema Gerenciador de Banco de Dados; em inglês DBMS, Database Management System). O banco é o conteúdo; o SGBD é o software que guarda, protege e serve esse conteúdo. Exemplos de SGBDs: PostgreSQL, MySQL, Oracle Database, SQL Server e SQLite.

📚 Relacional versus não relacional (NoSQL)

  • Relacional: os dados vivem em tabelas com colunas fixas e linhas; as tabelas se ligam por chaves. A linguagem padrão é a SQL (do inglês Structured Query Language; em português, Linguagem de Consulta Estruturada). Ideal quando os dados têm estrutura estável e as relações importam (clientes, pedidos, produtos). Exemplos: PostgreSQL, MySQL, Oracle, SQL Server, SQLite.
  • Não relacional (NoSQL):放弃了 a rigidez das tabelas em troca de flexibilidade e escala horizontal. Quatro subfamílias principais:
    • Documentos: guarda objetos JSON (formato de texto para troca de dados). Exemplo: MongoDB.
    • Chave-valor: um dicionário gigante e rapidíssimo. Exemplo: Redis.
    • Colunas largas: otimizado para escrita massiva distribuída. Exemplo: Apache Cassandra.
    • Grafos: otimizado para relações complexas (redes sociais, recomendação). Exemplo: Neo4j.

Não existe "melhor": existe o adequado. Um sistema de pedidos com regras fiscais pede relacional; um catálogo com atributos que mudam toda semana pode pedir documentos; um placar de jogo em tempo real pede chave-valor.

🌎 Quem usa o quê

  • Nubank (banco digital brasileiro): usa Datomic (banco de dados imutável criado pela empresa americana Cognitect) como núcleo transacional, com PostgreSQL e Cassandra em partes do ecossistema.
  • iFood (aplicativo brasileiro de entregas): PostgreSQL para dados transacionais de pedidos e Redis para cache de cardápios e sessões.
  • Instagram (rede social de fotos da Meta): PostgreSQL em larga escala para dados de usuários e Cassandra para feeds.
  • Netflix (serviço americano de streaming): Cassandra para histórico de visualização em escala global e MySQL para dados de assinatura.
  • Aplicativos de celular: SQLite (banco relacional embutido, sem servidor) roda dentro de praticamente todo Android e iPhone para guardar dados locais.

🛠️ Ferramentas para conversar com o banco

  • pgAdmin (interface gráfica oficial do PostgreSQL): cria tabelas, roda consultas e mostra planos de execução.
  • DBeaver (cliente universal gratuito): conecta em PostgreSQL, MySQL, SQLite, Oracle e dezenas de outros.
  • MySQL Workbench (ferramenta oficial da Oracle para MySQL): modelagem visual e administração.
  • psql (terminal do PostgreSQL) e mysql (terminal do MySQL): linha de comando para quem gosta de velocidade.

Aba 2 · Elementos relevantes de banco de dados no back-end

Sua missão é dominar o vocabulário estrutural do banco relacional: tabela (conjunto de registros do mesmo tipo), linha ou tupla (um registro), coluna ou atributo (uma característica), esquema (o desenho das tabelas e relações), chave primária (identificador único da linha), chave estrangeira (ponteiro para a chave de outra tabela) e as restrições que barram dados impossíveis. Você vai explorar um esquema de loja e ver a integridade em ação.

📚 As peças do modelo relacional

  • Tabela (relação): agrupa registros do mesmo tipo, como clientes ou pedidos.
  • Linha (tupla): um registro individual, como a cliente Ana.
  • Coluna (atributo): uma característica com tipo definido, como nome (texto) ou idade (inteiro).
  • Esquema (schema): o projeto do banco: quais tabelas existem, com quais colunas, tipos e relações.
  • Chave primária (PRIMARY KEY): coluna (ou conjunto) que identifica cada linha de forma única e não nula.
  • Chave estrangeira (FOREIGN KEY): coluna que aponta para a chave primária de outra tabela, garantindo a integridade referencial (nenhum pedido aponta para cliente inexistente).
  • Restrições: UNIQUE (sem duplicatas), NOT NULL (obrigatório), CHECK (regra de negócio, como preço maior que zero), DEFAULT (valor padrão).

📚 Cardinalidade e outros elementos do dia a dia

  • 1:1 (um para um): um cliente tem um cadastro de fidelidade.
  • 1:N (um para muitos): um cliente faz muitos pedidos; a tabela pedidos guarda cliente_id.
  • N:M (muitos para muitos): um pedido tem vários produtos e um produto aparece em vários pedidos; resolve-se com uma tabela associativa (itens_pedido).
  • Índice: estrutura auxiliar (geralmente uma árvore B) que acelera buscas por uma coluna, ao custo de espaço e de escrita um pouco mais lenta.
  • Transação: pacote de operações tudo-ou-nada, confirmado por COMMIT ou desfeito por ROLLBACK.
  • Visão (view): consulta salva que se comporta como uma tabela virtual, útil para relatórios e para esconder colunas sensíveis.

🌎 Esses elementos protegendo sistemas reais

  • Nota fiscal eletrônica: a chave estrangeira entre nota e cliente impede emitir nota para um CNPJ (Cadastro Nacional da Pessoa Jurídica) que não existe no cadastro.
  • Cadastro no gov.br (portal do governo federal): a restrição UNIQUE no CPF impede duas contas para a mesma pessoa.
  • Estoque da Amazon (varejista americana): um CHECK de quantidade não negativa impede que um bug zere o estoque para valores impossíveis.
  • Busca do Mercado Livre (marketplace latino-americano): índices nas colunas de categoria e preço fazem a busca responder em milissegundos entre milhões de produtos.
  • Transferência bancária: a transação garante que débito e crédito aconteçam juntos ou nenhum aconteça.

🛠️ Como inspecionar o esquema

  • PostgreSQL: no psql, o comando \d pedidos mostra colunas, tipos, índices e chaves estrangeiras.
  • MySQL: DESCRIBE pedidos; e SHOW CREATE TABLE pedidos;.
  • DBeaver: aba de propriedades da tabela mostra chaves, índices e diagrama de relações.
  • Diagrama ER (entidade-relacionamento): desenho das tabelas e ligações, gerado automaticamente por pgAdmin e MySQL Workbench.

Aba 3 · SQL para criar bancos de dados relacionais (DDL)

Sua missão é aprender a DDL (do inglês Data Definition Language; em português, Linguagem de Definição de Dados): o subconjunto da SQL que cria e altera a estrutura do banco. Você vai usar CREATE DATABASE, CREATE TABLE com tipos e restrições, ALTER TABLE para evoluir o esquema e DROP para remover, montando uma tabela na demo e vendo o SQL nascer.

📚 Os comandos de definição

  • CREATE DATABASE loja; cria o banco vazio.
  • CREATE TABLE cria uma tabela com colunas, tipos e restrições.
  • ALTER TABLE adiciona, remove ou altera colunas e restrições em uma tabela existente.
  • DROP TABLE remove a tabela e todos os seus dados (irreversível sem backup).
  • TRUNCATE TABLE apaga todas as linhas rapidamente, mas mantém a estrutura.
CREATE DATABASE loja;

CREATE TABLE clientes (
    id        SERIAL PRIMARY KEY,
    nome      VARCHAR(100) NOT NULL,
    email     VARCHAR(150) UNIQUE,
    idade     INT CHECK (idade >= 18),
    criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE pedidos (
    id         SERIAL PRIMARY KEY,
    cliente_id INT NOT NULL REFERENCES clientes(id),
    total      DECIMAL(10,2) CHECK (total > 0),
    criado_em  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

📚 Tipos de dados mais usados

  • INT / INTEGER: números inteiros (idade, quantidade).
  • SERIAL (PostgreSQL) ou AUTO_INCREMENT (MySQL): inteiro que se incrementa sozinho, ideal para chaves primárias.
  • VARCHAR(n): texto de tamanho variável até n caracteres (nome, email).
  • TEXT: texto longo sem limite prático (descrição, comentário).
  • DECIMAL(p,s) / NUMERIC: número exato com casas decimais, obrigatório para dinheiro.
  • DATE / TIMESTAMP: data e data com hora.
  • BOOLEAN: verdadeiro ou falso.

Regra de ouro: nunca use FLOAT ou DOUBLE para valores monetários; o arredondamento binário gera centavos fantasmas. Use DECIMAL(10,2).

🌎 DDL no mundo real

  • Migrações versionadas: ferramentas como Flyway (Java) e as migrations do Django (Python) guardam cada CREATE e ALTER em arquivos numerados, aplicados em ordem em todos os ambientes.
  • Nota fiscal eletrônica: o esquema das tabelas de NF-e segue tipos e restrições definidos pela Receita Federal (órgão brasileiro).
  • Sistemas bancários: valores em DECIMAL de alta precisão, nunca em ponto flutuante, para evitar diferenças de centavos em milhões de transações.
  • Startups: o primeiro CREATE TABLE de um MVP (produto mínimo viável) costuma virar o esquema que sustenta a empresa por anos; por isso vale pensar nas restrições desde o início.

🛠️ Boas práticas de DDL

  • Nomes claros e consistentes: tabelas no plural (clientes), colunas em snake_case (criado_em).
  • Sempre defina PK: toda tabela precisa de identificador único.
  • Restrições no banco: NOT NULL, UNIQUE e CHECK protegem mesmo quando o código falha.
  • Versione o esquema: cada mudança vira um arquivo de migração, nunca um comando solto em produção.
  • Cuidado com DROP: em produção, DROP sem backup é perda definitiva.

Aba 4 · SQL para manipular bancos de dados relacionais (DML)

Sua missão é dominar a DML (do inglês Data Manipulation Language; em português, Linguagem de Manipulação de Dados): INSERT para criar linhas, SELECT para consultar, UPDATE para alterar e DELETE para remover. Você vai operar um console SQL simulado sobre uma tabela de clientes e ver o efeito de cada comando, incluindo o perigo de um UPDATE sem WHERE.

📚 Os quatro comandos essenciais

-- Criar linhas
INSERT INTO clientes (nome, cidade, idade)
VALUES ('Ana', 'SP', 28);

-- Consultar linhas
SELECT * FROM clientes;
SELECT nome, cidade FROM clientes WHERE cidade = 'SP' ORDER BY nome;

-- Alterar linhas
UPDATE clientes SET cidade = 'RJ' WHERE id = 2;

-- Remover linhas
DELETE FROM clientes WHERE idade < 25;
  • INSERT: lista as colunas e os valores na mesma ordem; o id SERIAL é gerado sozinho.
  • SELECT: escolhe colunas (ou * para todas), filtra com WHERE, ordena com ORDER BY e limita com LIMIT.
  • UPDATE: define novos valores com SET e escolhe as linhas com WHERE.
  • DELETE: remove as linhas que casam com o WHERE.

Aviso mais importante da aula: UPDATE e DELETE sem WHERE atingem TODAS as linhas da tabela. Em produção, isso significa alterar ou apagar a base inteira em um comando.

📚 Consultando com mais poder

  • Operadores no WHERE: =, <>, >, <, BETWEEN, IN, LIKE, IS NULL.
  • Funções de agregação: COUNT, SUM, AVG, MIN, MAX resumem várias linhas em um valor.
  • GROUP BY: agrupa linhas antes de agregar (total de pedidos por cliente).
  • JOIN: combina linhas de duas tabelas pela chave que as liga.
SELECT c.nome, COUNT(p.id) AS qtde_pedidos, SUM(p.total) AS total_gasto
FROM clientes c
JOIN pedidos p ON p.cliente_id = c.id
GROUP BY c.nome
ORDER BY total_gasto DESC;

🌎 DML no dia a dia

  • Cadastro no iFood (aplicativo brasileiro de entregas): um INSERT cria o cliente; o SELECT com WHERE busca por email no login.
  • Atualização de endereço: um UPDATE com WHERE id garante que só o registro do próprio usuário mude.
  • Relatório de vendas: SELECT com JOIN e GROUP BY gera o total por loja que a diretoria vê no painel.
  • Incidentes reais: em 2017, um engenheiro da GitLab (plataforma de hospedagem de código) executou um comando de remoção no diretório errado e apagou dados de produção; o episódio virou caso público sobre a importância de WHERE, backups e revisão de comandos.

🛠️ Hábitos que evitam desastres

  • SELECT antes de UPDATE/DELETE: rode o SELECT com o mesmo WHERE para ver quais linhas serão atingidas.
  • Transação em produção: BEGIN, comando, conferência, COMMIT ou ROLLBACK.
  • LIMIT em consultas exploratórias: evita trazer milhões de linhas para a tela.
  • Backup antes de manutenção: sempre.

Explicação: SELECT não altera dados, mas um SELECT sem LIMIT em uma tabela de bilhões de linhas pode consumir memória, travar o banco e derrubar o serviço. Consultas exploratórias devem sempre usar LIMIT e filtros.

Aba 5 · SQL no back-end: conexão, segurança e transações

Sua missão é conectar o que você aprendeu ao código back-end: usar drivers (bibliotecas que falam o protocolo do banco), pool de conexões (conjunto de conexões reutilizáveis), consultas parametrizadas (valores enviados separados do comando, que bloqueiam a injeção de SQL) e transações (BEGIN, COMMIT, ROLLBACK). Você vai atacar uma consulta vulnerável na demo e ver a versão parametrizada resistir.

📚 Do código ao banco

  • Driver: biblioteca que implementa o protocolo do SGBD. Exemplos: pg (PostgreSQL em Node.js), mysql2 (MySQL em Node.js), psycopg (PostgreSQL em Python), JDBC (do inglês Java Database Connectivity; interface padrão de banco em Java).
  • Pool de conexões: abrir uma conexão custa tempo e memória; o pool mantém várias abertas e as empresta aos pedidos, devolvendo ao fim. Sem pool, um pico de acessos derruba o banco.
  • Consulta parametrizada: o comando vai com marcadores ($1, %s, ?) e os valores viajam separados. O banco trata o valor sempre como dado, nunca como parte do SQL.
  • Transação: BEGIN agrupa operações; COMMIT confirma; ROLLBACK desfaz. Essencial para transferências e criação de pedido com itens.
  • ORM (mapeamento objeto-relacional, visto na Aula 5): gera SQL parametrizado por baixo, mas o desenvolvedor continua precisando entender SQL para diagnosticar desempenho.

📚 Injeção de SQL: o ataque mais clássico

Quando o código monta a consulta colando texto digitado pelo usuário, um invasor pode escrever SQL dentro do campo. Exemplo vulnerável:

// ERRADO: concatenação de texto do usuário
const sql = "SELECT * FROM clientes WHERE nome = '" + nome + "'";

Se o usuário digitar ' OR '1'='1, a consulta vira:

SELECT * FROM clientes WHERE nome = '' OR '1'='1';

Como '1'='1' é sempre verdadeiro, o banco devolve TODOS os clientes. A versão segura usa parâmetro:

// CERTO: consulta parametrizada
const sql = "SELECT * FROM clientes WHERE nome = $1";
await pool.query(sql, [nome]);

🌎 Casos reais de injeção e de boas práticas

  • TalkTalk (2015): a operadora de telecomunicações britânica sofreu ataque por injeção de SQL; dados de cerca de 157 mil clientes foram expostos e a empresa foi multada em 400 mil libras pelo órgão regulador britânico.
  • Heartland Payment Systems (2008): a processadora de pagamentos americana foi comprometida por injeção de SQL, em um dos maiores vazamentos de cartões da história, com mais de 100 milhões de cartões expostos.
  • OWASP Top 10 (lista de riscos da organização aberta de segurança de aplicações): a injeção aparece há anos no topo, e a defesa recomendada é sempre consulta parametrizada.
  • Frameworks modernos: Django ORM, Hibernate e Prisma geram SQL parametrizado por padrão, o que reduziu drasticamente esse tipo de falha em projetos novos.

🛠️ Checklist de segurança e desempenho

  • Nunca concatene entrada do usuário em SQL; use parâmetros sempre.
  • Menor privilégio: o usuário do banco da aplicação não deve ser superusuário nem ter permissão de DROP.
  • Pool dimensionado: conexões demais esgotam o banco; de menos criam fila.
  • Transações curtas: transações longas seguram travas e degradam a concorrência.
  • Índices nas colunas de filtro e junção: sem eles, cada consulta varre a tabela inteira.
  • Logs e monitoramento: registre consultas lentas (slow query log no MySQL, pg_stat_statements no PostgreSQL).
