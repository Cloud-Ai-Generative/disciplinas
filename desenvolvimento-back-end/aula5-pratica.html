Aba 1 · Funcionalidades mais comuns em aplicações back-end

Sua missão é reconhecer o cardápio padrão de todo sistema back-end (a parte do sistema que roda no servidor, invisível para o usuário): CRUD (sigla em inglês para Create, Read, Update, Delete; em português, Criar, Ler, Atualizar e Apagar), autenticação (provar quem você é), autorização (definir o que você pode fazer), validação de entrada (barrar dados ruins antes de eles chegarem ao banco) e APIs REST (do inglês Application Programming Interface; em português, Interface de Programação de Aplicações, no estilo Representational State Transfer, Transferência de Estado Representacional). Você vai simular requisições (pedidos que um cliente faz ao servidor) e ver o caminho completo dentro do back-end.

📚 O cardápio padrão de um back-end

  • CRUD: as quatro operações básicas sobre qualquer recurso (cliente, pedido, produto). Criar (cadastrar um cliente), Ler (listar ou buscar), Atualizar (mudar o endereço), Apagar (remover um cadastro).
  • Autenticação e autorização: primeiro o sistema confirma sua identidade (login com senha, ou OAuth2, protocolo de autorização usado pelo botão Entrar com Google), depois verifica suas permissões (um cliente não pode aprovar o próprio reembolso). O JWT (do inglês JSON Web Token; em português, Token Web em JSON) é o crachá digital assinado que o servidor emite após o login e confere a cada requisição.
  • Validação de entrada: conferir tipo, tamanho e formato dos dados recebidos (e-mail com arroba, idade positiva) antes de tocar no banco. É a primeira linha de defesa contra dados corruptos e ataques.
  • APIs REST com métodos HTTP (do inglês Hypertext Transfer Protocol; em português, Protocolo de Transferência de Hipertexto): GET para ler, POST para criar, PUT ou PATCH para atualizar, DELETE para apagar. Cada método devolve um código de status (como 200 para sucesso, 201 para criado, 404 para não encontrado).
  • Registro de eventos (logging) e paginação (devolver listas em pedaços, 20 por página) completam o cardápio dos sistemas profissionais.

🌎 Essas funcionalidades no seu dia

  • Login do iFood (aplicativo brasileiro de entregas): autenticação com OAuth2 do Google ou Facebook (rede social da Meta); o token JWT acompanha cada pedido que você faz ao servidor.
  • Cadastro no Nubank (banco digital brasileiro): validação de entrada confere CPF (Cadastro de Pessoa Física) com o algoritmo de dígito verificador antes de criar a conta.
  • Busca do Mercado Livre (marketplace latino-americano): uma API REST com GET /produtos?q=teclado devolve JSON (do inglês JavaScript Object Notation; formato de texto para trocar dados) paginado com 50 itens por página.
  • Excluir conta no Instagram (rede social de fotos): um DELETE autenticado, que só o dono do JWT válido pode executar.

🛠️ Ferramentas para ver as requisições

  • Postman (aplicativo gratuito da empresa indiana Postman Inc.): envia requisições HTTP manualmente e mostra status, corpo e tempo de resposta.
  • Aba Network do navegador (ferramenta de desenvolvedor do Chrome e do Firefox): mostra cada GET e POST que a página faz, com códigos de status coloridos.
  • curl (comando de linha presente no Linux, macOS e Windows): envia requisições direto do terminal, útil em scripts de teste.

Aba 2 · Modelagem de dados para sistemas eficientes

Sua missão é aprender a desenhar o esqueleto de dados de um sistema antes de escrever código: o modelo entidade-relacionamento (representação gráfica criada por Peter Chen, pesquisador nipo-americano, em 1976, que mostra entidades, atributos e relacionamentos), as cardinalidades (1:1, 1:N e N:M, ou seja, quantas ocorrências de um lado se ligam ao outro) e a normalização (conjunto de regras que reduz repetição de dados e anomalias de atualização). Na demo, você vai normalizar uma tabela bagunçada passo a passo.

📚 Entidades, relacionamentos e cardinalidades

Uma entidade é uma coisa do mundo real que o sistema precisa guardar: Cliente, Pedido, Produto. Cada entidade vira uma tabela no banco, e cada característica vira uma coluna (atributo). Os relacionamentos dizem como as entidades se conectam, com três cardinalidades clássicas:

  • 1:1 (um para um): um Cliente tem exatamente um Carrinho ativo. Na implementação, uma chave estrangeira (coluna que aponta para a chave de outra tabela) com restrição de unicidade resolve.
  • 1:N (um para muitos): um Cliente faz muitos Pedidos, mas cada Pedido é de um só Cliente. A tabela Pedido ganha a coluna cliente_id apontando para Cliente.
  • N:M (muitos para muitos): um Pedido contém muitos Produtos e um Produto aparece em muitos Pedidos. Nenhum lado pode guardar a lista do outro; cria-se uma tabela associativa (também chamada de tabela de junção), como item_pedido, com as duas chaves estrangeiras e a quantidade.

A normalização organiza essas tabelas em formas normais (1FN, 2FN, 3FN) para que cada fato seja guardado uma única vez. O prêmio é triplo: menos espaço, menos inconsistência e atualizações em um lugar só.

🌎 Modelagem bem e mal feita no mundo real

  • E-commerce da Magalu (varejista brasileira): o pedido N:M com produtos exige a tabela de itens; sem ela, seria impossível calcular o total de um pedido com dez produtos diferentes.
  • Sistema SUS (Sistema Único de Saúde do Brasil): o cartão 1:1 com o paciente evita duplicar o histórico clínico em duas filas diferentes.
  • Planilhas virando banco: empresas que começam controlando estoque em Excel (planilha da Microsoft) sofrem anomalias de atualização clássicas: mudar o preço de um produto exige editar dezenas de linhas, e uma linha esquecida gera dois preços diferentes para o mesmo item.
  • PostgreSQL (banco de dados relacional livre, mantido por uma comunidade global) e MySQL (banco relacional hoje mantido pela Oracle, empresa americana) aplicam as restrições do modelo e garantem que o desenho seja respeitado em runtime.

🛠️ As três formas normais em linguagem plana

  • 1FN (primeira forma normal): nada de listas ou valores múltiplos dentro de uma célula; cada célula guarda um valor atômico e cada linha é única.
  • 2FN (segunda forma normal): estando na 1FN, toda coluna que não é chave deve depender da chave inteira, não de parte dela; isso empurra o preço do produto para a tabela Produto.
  • 3FN (terceira forma normal): estando na 2FN, nenhuma coluna pode depender de outra coluna que não seja a chave (dependência transitiva); isso empurra a cidade para a tabela Cliente.

Aba 3 · Integridade dos sistemas back-end

Sua missão é entender como um banco de dados se protege de dados impossíveis: as restrições de integridade (regras que o próprio banco impõe, como chave primária, chave estrangeira, UNIQUE, NOT NULL e CHECK) e as transações (pacotes de operações que valem tudo ou nada, garantidos pelas propriedades ACID: Atomicidade, Consistência, Isolamento e Durabilidade). Na demo, você vai transferir dinheiro entre contas e provocar uma falha no meio para ver o rollback (desfazer) em ação.

📚 As cinco restrições que barram dados impossíveis

  • PRIMARY KEY (chave primária): identifica cada linha de forma única e não nula; impede dois clientes com o mesmo id.
  • FOREIGN KEY (chave estrangeira): garante a integridade referencial: um Pedido não pode apontar para um Cliente que não existe; o banco recusa a inserção.
  • UNIQUE (único): impede duplicatas em colunas como e-mail ou CPF.
  • NOT NULL (não nulo): obriga o preenchimento de colunas essenciais, como o nome do cliente.
  • CHECK (verificação): valida regras de negócio no próprio banco, como quantidade maior que zero ou idade maior ou igual a 18.

Essas regras vivem no SGBD (Sistema Gerenciador de Banco de Dados; o software que administra o banco, como PostgreSQL, MySQL ou Oracle Database), não apenas no código da aplicação: mesmo que um bug ou um ataque passe pela aplicação, o banco continua sendo a última muralha.

📚 Transações e o pacto ACID

Uma transação agrupa várias operações em uma unidade indivisível: ou todas acontecem, ou nenhuma acontece. O exemplo clássico é a transferência bancária: debitar 200 reais da conta A e creditar 200 reais na conta B são duas operações que não podem ficar pela metade. As quatro garantias são:

  • Atomicidade: tudo ou nada; se o crédito falhar, o débito é desfeito pelo rollback.
  • Consistência: o banco sai de um estado válido para outro estado válido; o saldo total não muda do nada.
  • Isolamento: transações concorrentes não veem os resultados parciais uma da outra.
  • Durabilidade: depois do COMMIT (confirmação), os dados sobrevivem até a uma queda de energia.

🌎 Integridade salvando o dia (e evitando desastres)

  • PIX do Banco Central (sistema brasileiro de pagamentos instantâneos): cada transferência é uma transação ACID entre instituições; sem atomicidade, haveria débitos sem crédito todos os dias.
  • Reservas da Azul (companhia aérea brasileira): dois clientes comprando a última poltrona ao mesmo tempo só funcionam bem graças ao isolamento; um deles recebe a recusa, não duas passagens para o mesmo assento.
  • Estoque da Amazon (varejista americana): o CHECK de quantidade não negativa impede que um bug de carrinho zere o estoque de um produto para valores impossíveis.
  • Cadastro no gov.br (portal do governo federal): a restrição UNIQUE no CPF impede duas contas públicas para a mesma pessoa.

🛠️ Comandos que você verá na prática

  • BEGIN / START TRANSACTION: abre a transação.
  • COMMIT: confirma tudo de uma vez, tornando as mudanças duráveis.
  • ROLLBACK: desfaz tudo desde o BEGIN, voltando ao estado anterior.
  • SAVEPOINT (ponto de salvamento): marca um ponto intermediário para desfazer só até ali, suportado por PostgreSQL e Oracle.

Aba 4 · Frameworks e bibliotecas populares no back-end

Sua missão é distinguir framework (do inglês, estrutura; um esqueleto pronto que chama o seu código, fenômeno chamado de inversão de controle) de biblioteca (conjunto de funções que VOCÊ chama quando quer), e conhecer os grandes nomes de cada linguagem: Spring Boot (Java), Django (Python), Express (Node.js), Laravel (PHP) e ASP.NET Core (C#). Na demo, você explora o cartão de cada framework com seus casos reais.

📚 Framework ou biblioteca? A pergunta do controle

Com uma biblioteca, você dirige: chama a função quando precisa, como usar a Axios (biblioteca JavaScript para requisições HTTP) dentro do seu próprio fluxo. Com um framework, o volante é dele: você escreve pedaços de código (controladores, modelos) e o framework decide quando chamá-los, dentro do ciclo de vida que ele mesmo monta. Essa inversão de controle é a fronteira conceitual entre os dois.

O prêmio de usar um framework é a produtividade: roteamento (decidir qual código atende cada URL), validação, segurança básica, conexão com banco e geração de respostas já vêm prontos e testados.

🌎 Quem usa o quê

  • Spring Boot (Java): extensão do Spring (ecossistema Java mantido pela VMware/Broadcom); usado em bancos e no back-end de empresas como o iFood (aplicativo brasileiro de entregas), que roda microsserviços (partes pequenas e independentes do sistema) em Java.
  • Django (Python): framework batteries-included (com tudo incluído) mantido pela Django Software Foundation; nasceu em redações de jornal e hoje roda o Instagram (rede social de fotos) e o Disqus (sistema de comentários).
  • Express (Node.js): minimalista, é a camada web por trás de incontáveis APIs em JavaScript; empresas como o Uber (aplicativo de transporte) usam Node.js em serviços que conversam com Express.
  • Laravel (PHP): um dos pacotes mais baixados do Packagist (repositório oficial de pacotes PHP); domina agências e e-commerces médios no Brasil.
  • ASP.NET Core (C#): framework multiplataforma da Microsoft; o Stack Overflow (site de perguntas e respostas de programação) roda sobre essa tecnologia desde a fundação.

🛠️ Como escolher sem drama

  • Ecossistema da equipe: a linguagem que o time domina pesa mais que modinha.
  • Tamanho do projeto: Django e Spring brilham em sistemas grandes com muitas telas e regras; Express e Flask (microframework Python) dão agilidade em APIs pequenas.
  • Mercado e vagas: no Brasil, Java com Spring e C# com .NET dominam o mercado corporativo; JavaScript e Python lideram startups.

Aba 5 · Frameworks ORM: bancos de dados sem SQL manual

Sua missão é dominar os ORMs (do inglês Object-Relational Mapping; em português, Mapeamento Objeto-Relacional): frameworks que traduzem objetos do seu código (classes como Cliente) em tabelas do banco (como clientes) e transformam chamadas de método em SQL (do inglês Structured Query Language; em português, Linguagem de Consulta Estruturada) gerado e parametrizado. Você vai ver o SQL nascer por trás de cada chamada e conhecer a armadilha clássica do N+1.

📚 O que um ORM faz por você

Sem ORM, cada operação vira SQL escrito à mão: strings concatenadas, parâmetros escapados manualmente e linhas de banco mapeadas campo a campo para objetos. Com ORM, você escreve código na sua linguagem e ele cuida da tradução:

  • Mapeamento: a classe Cliente vira a tabela clientes; o atributo nome vira a coluna nome. Anotações (como @Entity no Hibernate) ou convenções fazem a ligação.
  • Geração de SQL parametrizado: os valores viajam separados do comando, o que bloqueia a injeção de SQL (ataque que cola código malicioso dentro da consulta; listado há anos no OWASP Top 10, ranking de riscos da organização aberta de segurança de aplicações OWASP).
  • Portabilidade: trocar de MySQL para PostgreSQL mexe pouco no código, porque o dialeto (sotaque do SQL de cada banco) é problema do ORM.
  • Migrações: ferramentas como Flyway (Java) ou as migrations do Django versionam mudanças de esquema junto com o código.

Os nomes por linguagem: Hibernate (Java, integrado ao Spring), Django ORM e SQLAlchemy (Python), Entity Framework Core (C#), Eloquent (Laravel/PHP), Sequelize, TypeORM e Prisma (Node.js).

🌎 ORM no mundo real

  • Hibernate no iFood: os microsserviços Java usam Spring Data JPA (camada do Spring sobre a especificação JPA, Java Persistence API), que por baixo roda Hibernate contra bancos PostgreSQL.
  • Django ORM no Instagram: as models (classes de modelo) do Django viram consultas SQL otimizadas contra o PostgreSQL da empresa.
  • Entity Framework no Stack Overflow: o site de programação acessa o SQL Server (banco da Microsoft) via EF Core, com LINQ (consulta integrada à linguagem C#).
  • Prisma em startups Node.js: o Prisma (ORM moderno sueco) gera um cliente tipado e virou padrão em muitas startups JavaScript pela legibilidade.

🛠️ O custo escondido: o problema N+1

A comodidade do ORM tem uma armadilha famosa: listar 100 pedidos e, para cada um, acessar pedido.cliente pode disparar 1 consulta para os pedidos MAIS 100 consultas para os clientes: 101 viagens ao banco, o problema N+1. A cura é o eager loading (carregamento ansioso, como include no Prisma ou select_related no Django), que traz tudo em uma ou duas consultas com junção (join, operação que combina tabelas relacionadas).

repositório = camada que guarda os métodos de acesso a dados · ? = parâmetro enviado separado do comando (anti-injeção) · join = junção de tabelas relacionadas em uma consulta · eager loading = trazer os relacionados de uma vez · N+1 = 1 consulta da lista mais N consultas dos relacionados

CRUD
Criar, Ler, Atualizar e Apagar: as quatro operações básicas sobre um recurso.
API REST
Interface web com métodos HTTP (GET, POST, PUT, DELETE) e códigos de status (200, 201, 404).
JWT
Token assinado que prova o login a cada requisição, sem sessão em memória no servidor.
OAuth2
Protocolo de autorização usado por logins de terceiros, como Entrar com Google.
Validação de entrada
Conferir tipo, formato e tamanho dos dados antes de tocar no banco; no back-end, por segurança.
Entidade
Coisa do mundo real que vira tabela, como Cliente ou Pedido.
Cardinalidade
Quantos de um lado se ligam ao outro: 1:1, 1:N ou N:M.
Tabela associativa
Tabela de junção que resolve relacionamentos N:M, como item_pedido.
Chave primária / estrangeira
Coluna que identifica a linha / coluna que aponta para a chave de outra tabela.
Normalização (1FN, 2FN, 3FN)
Regras que eliminam repetições: valores atômicos, dependência da chave inteira e fim da dependência transitiva.
Anomalia de atualização
Precisar editar várias linhas para mudar um fato único, risco de inconsistência.
Restrições de integridade
PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL e CHECK: regras que o próprio banco impõe.
Transação
Pacote de operações tudo-ou-nada, confirmado por COMMIT ou desfeito por ROLLBACK.
ACID
Atomicidade, Consistência, Isolamento e Durabilidade: as quatro garantias das transações.
Framework
Esqueleto pronto que chama o seu código (inversão de controle).
Biblioteca
Conjunto de funções que você chama quando quer; você mantém o controle do fluxo.
ORM
Mapeamento Objeto-Relacional: classes viram tabelas e métodos viram SQL.
SQL parametrizado
Valores enviados separados do comando; bloqueia injeção de SQL.
Problema N+1
Uma consulta da lista mais N consultas dos relacionados; curado com eager loading e join.
Hibernate / Prisma / Django ORM
