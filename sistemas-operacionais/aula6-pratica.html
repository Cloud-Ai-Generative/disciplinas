Aba 1 · Aspectos essenciais de arquivos

Sua missão é entender o arquivo (do inglês file; unidade lógica de armazenamento que o SO oferece aos programas, abstraindo os detalhes físicos do disco) como a principal abstração do sistema de arquivos. Você vai conhecer os metadados (informações sobre o arquivo: nome, tamanho, permissões, datas), os tipos (regular, diretório, link simbólico, dispositivo) e as operações básicas (abrir, ler, escrever, fechar).

📚 O que é um arquivo para o SO

Para o usuário, um arquivo é um documento, uma foto ou um programa. Para o SO, é uma sequência nomeada de bytes armazenada em disco (ou em memória, no caso de sistemas de arquivos virtuais como /proc no Linux). O SO esconde a complexidade física: setores, trilhas e cilindros do disco viram uma abstração simples de "arquivo com nome e conteúdo".

Todo arquivo tem dois componentes:

  • Dados: o conteúdo propriamente dito (texto, imagem, código executável).
  • Metadados: informações sobre o arquivo, guardadas em uma estrutura chamada inode (do inglês index node; em português, nó de índice, usado em sistemas Unix/Linux) ou MFT record (do inglês Master File Table; em português, Tabela Mestre de Arquivos, usada no NTFS do Windows).

📚 Metadados essenciais

  • Nome: identificador legível para humanos (relatório.pdf, foto.jpg).
  • Tamanho: quantidade de bytes do conteúdo.
  • Tipo: regular (arquivo comum), diretório (pasta), link simbólico (atalho), dispositivo (como /dev/sda no Linux).
  • Permissões: quem pode ler, escrever ou executar (dono, grupo, outros). No Linux, representadas como rwxr-xr-x; no Windows, ACLs (do inglês Access Control Lists; em português, Listas de Controle de Acesso).
  • Datas: criação, última modificação, último acesso. No Linux, são ctime, mtime e atime.
  • Proprietário: usuário e grupo donos do arquivo (UID e GID no Linux; SID no Windows).
  • Localização física: ponteiros para os blocos do disco onde o conteúdo está guardado.

🌎 Arquivos no seu dia a dia

  • /etc/passwd no Linux: arquivo regular que guarda a lista de usuários do sistema; cada linha tem sete campos separados por dois-pontos.
  • C:\Windows\System32: diretório do Windows com milhares de arquivos DLL (do inglês Dynamic Link Library; em português, Biblioteca de Ligação Dinâmica, bibliotecas compartilhadas) essenciais para o SO.
  • pagefile.sys: arquivo oculto do Windows que serve como memória virtual; pode ter dezenas de GB.
  • .git no diretório de projetos: diretório oculto (começa com ponto no Unix) que guarda todo o histórico do Git (sistema de controle de versão criado por Linus Torvalds).
  • /dev/null no Linux: arquivo especial de dispositivo que descarta tudo que é escrito nele; usado para silenciar saídas de comandos.

🛠️ Operações básicas sobre arquivos

  • open(): abre o arquivo e retorna um descritor (número que identifica o arquivo aberto).
  • read(): lê bytes do arquivo para a memória do programa.
  • write(): escreve bytes da memória do programa no arquivo.
  • close(): fecha o arquivo e libera o descritor.
  • seek(): move o ponteiro de leitura/escrita para uma posição específica.
  • stat(): obtém os metadados sem abrir o conteúdo.

Essas chamadas de sistema (system calls) são a interface entre o programa e o SO. Linguagens como C, Python e Java oferecem wrappers (invólucros) sobre elas.

Aba 2 · Diretórios e estrutura hierárquica

Sua missão é dominar os diretórios (do inglês directories; em português, pastas; arquivos especiais que contêm uma lista de nomes de outros arquivos e seus respectivos inodes) e a estrutura hierárquica em árvore que organiza todos os arquivos do sistema. Você vai aprender a diferença entre caminho absoluto (começa na raiz /) e caminho relativo (começa no diretório atual), e as operações essenciais sobre diretórios.

📚 O que é um diretório

Um diretório é, tecnicamente, um arquivo especial cujo conteúdo é uma tabela de pares (nome, número do inode). Quando você lista o conteúdo de uma pasta com ls, o SO lê esse arquivo especial e, para cada entrada, consulta o inode correspondente para obter os metadados.

Características importantes:

  • Entradas especiais: todo diretório tem pelo menos duas entradas: . (ponto, aponta para si mesmo) e .. (dois pontos, aponta para o diretório pai).
  • Limites: no Linux ext4, um diretório pode ter até 64.000 subdiretórios (limite que pode ser aumentado com a opção dir_nlink).
  • Permissões especiais: a permissão de execução (x) em um diretório significa "pode entrar nele"; sem ela, você não pode acessar o conteúdo mesmo tendo permissão de leitura.

📚 Caminhos: absoluto versus relativo

  • Caminho absoluto: começa na raiz do sistema de arquivos (/) e desce até o arquivo. Exemplo: /home/maria/documentos/relatorio.pdf. Sempre funciona, não importa onde você esteja.
  • Caminho relativo: começa no diretório atual (chamado de working directory ou current directory). Exemplo: se você está em /home/maria, o caminho relativo documentos/relatorio.pdf aponta para o mesmo arquivo.
  • Atalhos comuns: ~ (til) é o diretório home do usuário atual; . é o diretório atual; .. é o diretório pai.

No Windows, a raiz é a letra da unidade (C:\, D:\), e o separador é a barra invertida (\), embora a maioria dos programas modernos aceite a barra normal (/) também.

🌎 Estruturas de diretórios no mundo real

  • Filesystem Hierarchy Standard (FHS): padrão que define a estrutura de diretórios do Linux. Diretórios principais: /bin (binários essenciais), /etc (configurações), /home (diretórios dos usuários), /var (dados variáveis como logs), /tmp (arquivos temporários).
  • Windows: estrutura menos padronizada, mas com convenções: C:\Windows (sistema), C:\Program Files (aplicativos), C:\Users (diretórios dos usuários).
  • macOS: baseado no Unix, segue o FHS mas com adições da Apple como /Applications e /Library.
  • Android: usa uma variação do Linux com diretórios específicos como /data (dados dos apps) e /sdcard (armazenamento externo).
  • Projetos Python: convenção moderna com src/ (código-fonte), tests/ (testes), docs/ (documentação), venv/ (ambiente virtual).

🛠️ Operações sobre diretórios

  • mkdir(): cria um novo diretório.
  • rmdir(): remove um diretório vazio.
  • opendir()/readdir()/closedir(): abre, lê e fecha um diretório para listar seu conteúdo.
  • chdir(): muda o diretório atual do processo.
  • getcwd(): obtém o caminho absoluto do diretório atual (do inglês get current working directory).
  • rename(): renomeia ou move um arquivo ou diretório.

Comandos equivalentes no terminal Linux: mkdir, rmdir, ls, cd, pwd, mv.

Aba 3 · Desempenho do sistema de arquivos

Sua missão é entender por que o acesso a disco é milhares de vezes mais lento que o acesso à RAM, e como o SO usa técnicas de cache (do inglês, esconderijo; em português, memória temporária de alta velocidade), buffer (área de armazenamento temporário) e prefetch (do inglês, pré-busca; leitura antecipada de dados) para esconder essa lentidão. Você vai simular acertos e erros de cache e ver o impacto no desempenho.

📚 O abismo de velocidade: RAM versus disco

A diferença de velocidade entre memória principal (RAM) e armazenamento secundário (disco) é um dos maiores desafios da arquitetura de computadores:

  • RAM DDR5: latência de 10-20 nanossegundos (ns), largura de banda de 50 GB/s.
  • SSD NVMe: latência de 10-100 microssegundos (μs), largura de banda de 3-7 GB/s.
  • HDD mecânico: latência de 5-15 milissegundos (ms), largura de banda de 100-200 MB/s.

Isso significa que acessar um HDD é 1 milhão de vezes mais lento que acessar a RAM. Sem técnicas de otimização, qualquer programa que leia arquivos seria insuportavelmente lento.

📚 Técnicas de otimização de desempenho

  • Cache de sistema de arquivos (do inglês page cache ou buffer cache): o SO mantém na RAM uma cópia dos blocos de disco lidos recentemente. Quando um programa pede um bloco que já está no cache, a resposta é imediata (cache hit, acerto); senão, precisa ler do disco (cache miss, erro).
  • Buffer: área de memória usada para acumular escritas antes de gravá-las no disco. Em vez de gravar cada byte imediatamente (lento), o SO acumula e grava em lotes (flush, descarga).
  • Prefetch (pré-busca): quando um programa lê blocos sequenciais, o SO antecipa e carrega os próximos blocos no cache antes de serem pedidos. Funciona porque a maioria dos acessos a arquivos é sequencial.
  • Journaling (do inglês, registrar em diário): técnica usada por sistemas como ext4 e NTFS que grava as intenções de modificação em um diário antes de executá-las, acelerando a recuperação após falhas.
  • Read-ahead: leitura antecipada de blocos adjacentes ao solicitado, configurável no Linux com blockdev --setra.

🌎 Desempenho no mundo real

  • Linux page cache: o comando free -h mostra a memória usada como cache. É comum ver vários GB de RAM "ocupados" por cache, mas essa memória é liberada automaticamente quando programas precisam.
  • Windows SuperFetch (agora chamado SysMain): serviço que analisa padrões de uso e pré-carrega aplicativos frequentes na RAM.
  • macOS Unified Buffer Cache: gerencia cache de arquivos e memória virtual de forma unificada.
  • Bancos de dados: PostgreSQL e MySQL mantêm seus próprios caches (shared_buffers e innodb_buffer_pool) além do cache do SO, porque conhecem os padrões de acesso melhor que o SO genérico.
  • CDNs (do inglês Content Delivery Networks; em português, Redes de Distribuição de Conteúdo, como Cloudflare e Akamai): funcionam como caches gigantescos distribuídos pelo mundo, acelerando o acesso a sites.

🛠️ Medindo desempenho de disco

  • hdparm -tT /dev/sda (Linux): mede velocidade de leitura do disco e do cache.
  • fio (do inglês Flexible I/O Tester; em português, Testador Flexível de E/S): ferramenta profissional para benchmark de disco, usada por administradores de sistemas.
  • iostat (do pacote sysstat): mostra estatísticas de E/S em tempo real.
  • CrystalDiskMark (Windows): ferramenta gráfica popular para medir velocidade de SSDs e HDDs.
  • dd (Linux/Unix): comando simples para testes básicos de leitura/escrita.

Aba 4 · Sistemas de arquivos modernos

Sua missão é conhecer os sistemas de arquivos (do inglês file systems; em português, sistemas de arquivos; software que organiza como os dados são gravados e lidos no disco) mais usados hoje: ext4 (padrão do Linux), NTFS (padrão do Windows), APFS (padrão da Apple) e ZFS (sistema avançado usado em servidores). Você vai comparar recursos, casos de uso e limitações de cada um.

📚 O que um sistema de arquivos faz

O sistema de arquivos é a camada de software que traduz operações lógicas (criar arquivo, ler diretório) em operações físicas (gravar setores no disco). Suas responsabilidades incluem:

  • Organização: definir como arquivos e diretórios são estruturados no disco.
  • Alocação: decidir quais blocos do disco cada arquivo ocupa.
  • Metadados: manter inodes ou estruturas equivalentes com informações sobre cada arquivo.
  • Consistência: garantir que falhas de energia não corrompam dados.
  • Recuperação: verificar e reparar o sistema após falhas (com ferramentas como fsck ou chkdsk).

📚 Os quatro sistemas mais usados

  • ext4 (do inglês Fourth Extended Filesystem; em português, Quarto Sistema de Arquivos Estendido): padrão da maioria das distribuições Linux (Ubuntu, Fedora, Debian). Suporta arquivos de até 16 TB e partições de até 1 EB (exabyte, 1 milhão de TB). Usa journaling para recuperação rápida após falhas.
  • NTFS (do inglês New Technology File System; em português, Sistema de Arquivos de Nova Tecnologia): padrão do Windows desde o Windows NT (1993). Suporta arquivos de até 16 EB, ACLs (listas de controle de acesso) detalhadas, criptografia (EFS, do inglês Encrypting File System), compressão e quotas (limites de espaço por usuário).
  • APFS (do inglês Apple File System; em português, Sistema de Arquivos da Apple): introduzido em 2017, substituiu o HFS+ (do inglês Hierarchical File System Plus). Otimizado para SSDs, suporta snapshots (instantâneos do sistema em um ponto no tempo), criptografia nativa e clonagem rápida de arquivos.
  • ZFS (do inglês Zettabyte File System; em português, Sistema de Arquivos Zettabyte): desenvolvido pela Sun Microsystems (hoje parte da Oracle), usado em servidores FreeBSD, TrueNAS e Oracle Solaris. Oferece recursos avançados como pools de armazenamento, checksums (verificação de integridade) em todos os blocos, snapshots, clones e compressão transparente. É considerado o sistema de arquivos mais robusto, mas exige mais RAM.

🌎 Sistemas de arquivos no mundo real

  • Ubuntu 24.04 LTS: usa ext4 por padrão na instalação típica.
  • Windows 11: usa NTFS na partição do sistema; exFAT (do inglês Extended File Allocation Table) em pendrives e cartões SD.
  • iPhone 15 e Mac com macOS Sonoma: usam APFS em todos os dispositivos de armazenamento.
  • Netflix Open Connect: a CDN própria da Netflix usa FreeBSD com ZFS para armazenar e distribuir vídeos.
  • TrueNAS (solução de armazenamento da iXsystems, empresa americana): usa ZFS como base para NAS (do inglês Network Attached Storage; em português, Armazenamento Conectado à Rede) empresariais.
  • Android: usa ext4 ou F2FS (do inglês Flash-Friendly File System; em português, Sistema de Arquivos Amigável a Flash, desenvolvido pela Samsung) otimizado para memória flash.

🛠️ Como escolher o sistema certo

  • Linux desktop/servidor comum: ext4 é a escolha segura e bem suportada.
  • Windows: NTFS é obrigatório para a partição do sistema; exFAT para pendrives que precisam ser lidos em Mac e Linux.
  • Mac/iPhone: APFS é o único suportado nativamente.
  • Servidores de armazenamento críticos: ZFS oferece a melhor proteção contra corrupção de dados, mas exige mais RAM (recomenda-se 1 GB de RAM por TB de armazenamento).
  • Dispositivos flash (pendrives, cartões SD): exFAT ou F2FS, otimizados para memória flash.

Aba 5 · Processamento paralelo e distribuído

Sua missão é entender como os sistemas de arquivos distribuídos (do inglês distributed file systems; sistemas que espalham dados por vários servidores em rede, apresentando-os como um único sistema de arquivos) permitem o processamento paralelo (múltiplos servidores trabalhando simultaneamente nos mesmos dados). Você vai conhecer o HDFS (do inglês Hadoop Distributed File System; em português, Sistema de Arquivos Distribuído Hadoop) e o GFS (do inglês Google File System; em português, Sistema de Arquivos do Google), e entender como eles dividem arquivos grandes em blocos distribuídos com replicação.

📚 Por que sistemas de arquivos distribuídos

Quando os dados crescem além da capacidade de um único servidor (petabytes de logs, bilhões de transações, vídeos de milhões de usuários), é preciso distribuí-los por vários servidores. Os desafios são:

  • Escalabilidade: adicionar mais servidores deve aumentar a capacidade total.
  • Tolerância a falhas: se um servidor cair, os dados devem continuar acessíveis.
  • Consistência: todos os clientes devem ver a mesma versão dos dados.
  • Desempenho: múltiplos clientes devem poder ler/escrever simultaneamente.

Sistemas de arquivos distribuídos resolvem esses desafios dividindo arquivos grandes em blocos (tipicamente 64 MB a 128 MB) e distribuindo esses blocos por vários servidores, com replicação (cópias em múltiplos servidores para tolerância a falhas).

📚 HDFS: o sistema de arquivos do Hadoop

O HDFS foi criado pelo Yahoo! (empresa americana de internet) em 2006, inspirado no GFS do Google, e é o sistema de arquivos padrão do Apache Hadoop (framework de processamento distribuído de código aberto). Suas características:

  • Arquitetura mestre-escravo: um NameNode (nó de nomes) gerencia os metadados (quais blocos formam cada arquivo, onde estão); vários DataNodes (nós de dados) armazenam os blocos reais.
  • Blocos grandes: 128 MB por padrão (versus 4 KB de sistemas tradicionais), otimizado para leitura sequencial de arquivos grandes.
  • Replicação padrão: cada bloco tem 3 cópias em servidores diferentes (fator de replicação 3).
  • Escrita única, múltiplas leituras: arquivos são escritos uma vez e lidos muitas vezes; não suporta modificações no meio do arquivo.
  • Processamento local: o princípio "mova a computação para os dados, não os dados para a computação". O framework MapReduce (modelo de programação do Hadoop) executa o processamento nos mesmos servidores que guardam os dados.

📚 GFS e sucessores do Google

O GFS (Google File System) foi desenvolvido internamente pelo Google e descrito em um artigo famoso de 2003. Era usado para armazenar os dados do mecanismo de busca, Gmail, YouTube e outros serviços. Evoluções:

  • GFS original (2003): blocos de 64 MB, replicação 3, mestre único (single master).
  • Colossus (2010): segunda geração, com múltiplos mestres e melhor escalabilidade.
  • Borg e Kubernetes: o Google evoluiu para orquestração de contêineres, mas o sistema de arquivos distribuído continua sendo a base.

O GFS inspirou não só o HDFS, mas também sistemas como o Ceph (sistema de código aberto usado em nuvens OpenStack) e o GlusterFS (da Red Hat).

🌎 Sistemas distribuídos no Brasil e no mundo

  • Magazine Luiza (Magalu): usa Hadoop com HDFS para processar dados de cliques, recomendações e análises de vendas.
  • Nubank: usa Apache Spark (framework de processamento distribuído sucessor do MapReduce) sobre HDFS ou S3 (da AWS) para análises de risco de crédito e detecção de fraude.
  • iFood: processa petabytes de dados de pedidos e entregas com Hadoop e Spark.
  • Netflix: usa S3 (Amazon Simple Storage Service) como data lake (lago de dados, repositório centralizado de dados em escala) para análises de viewing patterns (padrões de visualização).
  • Facebook: desenvolveu o HDFS em larga escala e criou o Hive (ferramenta de consulta SQL sobre Hadoop) para análises de dados sociais.
  • Governo Federal: o Serpro (Serviço Federal de Processamento de Dados) usa Hadoop para processar dados de impostos e previdência social.

🛠️ Ferramentas do ecossistema Hadoop

  • HDFS: sistema de arquivos distribuído.
  • MapReduce: modelo de programação para processamento paralelo (hoje substituído por Spark em muitos casos).
  • Apache Spark: framework de processamento em memória, 100x mais rápido que MapReduce para muitas cargas.
  • Hive: consulta SQL sobre dados no HDFS.
  • HBase: banco de dados NoSQL columnar sobre HDFS.
  • Pig: linguagem de script para transformações de dados.
  • Oozie: agendador de workflows (fluxos de trabalho) Hadoop.

Enunciado: Você é administrador de sistemas na DataCorp Brasil (empresa fictícia de análise de dados, inspirada em empresas como Neoway e Serasa Experian) e precisa resolver quatro problemas técnicos urgentes.

Problema 3 — Migração de sistema: a empresa precisa migrar um sistema legado que usa NTFS (Windows) para Linux. Os arquivos têm ACLs detalhadas e criptografia EFS.

Problema 4 — Big Data: a empresa quer processar 500 TB de logs de cliques para análises de comportamento. Precisa escolher entre HDFS com MapReduce ou Spark sobre S3.

Parte 1 — Arquivos corrompidos (Abas 1 e 4): explique como o journaling do ext4 (termo da cola rápida) ajuda na recuperação após queda de energia. Parte 2 — Lentidão (Aba 3): o servidor tem 2 GB livres e 14 GB em buff/cache. Isso é um problema? Explique o que é page cache (termo da cola rápida) e por que o Linux usa tanta RAM como cache. Se um programa precisar de mais memória, o que acontece com o cache? Cite a diferença de latência entre cache hit e cache miss (termos da cola rápida).

Parte 3 — Migração (Abas 2 e 4): proponha uma estratégia para migrar arquivos NTFS com ACLs e criptografia EFS para Linux. Cite qual sistema de arquivos você usaria no Linux (termo da cola rápida) e como mapearia as permissões NTFS para permissões Linux. Explique o que fazer com os arquivos criptografados.

Parte 4 — Big Data (Aba 5): para processar 500 TB de logs, recomende HDFS com MapReduce ou Spark sobre S3. Justifique com base em: custo, desempenho, complexidade e casos de uso. Cite o tamanho de bloco do HDFS (termo da cola rápida), o fator de replicação padrão e quantos blocos totais (com réplicas) seriam necessários para 500 TB.

📚 Dica para o Chefão

Na Parte 1, o journaling grava as intenções antes de executar; após queda, o fsck replaya o journal em segundos. O comando é fsck.ext4 ou e2fsck. Na Parte 2, 14 GB em cache é normal e saudável; o Linux libera automaticamente quando programas precisam. Cache hit ~10 ns, miss ~10 ms (1 milhão de vezes mais lento). Na Parte 3, use ext4 ou XFS; mapeie ACLs NTFS para POSIX ACLs; descriptografe antes de migrar ou use ferramentas como ntfs-3g. Na Parte 4, Spark sobre S3 é mais moderno e flexível; HDFS exige infraestrutura própria. 500 TB / 128 MB = ~4 milhões de blocos; com replicação 3 = 12 milhões de blocos totais.
