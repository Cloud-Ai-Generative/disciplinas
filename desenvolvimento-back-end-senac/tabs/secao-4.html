📐 Os dados e as camadas

📐 D-06 Entidade-relacionamento A tabela doacoes

👀 Como ler: cada linha é uma coluna da tabela, com o tipo no PostgreSQL. PK é a chave primária, gerada pelo banco. Só doador pode ficar vazio.

📐 D-07 C4 · Componentes O caminho de uma requisição dentro da API

👀 Como ler: cada caixa é um arquivo da pasta app/. A requisição entra pelas rotas, passa pela validação, vira um objeto do modelo e chega ao banco. Qualquer erro sai pelo mesmo formato.

api/ ├── app/ │ ├── __init__.py # create_app(): monta a aplicação │ ├── config.py # configuração lida do .env │ ├── extensions.py # o objeto db │ ├── models.py # o modelo Doacao ← nesta etapa │ ├── cli.py # o comando "flask seed" ← nesta etapa │ ├── routes.py # as rotas GET ← nesta etapa │ └── erros.py # o formato único de erro ├── tests/ # testes automatizados ├── docs/adr/ # decisões de arquitetura ├── requests.http # requisições prontas ├── Dockerfile └── docker-compose.yml
💡 Conceito: ORM e modelo

🔄 ORM (Object-Relational Mapping)

O banco fala SQL e guarda linhas em tabelas. O Python trabalha com objetos. O ORM (aqui, o SQLAlchemy) traduz um no outro: você escreve Doacao(tipo="roupa", ...) e ele gera o INSERT; pede db.select(Doacao) e ele gera o SELECT.

api/app/models.py
class Doacao(db.Model):
    __tablename__ = "doacoes"

    id = db.Column(db.Integer, primary_key=True)
    tipo = db.Column(db.String(20), nullable=False)          # alimento, roupa ou higiene
    descricao = db.Column(db.String(200), nullable=False)
    quantidade = db.Column(db.Integer, nullable=False)
    data_recebimento = db.Column(db.Date, nullable=False)
    doador = db.Column(db.String(100), nullable=True)        # opcional
    criado_em = db.Column(db.DateTime(timezone=True), nullable=False,
                          default=lambda: datetime.now(timezone.utc))

    def to_dict(self):
        """Converte a doação no JSON que a API devolve."""
        return {"id": self.id, "tipo": self.tipo, "descricao": self.descricao,
                "quantidade": self.quantidade,
                "data_recebimento": self.data_recebimento.isoformat(),
                "doador": self.doador}
💡 Repare: criado_em existe na tabela, mas não aparece no to_dict(). O modelo do banco e o JSON da API não precisam ser iguais: a API decide o que expor.
📝 As decisões: ADRs 0002, 0005 e 0008
🗳️ Decisão do time: como organizar o código da API?
Cores: 🟢 escolha do time · 🟠 alternativa válida, com custo · 🔴 opção errada
ADR 0002 · PostgreSQL como banco de dados aceita

Contexto: as doações se perdem nos cadernos; várias pessoas registram ao mesmo tempo.

Decisão: PostgreSQL 17, em contêiner.

Alternativas: SQLite (ótimo para os testes, fraco para vários usuários num servidor); MySQL (também atenderia); NoSQL (os dados têm estrutura fixa e conhecida).

Consequências: banco robusto e gratuito, com restrições que protegem os dados; em troca, é mais um serviço para rodar (o Compose resolve).

ADR 0005 · App factory, blueprint, modelo e validação separados aceita

Contexto: tudo num app.py funciona no começo, mas mistura responsabilidades e dificulta testar.

Decisão: um arquivo por responsabilidade (diagrama D-07).

Alternativas: arquivo único; camadas completas com serviços e repositórios (excesso para um recurso só).

Consequências: cada arquivo tem um motivo para mudar e os testes trocam o banco pela app factory; em troca, mais arquivos para quem está começando.

ADR 0008 · db.create_all() em vez de migrations, por enquanto aceita

Contexto: a tabela precisa existir antes do primeiro uso.

Decisão: create_all() ao subir a API: cria o que falta e não mexe no que existe.

Alternativas: Flask-Migrate (Alembic), o caminho certo quando o modelo começar a mudar.

Consequências: zero passos extras; em troca, mudar uma coluna exige zerar o banco até adotarmos migrations.

Arquivos completos: ADR 0002 · ADR 0005 · ADR 0008

✋ Errou? Casos comuns desta etapa
Adicionei um campo no modelo, mas a coluna não aparece no banco

É a consequência do ADR 0008: create_all() não altera tabelas existentes. Zere o banco com docker compose down -v e suba de novo. Em projeto real, use migrations (Flask-Migrate).

role "vila" does not exist no psql

Você mudou POSTGRES_USER no .env. Use o seu usuário no lugar de vila nos comandos.
