🔢 Como ler a numeração

Cada diagrama tem um número (D-01, D-02...), uma etiqueta com o tipo e um título. O número permite citar o diagrama sem ambiguidade: "repare no D-06". Clique no título para ir até ele.

🧩 Os tipos de diagrama

➡️ Fluxo (fluxograma)

Para que serve: mostrar um caminho: por onde passa uma informação, uma pessoa ou um pedido, passo a passo.

Como ler: siga as setas. Caixas são etapas ou participantes; o texto na seta diz o que passa de um para o outro. Setas tracejadas indicam algo opcional ou que pode falhar.

Onde aparece: D-00 e D-01.

🗺️ Modelo C4 (Contexto, Contêineres, Componentes)

Para que serve: desenhar a arquitetura em níveis de zoom, como um mapa. O nome vem de quatro níveis: Contexto, Contêineres, Componentes e Código. Usamos os três primeiros.

  • Contexto (D-02): o sistema visto de longe: quem usa e com quem ele conversa.
  • Contêineres (D-04): as partes que rodam separadas, como a API e o banco. Aqui "contêiner" é qualquer coisa que roda sozinha, e coincide com os contêineres do Docker.
  • Componentes (D-07): as peças de dentro de um contêiner; aqui, os arquivos da pasta app/.

Como ler: comece pelo Contexto e vá dando zoom. Cada nível responde a uma pergunta diferente: "com quem fala?", "o que roda?", "do que é feito?".

⏱️ UML · Diagrama de sequência

Para que serve: mostrar a ordem no tempo das mensagens entre participantes: quem chama quem, e o que volta.

Como ler: os participantes ficam no topo, cada um com uma linha vertical. De cima para baixo é o tempo. Seta cheia é uma chamada; seta tracejada é a resposta. Um bloco alt mostra caminhos alternativos (deu certo / deu errado), e um bloco loop, algo que se repete.

Onde aparece: D-03, D-05, D-08 e D-09. UML (Unified Modeling Language) é a linguagem padrão de diagramas de software; o de sequência é um dos seus tipos.

🗃️ Entidade-relacionamento (ER)

Para que serve: mostrar como os dados ficam guardados no banco: as tabelas (entidades), suas colunas e como elas se relacionam.

Como ler: cada caixa é uma tabela. Cada linha é uma coluna, com o tipo (integer, varchar, date...), o nome e uma marca como PK (chave primária, o identificador único). Quando há várias tabelas, linhas entre elas mostram os relacionamentos.

Onde aparece: D-06. Hoje temos uma tabela só; quando a associação cadastrar as famílias atendidas, o diagrama ganha uma segunda tabela e um relacionamento.

🔀 Histórico do Git (gitGraph)

Para que serve: mostrar a história de um repositório: os commits em ordem, os branches e as tags.

Como ler: cada bolinha é um commit, do mais antigo (esquerda) para o mais recente (direita). Cada linha horizontal é um branch; quando uma linha sai de outra, um branch novo começou ali. As etiquetas marcam as tags.

Onde aparece: D-10.

🧜 Mermaid: diagramas escritos em texto. Todos os diagramas do ODA são escritos em Mermaid, uma linguagem de texto que vira desenho. O botão ⟨/⟩ Código, em cima de cada diagrama, mostra o texto que o gerou, e o GitHub desenha Mermaid sozinho em arquivos .md. Por ser texto, o diagrama fica versionado no Git, junto com o código.
📝 O que é um ADR

📝 ADR (Architecture Decision Record)

Para que serve: registrar uma decisão de arquitetura para responder, meses depois, à pergunta "por que foi feito assim?". Sem ADR, o motivo fica na cabeça de quem decidiu e vai embora com essa pessoa.

Estrutura: todo ADR tem as mesmas partes:

  • Contexto: a situação e o problema que exigiram a decisão.
  • Decisão: o que foi escolhido.
  • Alternativas: o que mais foi considerado, e por que não foi escolhido.
  • Consequências: o que se ganha e o preço que se paga.

Ciclo de vida: proposta → aceita → (um dia, talvez) substituída. Depois de aceita, a decisão vale para todo o time, inclusive para quem votou diferente. Se o contexto mudar, ninguém edita o ADR antigo: escreve-se um novo, que o substitui, e o antigo fica marcado como "substituída pelo ADR 00XX". Assim o histórico das decisões nunca se perde.
