💡 Conceito: REST em quatro ideias

🔁 REST (Representational State Transfer)

  1. Recurso: a "coisa" que a API gerencia, com um endereço. Aqui: /doacoes (todas) e /doacoes/3 (a de id 3).
  2. Verbos HTTP: dizem a ação. GET lê, POST cria, PUT substitui, DELETE remove.
  3. Representação: o recurso viaja como texto; usamos JSON.
  4. Sem estado (stateless): cada requisição traz tudo o que precisa. O servidor não "lembra" do pedido anterior.

📜 API First: o contrato antes do código

📜 API First

API First é uma abordagem em que a API é desenhada e acordada como um contrato antes de qualquer código. O contrato diz quais rotas existem, o que cada uma recebe, o que devolve e quais erros podem acontecer. Com ele em mãos, front-end e back-end trabalham em paralelo, sem esperar um pelo outro.

Você também vai ouvir design-first ou contract-first: são o mesmo fluxo de trabalho, escrever e revisar o contrato antes de programar.

Code-firstAPI First
Ponto de partidaO código das rotasO contrato da API

Front-endEspera o back-end ficar prontoComeça junto, usando o contrato
DivergênciasAparecem na integração, com retrabalhoAparecem na conversa, antes do código
⚠️ No mundo real, o contrato é desenhado junto com o time de front-end, com a PO e o QA, numa sessão de design: cada lado traz o que precisa, e os casos difíceis aparecem antes do código. Para fins didáticos, nesta aula o nosso time desenha o contrato sozinho. Em projetos reais, não pule essa conversa.
💡 O formato do contrato: no mercado, o contrato costuma virar um arquivo OpenAPI, que ferramentas usam para gerar documentação e um mock (uma API de mentira que já responde pelo contrato). Aqui, o contrato é a tabela abaixo mais o arquivo requests.http. O OpenAPI fica como próximo passo.
ADR 0009 · Contrato antes do código (API First) aceita

Contexto: o aplicativo da turma de front-end vai consumir a nossa API; sem um acordo, cada time supõe uma coisa e a integração vira retrabalho.

Decisão: definir o contrato (rotas, verbos, campos, status e formato de erro) antes do código. Nesta aula, o back-end desenha e a PO leva para o front-end validar.

Alternativas: code-first (começa rápido, mas o front-end espera e as diferenças aparecem tarde); OpenAPI desde já (padrão de mercado, mas mais difícil de ler nesta etapa).

Consequências: os times trabalham em paralelo e decidem os casos difíceis antes; em troca, o contrato ainda não está num formato que ferramentas leem sozinhas.

Arquivo completo: ADR 0009

❓ O que é um ADR e como ler?

ADR 0001 · Flask como framework da API aceita

Contexto: turma aprendendo back-end; o objetivo é entender como a API funciona por dentro.

Decisão: Flask, com Flask-SQLAlchemy para o banco.

Alternativas: FastAPI valida e documenta sozinho, mas esconde justamente a validação que queremos ensinar; Django REST Framework traz muitas convenções de uma vez para uma API de um recurso só.

Consequências: código pequeno e explícito; em troca, escrevemos a validação à mão (ADR 0004).
