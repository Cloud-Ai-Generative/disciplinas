🔀 Git, GitHub e GitLab: guardar, versionar e trabalhar em equipe

Todo projeto do guia — o Hello World da Tab 2, 3 ou 3-P, as APIs das Tabs 6, 7 e 9 — termina no mesmo lugar: num repositório Git. Esta aba ensina isso uma vez só, com o mouse no VS Code e no IntelliJ: guardar versões, enviar para o GitHub, trabalhar em equipe com branch e Pull Request, resolver conflito e entender o que é CI/CD.

🗺️ O caminho desta aba: ⓪ por que Git → ① instalar e criar a conta → ② as palavras do Git → ③ publicar o primeiro projeto → ④ o dia a dia → ⑤ trabalho em equipe (branch + Pull Request) → ⑥ resolver um conflito → ⑦ GitLab: o que muda → ⑧ CI/CD → ⑨ erros comuns e quiz. Tempo total: ~1h30.
🧭 Antes de começar: tenha um projeto pronto para guardar — o hello-spring (Tab 2), o HelloDotnetApi (Tab 3) ou o hello-api (Tab 3-P). Os passos com 🖱️ são com o mouse e aparecem para as duas IDEs; ⌨️ Prefere o terminal? é opcional.

⓪ 🎮 Por que usar Git

🎮
Analogia do "salvar o jogo": antes de enfrentar o chefão, você salva. Se der errado, volta para aquele ponto. O Git faz isso com o código: cada commit é um ponto de salvamento, com uma legenda dizendo o que mudou. E o GitHub é a "nuvem" onde esses saves ficam guardados — e onde o seu time joga junto.
O que éOnde roda
🔀 GitO programa que guarda o histórico do códigoNo seu computador (a IDE usa por baixo)
🐙 GitHubUm site que guarda uma cópia do histórico na nuvem e organiza o trabalho em equipegithub.com (Microsoft)
🦊 GitLabUm site parecido com o GitHub, muito usado em empresas — pode rodar no servidor da própria empresagitlab.com ou servidor próprio

Sem Git: projeto_final_v2_AGORA_VAI.zip no e-mail. Com Git: um histórico com quem mudou o quê, quando e por quê, e a chance de voltar a qualquer ponto.

① 🧰 Instalar o Git e criar a conta no GitHub

1 🖱️ Instalar o Git (Windows)

  1. Entre em git-scm.com/downloads/win → clique em Click here to download (instalador x64).
  2. Abra o arquivo baixado → Sim na pergunta do Windows → clique em Next em todas as telas (as opções padrão servem) → Install → Finish.
  3. Feche e abra de novo o VS Code ou o IntelliJ, para eles acharem o Git.
☕ Usa IntelliJ? Ele mesmo oferece instalar: quando aparecer "Git is not installed", clique em Download and Install.
🍎 macOS e 🐧 Linux

macOS: na primeira vez que algo usar o Git, o sistema oferece instalar as Command Line Tools — aceite. Linux (Ubuntu/Debian): sudo apt install git.

2 Dizer ao Git quem é você (uma vez por computador)

Todo commit leva o nome e o e-mail de quem fez. É o único passo que precisa do terminal (no IntelliJ, se você esquecer, ele pergunta numa janela):

  1. No VS Code: Terminal → New Terminal · no IntelliJ: aba Terminal (Alt+F12).
  2. Digite as duas linhas, uma de cada vez, com os seus dados (use o mesmo e-mail da conta do GitHub):
terminal — uma vez por computador 
git config --global user.name "Seu Nome"
git config --global user.email "seu@email.com"
git config --global init.defaultBranch main     # todo repositório novo começa no branch "main"
git config --global pull.rebase false           # no pull, junta com "merge" (evita o erro "divergent branches")
✅ Resultado esperado: nenhuma resposta — no terminal, silêncio quer dizer que deu certo. Para conferir: git config --global --list.

3 🖱️ Criar a conta no GitHub

  1. Entre em github.com/signup → e-mail, senha e nome de usuário → confirme o código que chega no e-mail. É gratuito.
  2. Recomendado: ligue a verificação em duas etapas em Settings → Password and authentication.
🎓 É estudante? O GitHub Student Developer Pack dá ferramentas pagas de graça com o e-mail da faculdade.

② 📖 As palavras do Git

PalavraEm uma frase
Repositório (repo)O projeto + todo o histórico dele. Fica numa pasta escondida .git.
CommitUm ponto de salvamento: as mudanças + uma mensagem explicando o que foi feito.
Stage (preparar)Escolher quais mudanças vão no próximo commit.
BranchUma linha paralela de trabalho. main é a principal.
Remoto (origin)A cópia do repositório no site (GitHub ou GitLab).
Push / PullEnviar seus commits para o site / trazer de lá o que os outros enviaram.
CloneBaixar um repositório inteiro do site para o seu computador.
Pull Request (PR)Pedido para alguém revisar o seu branch antes de juntá-lo ao main. No GitLab: Merge Request (MR).
MergeJuntar um branch em outro.
ConflitoDuas pessoas mudaram a mesma linha: o Git pede para um humano escolher.
.gitignoreA lista do que o Git deve ignorar (pastas geradas, senhas).

③ ☁️ Publicar o primeiro projeto no GitHub

1 🙈 Antes: o .gitignore

Pastas que a IDE ou o compilador geram sozinhos não vão para o Git: deixam o repositório pesado e criam conflito entre colegas. Senhas e chaves nunca vão. Os ZIPs do guia já trazem um .gitignore; confira se ele está na raiz do projeto.

ProjetoIgnorarGerar automático
☕ Java (Maven)target/, .idea/o Spring Initializr já gera
🔷 C# (.NET)bin/, obj/, .vs/dotnet new gitignore
🐍 Python.venv/, __pycache__/modelos em github/gitignore
Todos.env, chaves, senhas—

💙 Pelo VS Code

  1. File → Open Folder… → a pasta do projeto.
  2. Barra da esquerda → ícone Source Control 🔀 (Ctrl+Shift+G).
  3. Clique em Publish to GitHub.
  4. Na primeira vez: Allow → o navegador abre o GitHub → login → Authorize Visual Studio Code → volte ao VS Code.
  5. No topo, escolha private repository (só você vê) ou public (todos veem).
  6. Confira a lista de arquivos: sem bin, obj, .venv → OK.
  7. Aparece "Successfully published…" → Open on GitHub. 🎉

☕ Pelo IntelliJ

  1. Com o projeto aberto: menu Git → GitHub → Share Project on GitHub (sem o menu Git? aperte Shift duas vezes e digite Share Project on GitHub).
  2. Na primeira vez: Log In via GitHub… → navegador → Authorize JetBrains → volte.
  3. Repository name → marque Private se quiser → Share.
  4. Se pedir nome e e-mail do Git, preencha (uma vez só).
  5. Janela Add Files For Initial Commit: sem target e .idea → Add.
  6. Aparece "Successfully shared project on GitHub" com o link. 🎉
✅ Resultado esperado: no site do GitHub, a página do repositório mostra os seus arquivos, o .gitignore e 1 commit.
⌨️ Prefere o terminal? Publicar com comandos (e chave SSH)

Crie antes, no site, um repositório vazio (sem README): botão + no canto → New repository.

terminal — primeiro envio 
git init                          # transforma a pasta num repositório
git add .                         # prepara todos os arquivos (o .gitignore barra o lixo)
git commit -m "feat: primeiro commit"
git remote add origin https://github.com/SEU-USUARIO/NOME-DO-REPO.git
git push -u origin main           # envia; nas próximas vezes, só "git push"

Com HTTPS, o Windows abre uma janela de login do GitHub na primeira vez. Prefere SSH (o "crachá" do seu computador)?

terminal — chave SSH 
ssh-keygen -t ed25519 -C "seu@email.com"    # Enter em todas as perguntas
cat ~/.ssh/id_ed25519.pub                    # copie a linha e cole em:
                                             # GitHub → Settings → SSH and GPG keys → New SSH key
ssh -T git@github.com                        # esperado: "Hi SEU-USUARIO! You've successfully authenticated"
# Daí em diante, use o endereço git@github.com:SEU-USUARIO/NOME-DO-REPO.git

⚠️ A chave .pub é pública (pode mostrar). A outra, id_ed25519, é privada: nunca compartilhe.

④ 🔁 O dia a dia: mudar → ver → commit → enviar

💙 VS Code

  1. Mude e salve um arquivo. No Explorer ele ganha um M (modificado).
  2. Source Control (Ctrl+Shift+G) → o arquivo aparece em Changes. Clique nele: antes e depois lado a lado.
  3. Escreva a mensagem na caixa Message.
  4. ✓ Commit (se perguntar sobre stage, Yes).
  5. Sync Changes: envia (push) e traz (pull).

☕ IntelliJ

  1. Mude um arquivo: o nome fica azul na coluna Project.
  2. Janela Commit (Ctrl+K) → o arquivo em Changes; dois cliques mostram o antes/depois.
  3. Deixe ☑ marcado e escreva a mensagem embaixo.
  4. Commit and Push… → Push.
  5. Para trazer o que outros enviaram: Git → Pull… (Ctrl+T atualiza o projeto).

✍️ Como escrever a mensagem do commit

Use o padrão Conventional Commits: um prefixo com o tipo da mudança + o que foi feito, no imperativo.

PrefixoQuandoExemplo
feat:coisa novafeat: adiciona rota /hello/{nome}
fix:correçãofix: recusa nome com mais de 30 letras
docs:documentaçãodocs: explica como rodar no README
test:testestest: cobre preço negativo
refactor:melhora sem mudar comportamentorefactor: extrai ProdutoMapper
⚠️ Commits pequenos e frequentes: um commit por ideia ("adiciona rota", "corrige validação"), não um commit gigante no fim do dia. Fica fácil revisar e, se precisar, desfazer só aquele passo.
⌨️ Prefere o terminal? O ciclo com comandos
terminal — o ciclo do dia a dia 
git status                        # o que mudou?
git diff                          # o que mudou DENTRO dos arquivos
git add Program.cs                # prepara (ou "git add ." para tudo)
git commit -m "feat: adiciona rota /hello/{nome}"
git push                          # envia
git pull                          # traz o que os outros enviaram
git log --oneline --graph         # o histórico, desenhado

⑤ 👥 Trabalho em equipe: branch + Pull Request

Em equipe, ninguém faz commit direto no main. Cada tarefa ganha um branch; quando fica pronta, vira um Pull Request, alguém revisa e só então ela entra no main.

1 🖱️ Criar o branch da tarefa

  • VS Code: clique no nome do branch no rodapé (canto inferior esquerdo, mostra main) → Create new branch… → feat/rota-nome → Enter.
  • IntelliJ: clique no nome do branch no topo da janela → New Branch… → feat/rota-nome → Create.
✅ Resultado esperado: o rodapé (VS Code) ou o topo (IntelliJ) passa a mostrar feat/rota-nome.

2 🖱️ Commitar e enviar o branch

Faça a mudança e o commit como na parte ④. Ao enviar: no VS Code o botão vira Publish Branch; no IntelliJ, Push cria o branch no site.

3 🖱️ Abrir o Pull Request no site

  1. Abra o repositório no GitHub: aparece uma faixa amarela "feat/rota-nome had recent pushes" → Compare & pull request.
  2. Título (pode ser a mensagem do commit) e uma descrição: o que mudou e como testar.
  3. À direita, em Reviewers, escolha quem vai revisar → Create pull request.
  4. O revisor abre a aba Files changed, comenta nas linhas e clica em Review changes → Approve.
  5. Aprovado: Merge pull request → Confirm merge → Delete branch.
  6. De volta à IDE: mude para o main e faça Pull (VS Code: Sync Changes; IntelliJ: Git → Pull…).
🔒 Proteja o main: GitHub → Settings → Branches → Add branch ruleset → exija Pull Request e aprovação. Assim, nem por engano alguém envia direto para o main.
📑 Decisões também entram por Pull Request: num projeto de verdade, as ADRs (as "atas" das decisões técnicas) ficam no próprio repositório, em docs/adr/, um arquivo Markdown por decisão. Uma decisão nova chega como Pull Request: o time comenta, aprova e só então ela passa a valer — o mesmo fluxo do código. O que é uma ADR e um modelo para copiar: Tab 4, parte ⑦.
⌨️ Prefere o terminal? Branch com comandos
terminal — branch da tarefa 
git switch main && git pull                  # começa do main atualizado
git switch -c feat/rota-nome                 # cria o branch e entra nele
# ... muda, git add, git commit ...
git push -u origin feat/rota-nome            # envia o branch; depois abra o PR no site
git switch main && git pull                  # depois do merge, atualiza o main
git branch -d feat/rota-nome                 # apaga o branch local

⑥ ⚔️ Resolver um conflito (exercício guiado)

Conflito não é erro: é o Git dizendo "duas pessoas mudaram a mesma linha, alguém precisa escolher". Vamos provocar um de propósito, com você fazendo o papel das duas pessoas.

1 🖱️ Provocar o conflito

  1. "Pessoa A" (no site): no GitHub, abra um arquivo do repositório (ex.: o README ou o controller) → ícone de lápis ✏️ → mude uma linha (ex.: a mensagem Hello para Olá do site) → Commit changes.
  2. "Pessoa B" (na IDE), sem fazer pull antes: mude a mesma linha para outra coisa (ex.: Olá da IDE) → commit.
  3. Tente enviar (Sync / Push). O Git recusa: o site tem um commit que você não tem. Faça Pull.
✅ Resultado esperado: a IDE avisa Merge conflict e marca o arquivo com um ! (VS Code) ou em vermelho (IntelliJ).

2 🖱️ Resolver

  • VS Code: abra o arquivo → clique em Resolve in Merge Editor. À esquerda a versão do site (Incoming), à direita a sua (Current), embaixo o resultado. Marque a(s) que fica(m) → Complete Merge → commit → Sync.
  • IntelliJ: na janela Conflicts → Merge… → três colunas (sua, resultado, do site): clique nas setas » / « para trazer cada lado → Apply → Commit and Push.
👀 Por baixo dos panos: o Git escreve no arquivo marcas assim — é isso que as IDEs mostram bonito:
como o arquivo fica durante o conflito 
<<<<<<< HEAD
    return "Olá da IDE";
=======
    return "Olá do site";
>>>>>>> origin/main
✅ Resultado esperado: as marcas <<<<<<< somem, o histórico (D-G1) mostra um commit de merge e o push volta a funcionar.

▶ 🖱️ Levar um projeto para o GitLab

  1. Crie a conta em gitlab.com/users/sign_up.
  2. New project → Create blank project → nome → desmarque Initialize repository with a README → Create project.
  3. A página do projeto vazio mostra os comandos de envio. No VS Code ou no IntelliJ, adicione esse endereço como remoto (VS Code: Source Control → … → Remote → Add Remote… · IntelliJ: Git → Manage Remotes… → +) e faça Push.

⑧ 🔁 CI/CD: o robô que testa cada push

🏭
Analogia da linha de produção: cada peça que chega passa por uma esteira com inspetores automáticos. Peça com defeito para a esteira na hora — antes de ir para o cliente. No código: a cada push ou PR, um robô compila e roda os testes; se algo quebrar, o PR fica vermelho e não entra.
PalavraEm uma frase
CI (Integração Contínua)A cada push/PR: compilar + testar, automaticamente.
CD (Entrega Contínua)Com tudo verde: empacotar (ex.: imagem Docker) e deixar pronto para publicar — ou publicar sozinho.
PipelineA sequência inteira, descrita num arquivo .yml dentro do repositório.
Stage / jobUma fase (build, test, deploy) / uma tarefa dentro dela.
RunnerA máquina que executa (o GitHub e o GitLab emprestam uma de graça, com limite).

📐 D-G3 Fluxo — Do push ao merge

O arquivo é parecido nos dois sites — muda o formato. Exemplo mínimo para um projeto .NET:

🐙 .github/workflows/ci.yml

.github/workflows/ci.yml 
name: ci
on: [push, pull_request]          # quando rodar
jobs:
  build-test:
    runs-on: ubuntu-latest        # o runner
    steps:
      - uses: actions/checkout@v4             # baixa o código
      - uses: actions/setup-dotnet@v4         # instala o .NET
        with: { dotnet-version: '10.0.x' }
      - run: dotnet build
      - run: dotnet test

🦊 .gitlab-ci.yml

.gitlab-ci.yml 
stages: [build, test]             # as fases, em ordem
build:
  stage: build
  image: mcr.microsoft.com/dotnet/sdk:10.0   # o "runner" é um container
  script: [ dotnet build ]
test:
  stage: test
  image: mcr.microsoft.com/dotnet/sdk:10.0
  script: [ dotnet test ]
  1. 🖱️ Coloque o arquivo no repositório e faça push.
  2. Veja rodar: GitHub → aba Actions · GitLab → Build → Pipelines.
  3. Abra um PR/MR: o resultado aparece nele (✔ verde ou ✖ vermelho).
📦 Os pipelines de verdade: cada projeto completo do guia traz os seus, prontos — Java na Tab 6, C# na Tab 7 e na Tab 9.

⚠️ ⑨ Erros comuns e o que fazer:
  • rejected … (fetch first) / push recusado → o site tem commits que você não tem: faça Pull primeiro, depois Push.
  • Need to specify how to reconcile divergent branches → você e o site têm commits diferentes e o Git quer saber como juntar: rode uma vez git config --global pull.rebase false e faça o Sync/Pull de novo.
  • O branch saiu master em vez de main → falta o init.defaultBranch main do passo ①.2. Para este projeto: VS Code → Ctrl+Shift+P → Git: Rename Branch; IntelliJ → menu do branch → Rename….
  • Please tell me who you are → falta o passo ①.2 (user.name e user.email).
  • Login falha no push (HTTPS) → senha da conta não funciona mais no Git: use o login pelo navegador da IDE ou um Personal Access Token; ou configure SSH.
  • src refspec main does not match any → ainda não há commit, ou o branch se chama master: faça um commit ou git branch -M main.
  • Enviei bin/, target/ ou .venv/ → acrescente ao .gitignore e rode git rm -r --cached bin obj + commit.
  • Enviei uma senha → troque a senha imediatamente. Apagar o arquivo não basta: ela continua no histórico.

🎯 Teste rápido: 6 perguntas

1. Git e GitHub são…

O Git é o programa que guarda o histórico; o GitHub é um site que guarda uma cópia dele e organiza o trabalho em equipe.

2. O que deve entrar no .gitignore de um projeto .NET?

São pastas geradas a cada build; o código e o .csproj são o que importa guardar.

3. O push foi recusado com fetch first. O que fazer?

O site tem commits que você não tem. Traga-os (pull), resolva se houver conflito e envie de novo.

4. No GitLab, o "Pull Request" se chama…

Mesmo fluxo, outro nome: MR.

5. Qual é a melhor mensagem de commit?

Diz o tipo (fix) e o que foi feito — quem lê o histórico entende sem abrir o código.

6. O que o CI faz a cada push?

Integração Contínua: build + testes automáticos; vermelho bloqueia o PR.
