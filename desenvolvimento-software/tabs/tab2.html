🌱 Spring Boot em 30 segundos

Spring Boot elimina a configuração manual do Spring: embute um servidor web (Tomcat), auto-configura dependências a partir do pom.xml e deixa você focar no código. Usamos a linha 4.1.x (estável atual).

🧵 Virtual Threads (Project Loom, Java 21)

  • Threads de SO ~1MB cada; virtuais ~1KB — milhões simultâneas.
  • Em I/O, a JVM desmonta a virtual thread e libera a thread de SO.

src/main/java/com/example/hello/controller/HelloController.java 
package com.example.hello.controller;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

import java.time.Instant;
import java.util.Map;

/**
 * Controller REST de demonstração (smoke test do ambiente).
 *
 * <p>{@code @RestController} = {@code @Controller} + {@code @ResponseBody}:
 * todo retorno é serializado como JSON automaticamente.</p>
 *
 * @since 1.0.0
 */
@RestController
public class HelloController {

    /**
     * GET /hello — responde um JSON com mensagem, thread e horário.
     *
     * @return mapa serializado como JSON pelo Spring
     */
    @GetMapping("/hello")
    public Map<String, Object> hello() {
        return Map.of(
            "mensagem", "Hello World com Spring Boot 4 + Java 21!",
            "thread", Thread.currentThread().toString(),
            "horarioUtc", Instant.now().toString()
        );
    }

    /**
     * GET / — healthcheck simples com roteiro de testes.
     *
     * @return mapa JSON com status e próximo endpoint a testar
     */
    @GetMapping("/")
    public Map<String, String> raiz() {
        return Map.of(
            "status", "API Spring Boot no ar",
            "roteiro", "GET /hello"
        );
    }
}

🔀 O que é Git? E GitHub vs GitLab?

Git é um sistema de controle de versão distribuído: registra o histórico de mudanças do código, permite branches (linhas paralelas), merge (junção) e rollback (voltar). Cada dev tem o repositório completo localmente.

  • Repositório (repo): o projeto + histórico.
  • Commit: um "snapshot" comentado das mudanças.
  • Branch: linha paralela (ex.: feat/x); main é a principal.
  • Remote / origin: a cópia no servidor (GitHub/GitLab).
  • push / pull: enviar / trazer mudanças do remote.
  • PR/MR (Pull/Merge Request): pedido de revisão p/ juntar um branch ao main.

GitHub vs GitLab

GitHubGitLab
HospedagemSaaS (Microsoft)SaaS ou self-hosted
RevisãoPull RequestMerge Request
CI/CDGitHub ActionsGitLab CI (integrado)

6🔀 Git + GitHub/GitLab: do clone ao Pull Request

🖥️ Abrir terminal: IntelliJ Alt+F12. Rode na pasta do projeto.
terminal - configuração + ciclo diário + PR 
# Identidade dos commits (quem aparece no log)
git config --global user.name "Seu Nome"
git config --global user.email "seu@email.com"
# SSH (recomendado): gera chave e cole a pública no site
ssh-keygen -t ed25519 -C "seu@email.com"
cat ~/.ssh/id_ed25519.pub   # copie o conteúdo e cole no GitHub/GitLab
# Ciclo diário: veja mudanças, revise, commit, sincronize
git status && git diff
git add . && git commit -m "feat: adiciona endpoint /hello"
git pull origin main && git push -u origin main
# Branch + PR/MR
git switch -c feat/novo-endpoint   # cria e troca de branch
git push -u origin feat/novo-endpoint   # publica o branch p/ abrir PR

🎯 Por que usar SDKMAN? (o sentido disso)

⚠️ Onde o SDKMAN roda: ele é uma ferramenta de shell POSIX — funciona em Linux, macOS e Windows via WSL/Cygwin/MSYS. Em CMD/PowerShell nativo do Windows ele NÃO funciona. No Windows nativo, use WSL (recomendado) ou instale o JDK manualmente / via winget.

Problema: um dev tem Java 17, outro 21, o CI usa 25 — builds quebram "do nada".

SDKMAN resolve: várias JDKs lado a lado; .sdkmanrc commitado declara a versão por projeto e sdk env troca sozinho.

🧰
Analogia: caixa de ferramentas com gavetas etiquetadas — o .sdkmanrc é o bilhete na ordem de serviço dizendo qual gaveta usar.
terminal - SDKMAN do zero (Linux/macOS/WSL) 
# Instala o SDKMAN (script oficial)
curl -s "https://get.sdkman.io" | bash
# Carrega o SDKMAN no shell atual
source "$HOME/.sdkman/bin/sdkman-init.sh"
# Lista JDKs disponíveis ("tem" = Eclipse Temurin, recomendado)
sdk list java | grep tem
# Instala o JDK 21 LTS e define como padrão da máquina
sdk install java 21.0.4-tem && sdk default java 21.0.4-tem
# Dentro de um projeto com .sdkmanrc: aplica a versão declarada
sdk env
# Valida
java -version
🎯 Seletor de Versão do JDK:
.sdkmanrc (commitado na raiz) 
# .sdkmanrc
java=21.0.4-tem
