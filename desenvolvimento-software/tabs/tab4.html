🌐 O que é curl (e por que usamos tanto)?

curl (client URL) é um cliente HTTP de linha de comando: você envia requisições (GET/POST/PUT/DELETE) e vê a resposta crua (status, headers, body). É a forma mais direta de testar uma API sem IDE.

FlagO que fazExemplo
-iMostra headers + bodycurl -i url
-XDefine o métodocurl -X POST url
-HAdiciona header-H "Authorization: Bearer $TOKEN"
-dBody da requisição-d '{"nome":"x"}'
-sSilencioso (sem barra de progresso)curl -s url
-oSalva a resposta em arquivocurl -o out.json url

Aprofundar: curl.se/docs.

🔑 JWT a fundo: o que é, por que e como funciona

JWT (JSON Web Token, RFC 7519) é um token auto-contido e assinado: ele carrega as claims (quem é você) dentro dele mesmo. Por isso o servidor não guarda sessão — só verifica a assinatura. É isso que dá escala horizontal (stateless).

Anatomia: header.payload.signature

  • header: algoritmo (HS256) e tipo (JWT), em base64url.
  • payload: as claims — sub (usuário), role, exp (expiração), iat (emissão) — em base64url. Atenção: base64 ≠ criptografia: qualquer um consegue ler; por isso nunca coloque dado sensível no payload.
  • signature: HMAC-SHA256(header.payload, secret). Qualquer alteração de 1 caractere invalida o token.

Por que o login é público e o resto não?

O POST /api/auth/login é o único endpoint que não pode exigir token — é ele que o emite. Por isso o contrato traz security: [] nele. Todos os demais exigem Authorization: Bearer <token>.

Fluxo em 4 passos

  1. Cliente envia credenciais ao login.
  2. Servidor valida e emite o JWT assinado com o secret.
  3. Cliente guarda o token e o envia em cada request seguinte.
  4. Servidor verifica assinatura + expiração e autoriza (ou 401).

Aprofundar: RFC 7519 (JWT) · jwt.io (debugger interativo) · OWASP JWT Cheat Sheet.

⚠️ Erros comuns: token expirado (exp); secret errado/trocado; esquecer o prefixo Bearer ; achar que base64 criptografa (não criptografa!). Onde guardar o secret: variável de ambiente / secret manager — nunca commitado.

📑 ADRs desta aba (padrão AWS: Contexto·Decisão·Alternativas·Consequências·Status·Stakeholders)


ADR-001 · Contrato OpenAPI como fonte únicaAceita


Contexto: frontend/mobile bloqueados aguardando backend.


Decisão: contrato OpenAPI 3.1 primeiro + mock Prism; negociado na Sala de Contrato.


Alternativas consideradas: code-first (rejeitada); GraphQL (fora de escopo).


Consequências: (+) desenvolvimento paralelo; (−) cerimônia inicial de desenho.


Status: Aceita · Stakeholders: Backend, Frontend, QA, Produto.


ADR-005 · JWT statelessAceita


Contexto: autenticação sem sessão em servidor.


Decisão: Bearer JWT HMAC-SHA256; erros em RFC 7807.


Alternativas consideradas: sessão em servidor/cookie (rejeitada); OAuth2 completo (adiado).


Consequências: (+) stateless, escala horizontal; (−) revogação exige blacklist/refresh.


Status: Aceita · Stakeholders: Backend, SRE, Segurança.


ADR-007 · Mock Prism em validação estrita (-m false)Aceita


Contexto: mock dinâmico mascarava erros de contrato.


Decisão: Prism com -m false valida o body contra o schema e retorna 400 quando não bate.


Alternativas consideradas: mock dinâmico default (rejeitada); mock manual (rejeitada).


Consequências: (+) QA pega erros de contrato cedo; (−) mock menos "mágico".


Status: Aceita · Stakeholders: QA, Backend, Frontend.


ADR-008 · Erros no padrão RFC 7807 (application/problem+json)Aceita


Contexto: erros ad-hoc dificultavam tratamento no cliente.


Decisão: todos os erros usam Problem Details (type/title/status/detail).


Alternativas consideradas: envelope custom {erro} (rejeitada); HTML error pages (rejeitada).


Consequências: (+) clientes parseiam erros de forma uniforme; (−) exige disciplina de emitir Problem Details.


Status: Aceita · Stakeholders: Backend, Frontend, QA.







🐳 Prism via compose dedicado


✅ Separação: Prism tem compose próprio, independente dos bancos (Tab 5). -m false desabilita o mock dinâmico: o Prism valida estritamente o contrato, retornando 400 quando o body não bate com o schema.


🖥️ Abrir terminal: IntelliJ Alt+F12 · VS Code Ctrl+`. Na pasta do docker-compose.prism.yml.



docker-compose.prism.yml


# Compose dedicado ao Mock Server (Stoplight Prism)
services:
  prism-mock:
    image: stoplight/prism:5            # imagem oficial do Prism
    container_name: dev_prism_mock      # nome fixo p/ logs/exec
    restart: unless-stopped             # reinicia sozinho se cair
    command: mock -h 0.0.0.0 -m false -d /tmp/openapi.yaml   # -m false = valida estritamente
    volumes:
      - ./contracts/openapi.yaml:/tmp/openapi.yaml:ro  # monta o contrato (somente leitura)
    ports:
      - "4010:4010"                     # expõe a porta do mock no host





terminal da IDE - comandos comentados


# Sobe o mock em background (-d = detached; o terminal fica livre)
docker compose -f docker-compose.prism.yml up -d
# Lista os containers deste compose (coluna STATUS deve mostrar "Up")
docker compose -f docker-compose.prism.yml ps
# Acompanha os logs em tempo real (Ctrl+C para sair do follow)
docker compose -f docker-compose.prism.yml logs -f prism-mock
# Editou o openapi.yaml? O Prism lê o contrato no boot → reinicie p/ reler:
docker compose -f docker-compose.prism.yml restart
# Derruba apenas o mock (não afeta outros composes)
docker compose -f docker-compose.prism.yml down

B Teste AUTENTICADO — login + CRUD completo


Como fazer funcionar: login primeiro → extrai token → usa em todas as requests seguintes.


🖥️ Terminal: IntelliJ Alt+F12 · VS Code Ctrl+`.



terminal da IDE - teste autenticado completo


# ── PASSO 1: Login (extrai token) ──
TOKEN=$(curl -s -X POST http://localhost:4010/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"dev@loja.com.br","senha":"SenhaForte#2026"}' \
  | jq -r '.tokenAcesso')
echo "Token: $TOKEN"
# ── PASSO 2: GET (listar) ── esperado 200
curl -i http://localhost:4010/api/produtos -H "Authorization: Bearer $TOKEN"
# ── PASSO 3: POST (criar) ── esperado 201
curl -i -X POST http://localhost:4010/api/produtos \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"nome":"Monitor Ultrawide 34","preco":2499.90,"estoque":8}'
# ── PASSO 4: PUT (atualizar) ── esperado 200
curl -i -X PUT http://localhost:4010/api/produtos/101 \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"nome":"Monitor Ultrawide 34 4K","preco":2999.90,"estoque":12}'
# ── PASSO 5: DELETE (excluir) ── esperado 204
curl -i -X DELETE http://localhost:4010/api/produtos/101 \
  -H "Authorization: Bearer $TOKEN"




✅ Resultado esperado: POST → 201 · PUT → 200 · DELETE → 204, todos com Authorization: Bearer $TOKEN.
