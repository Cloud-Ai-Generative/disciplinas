📜 API-First: combinar o contrato antes de programar (OpenAPI + Prism + JWT)

Antes de escrever uma linha de Java ou C#, o time combina por escrito como a API vai funcionar: quais endereços existem, o que cada um recebe e o que devolve. Esse acordo é o contrato (um arquivo openapi.yaml). Com ele pronto, um programa chamado Prism finge ser a API em segundos — e o frontend já pode trabalhar enquanto o backend é construído.

🗺️ O caminho desta aba: ① entender a ideia → ② negociar o contrato na Sala (interativo) → ③ ler o contrato linha a linha → ④ ligar o mock no Docker Desktop → ⑤ testar com o VS Code → ⑥ entender o login com JWT → ⑦ as decisões registradas (ADRs). Tempo total: ~1h30.
🧭 Como ler esta aba: os passos com 🖱️ são feitos com o mouse. Os blocos ⌨️ Prefere o terminal? mostram o mesmo passo por comandos — são opcionais. Pré-requisitos: Docker Desktop instalado (Tab 5) e VS Code (Tab 3).

① 📐 O que é API-First (e por que começar pelo contrato)

🏢
Analogia da planta da casa: ninguém começa uma obra assentando tijolo. Primeiro se aprova a planta. Com ela em mãos, o eletricista, o encanador e o marceneiro trabalham ao mesmo tempo, cada um na sua parte, e tudo se encaixa no final. Na API, a planta é o openapi.yaml: o backend constrói a API, o frontend constrói as telas e o QA prepara os testes — todos olhando para o mesmo papel.
  1. Reunião: negócio, backend, frontend e QA desenham o contrato juntos (é o que você vai fazer na Sala, logo abaixo).
  2. Contrato: o resultado vira o arquivo openapi.yaml — a fonte única da verdade.
  3. Mock: o Prism lê o arquivo e vira uma API de mentirinha na porta 4010.
  4. Em paralelo: o frontend usa o mock; o backend implementa a API de verdade (Tabs 6 e 7).
  5. Conferência: no fim, a API real é testada contra o mesmo contrato.

📖 Quatro palavras que você vai ver o tempo todo

PalavraO que é, em uma frase
Contrato (OpenAPI)Um arquivo de texto (.yaml) que descreve cada endereço da API, o que ele recebe e o que devolve.
MockUma API "de mentirinha" que responde com os exemplos do contrato. Não tem banco de dados.
PrismO programa que transforma o contrato em mock. Roda dentro do Docker.
Token (JWT)Um "crachá" que você recebe ao fazer login e mostra em cada pedido que exige estar logado.

③ 📜 Ler o contrato: contracts/openapi.yaml

🛠️ Abrir no Swagger Editor ↗

Este é o contrato que sai da Sala (ou o padrão, se você não jogou). Não precisa decorar: leia com calma usando o quadro logo abaixo. Repare em três coisas:

  • Leitura é pública: os dois get têm security: [] — qualquer um pode listar e ver produtos.
  • Escrita exige login: post, put e delete têm bearerAuth e preveem a resposta '401'.
  • O cliente não manda id: o ProdutoRequest (o que se envia) só tem nome, preco e estoque; o id é criado pelo servidor e aparece no ProdutoResponse (o que volta).

🔎 O que significa CADA palavra do contrato (quadro linha a linha)






Linha / palavraSignificado



openapi: 3.1.0Versão da especificação OpenAPI usada no arquivo.


info:Nome, versão e descrição da API.


servers:Onde a API roda: mock (4010) e backend real (8080).


security: (no topo)A regra geral: exige o token bearerAuth.


security: [] (numa rota)Exceção: esta rota não exige token (login e leituras).


paths:A lista de endereços (rotas). Cada chave é um caminho, como /api/produtos.


get / post / put / delete:Os verbos HTTP: ler, criar, atualizar, excluir.


summary: · tags:Descrição curta e agrupamento (aparecem no Swagger UI).


parameters:Valores na URL: no caminho ({id}) ou depois do ? (page, size).


requestBody:O JSON que o cliente envia.


responses:O que pode voltar: 200 ok, 201 criado, 204 excluído, 400 dados inválidos, 401 sem login, 404 não existe.


application/problem+jsonFormato padrão de erro (RFC 7807): type, title, status, detail.


components:Peças reutilizáveis: schemas, responses e securitySchemes.


$ref:"Use a peça tal": aponta para algo em components, para não repetir.


required:Campos obrigatórios.


type / formatTipo do campo: integer + int64 (número inteiro grande), number, string.


minimum / minLength / maxLengthRegras: valor mínimo, tamanho mínimo e máximo. O Prism recusa com 400 o que não obedecer.


additionalProperties: falseCampo que não está no contrato (como um id no POST) é recusado.


example:Valor de exemplo. É exatamente o que o mock devolve.






💰 Por que o preço é number e não double? Em JSON todo número é "number". O que importa é onde ele fica guardado: no banco, DECIMAL(10,2) (Tab 5), e no código, BigDecimal (Java) ou decimal (C#) — nunca float/double, que arredondam centavos. Se o time quiser zero risco também no caminho, a Sala oferece a opção string decimal.

docker-compose.prism.yml


# ─────────────────────────────────────────────────────────────
#  Mock Server da API (Stoplight Prism) — compose só dele,
#  separado dos bancos da Tab 5. Fica na RAIZ da pasta loja-contrato,
#  ao lado da pasta contracts/.
# ─────────────────────────────────────────────────────────────
services:
  prism-mock:
    image: stoplight/prism:5          # imagem oficial do Prism (versão 5)
    container_name: dev_prism_mock    # nome fixo: é assim que aparece no Docker Desktop
    restart: unless-stopped           # se cair, o Docker sobe de novo
    # mock         → finge ser a API, lendo o contrato
    # -h 0.0.0.0   → aceita conexões de fora do container (do seu PC)
    # --errors     → qualquer violação do contrato vira resposta de erro
    # Sem -d: as respostas usam os "example:" do contrato (sempre os mesmos
    # valores — bom para testar). Com -d o Prism inventaria dados aleatórios.
    command: mock -h 0.0.0.0 --errors /tmp/openapi.yaml
    volumes:
      - ./contracts/openapi.yaml:/tmp/openapi.yaml:ro   # o contrato entra no container (só leitura)
    ports:
      - "4010:4010"                   # http://localhost:4010 no seu PC → porta 4010 do Prism




✅ Resultado esperado: no Explorer do VS Code aparecem contracts/openapi.yaml e docker-compose.prism.yml, um ao lado do outro.

🔧 O que significa a linha command? mock = finja ser a API · -h 0.0.0.0 = aceite conexões vindas do seu PC · --errors = trate qualquer violação do contrato como erro. Deixamos de fora o -d (dynamic), que inventaria dados aleatórios a cada resposta — com dados fixos, todo mundo vê o mesmo resultado.

⑤ 🧪 Testar o mock com o VS Code (REST Client)






0 🖱️ Ainda sem Docker? Treine no simulador


Este simulador roda aqui na página e confere o seu pedido contra o seu contrato (o da Sala), com as mesmas regras do Prism: rota que não existe → 404, verbo errado → 405, sem token → 401, corpo fora das regras → 400. Escolha um exemplo ou monte o seu pedido e clique em Enviar.















Simulador do Prism (no navegador)






💡 O simulador não substitui o Prism: ele serve para treinar e para quem ainda não instalou o Docker. O teste de verdade é o dos passos abaixo — é assim que o frontend vai usar o mock no dia a dia.




⚠️ O mock é de mentirinha — saiba o que ele NÃO faz: (1) aceita qualquer token: ele só confere se o header Authorization: Bearer … existe, não se o token é verdadeiro; (2) não guarda nada: depois do POST, o GET continua devolvendo o mesmo exemplo; (3) nunca devolve 404 sozinho, porque não tem banco — por isso o teste 9 pede o 404 com o header Prefer: code=404. Login de verdade e dados de verdade só no backend real (Tabs 6 e 7).

### 2) Criar SEM token → esperado 401 (teste negativo de propósito: escrever exige login)

Content-Type: application/json

Content-Type: application/json

GET {{host}}/api/produtos/101

### 7) Atualizar → esperado 200
PUT {{host}}/api/produtos/101
Authorization: Bearer {{token}}
Content-Type: application/json

⌨️ Prefere o terminal? Os mesmos testes com curl (Git Bash/macOS/Linux e PowerShell)




curl é um programa de linha de comando que faz pedidos HTTP e mostra a resposta crua. Vem instalado no Windows 10/11, no macOS e no Linux.




OpçãoO que faz



-iMostra os headers da resposta junto com o corpo.


-X POSTEscolhe o verbo (o padrão é GET).


-H "…"Adiciona um header, como Authorization: Bearer ….


-d '…' · --data-binary @arq.jsonManda um corpo (texto ou arquivo).


-s -o /dev/null -w "%{http_code}"Silencioso, descarta o corpo e imprime só o status.




Git Bash (Windows), macOS ou Linux — salve em scripts/testar-mock.sh e rode bash scripts/testar-mock.sh na pasta loja-contrato. Não precisa instalar o jq.



scripts/testar-mock.sh


#!/usr/bin/env bash
# Testes do mock por terminal — Git Bash (Windows), macOS ou Linux.
# Rode na pasta loja-contrato:   bash scripts/testar-mock.sh
# Não precisa de jq: o token é recortado com sed.
H=http://localhost:4010

echo "== 1) GET sem token (esperado 200)"
curl -s -o /dev/null -w "%{http_code}\n" "$H/api/produtos?page=0&size=20"

echo "== 2) POST sem token (esperado 401)"
curl -s -o /dev/null -w "%{http_code}\n" -X POST "$H/api/produtos" \
  -H "Content-Type: application/json" \
  -d '{"nome":"Monitor Ultrawide 34","preco":2499.90,"estoque":8}'

echo "== 3) Login (esperado: um token)"
TOKEN=$(curl -s -X POST "$H/api/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"email":"dev@loja.com.br","senha":"SenhaForte#2026"}' \
  | sed -E 's/.*"tokenAcesso" *: *"([^"]+)".*/\1/')
echo "token: ${TOKEN:0:25}..."

echo "== 4) POST com token (esperado 201)"
curl -s -o /dev/null -w "%{http_code}\n" -X POST "$H/api/produtos" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"nome":"Monitor Ultrawide 34","preco":2499.90,"estoque":8}'

echo "== 5) POST inválido (esperado 400)"
curl -s -o /dev/null -w "%{http_code}\n" -X POST "$H/api/produtos" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"nome":"X","preco":-5,"estoque":8}'

echo "== 6) PUT (esperado 200)"
curl -s -o /dev/null -w "%{http_code}\n" -X PUT "$H/api/produtos/101" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"nome":"Monitor Ultrawide 34 4K","preco":2999.90,"estoque":12}'

echo "== 7) DELETE (esperado 204)"
curl -s -o /dev/null -w "%{http_code}\n" -X DELETE "$H/api/produtos/101" \
  -H "Authorization: Bearer $TOKEN"

echo "== 8) 404 forçado (esperado 404)"
curl -s -o /dev/null -w "%{http_code}\n" "$H/api/produtos/999" -H "Prefer: code=404"




PowerShell do Windows — salve em scripts/testar-mock.ps1 e rode powershell -ExecutionPolicy Bypass -File scripts\testar-mock.ps1. Usamos curl.exe (no PowerShell 5.1, curl sozinho é outro comando) e o login com Invoke-RestMethod.



scripts/testar-mock.ps1


# Testes do mock no PowerShell do Windows (funciona no 5.1 e no 7).
# Rode na pasta loja-contrato:   powershell -ExecutionPolicy Bypass -File scripts\testar-mock.ps1
# Usamos curl.exe (o "curl" puro do PowerShell 5.1 é outro comando!) e mandamos
# os corpos JSON por arquivo, para fugir das regras de aspas do PowerShell.
$H = "http://localhost:4010"
'{"nome":"Monitor Ultrawide 34","preco":2499.90,"estoque":8}'      | Set-Content -Encoding ascii novo.json
'{"nome":"X","preco":-5,"estoque":8}'                               | Set-Content -Encoding ascii invalido.json
'{"nome":"Monitor Ultrawide 34 4K","preco":2999.90,"estoque":12}'  | Set-Content -Encoding ascii editado.json

function Status($rotulo, $args2) {
  $code = & curl.exe -s -o NUL -w "%{http_code}" @args2
  Write-Host "$rotulo -> $code"
}

Status "1) GET sem token      (esperado 200)" @("$H/api/produtos?page=0&size=20")
Status "2) POST sem token     (esperado 401)" @("-X","POST","$H/api/produtos","-H","Content-Type: application/json","--data-binary","@novo.json")

# 3) Login: Invoke-RestMethod já devolve o JSON como objeto
$login = Invoke-RestMethod -Method Post -Uri "$H/api/auth/login" -ContentType "application/json" `
         -Body '{"email":"dev@loja.com.br","senha":"SenhaForte#2026"}'
$TOKEN = $login.tokenAcesso
Write-Host "3) Login -> token: $($TOKEN.Substring(0,25))..."
$auth = "Authorization: Bearer $TOKEN"

Status "4) POST com token     (esperado 201)" @("-X","POST","$H/api/produtos","-H",$auth,"-H","Content-Type: application/json","--data-binary","@novo.json")
Status "5) POST inválido      (esperado 400)" @("-X","POST","$H/api/produtos","-H",$auth,"-H","Content-Type: application/json","--data-binary","@invalido.json")
Status "6) PUT                (esperado 200)" @("-X","PUT","$H/api/produtos/101","-H",$auth,"-H","Content-Type: application/json","--data-binary","@editado.json")
Status "7) DELETE             (esperado 204)" @("-X","DELETE","$H/api/produtos/101","-H",$auth)
Status "8) 404 forçado        (esperado 404)" @("$H/api/produtos/999","-H","Prefer: code=404")

Remove-Item novo.json, invalido.json, editado.json




✅ Resultado esperado (nos dois): 200, 401, um token, 201, 400, 200, 204, 404 — um por linha, nessa ordem.

🧩 D1 · Preço negativo — "preco": -5 → qual status volta?


Resposta: 400 Bad Request. O contrato diz minimum: 0.01. O Prism confere o corpo contra o schema e recusa. Na API real, essa mesma regra protege o banco de um produto "de graça".


🧩 D2 · Nome com 1 letra — "nome": "M" → qual status volta?


Resposta: 400 Bad Request. minLength: 2. Regras de tamanho no contrato evitam que cada time (front, back, QA) invente a sua.


🧩 D3 · Estoque 2.5 — "estoque": 2.5 → qual status volta?


Resposta: 400 Bad Request. type: integer: número com vírgula não é inteiro. O tipo também é uma regra.


🧩 D4 · O cliente manda o id — "id": 7 no POST → qual status volta?


Resposta: 400 Bad Request. additionalProperties: false no ProdutoRequest: campo que não está no contrato é recusado. Quem cria o id é o servidor.


🧩 D5 · Sem a palavra Bearer — Authorization: qualquer-coisa → qual status volta?


Resposta: 401 Unauthorized. O esquema é bearer: o header precisa começar com Bearer  (com espaço). Sem isso, para o Prism é como se não houvesse token.


🧩 D6 · Rota no singular — GET /api/produto → qual status volta?


Resposta: 404 Not Found. Essa rota não existe no contrato (é /api/produtos, no plural). O Prism responde 404 com NO_PATH_MATCHED_ERROR.


🧩 D7 · Verbo que não existe — PATCH /api/produtos/101 → qual status volta?


Resposta: 405 Method Not Allowed. A rota existe, mas o contrato só tem get, put e delete nela. 405 = "o endereço está certo, o verbo não".


🧩 D8 · Id que não é número — GET /api/produtos/abc → qual status volta?


Resposta: 422 Unprocessable Entity. O id é integer. Por que 422 e não 400? Essa rota não prevê resposta 400 no contrato, então o Prism usa o erro padrão dele (422). Lição: o contrato também decide quais erros existem — um bom contrato prevê o 400 aqui.

⑥ 🔑 Como funciona o login com JWT



🎫

Analogia da pulseira do show: na entrada você mostra o ingresso uma vez (o login) e ganha uma pulseira (o token). Daí em diante, cada segurança só olha a pulseira — ninguém precisa consultar a lista de convidados de novo. A pulseira tem validade (exp) e é difícil de falsificar (a assinatura).




JWT (JSON Web Token, RFC 7519) é um texto em três partes separadas por ponto: header.payload.signature.


    

  • header: qual algoritmo assinou (ex.: HS256).
    • 

  • payload: os dados do usuário — sub (quem é), exp (quando vence), iat (quando foi emitido). Atenção: isso é só base64, qualquer um consegue ler. Nunca coloque senha ou dado sensível ali.
    • 

  • signature: um "lacre" calculado com uma chave secreta do servidor. Mudou 1 letra do token, o lacre não confere → 401.
    • 



Neste guia o contrato só pergunta "está logado?" — não existem perfis (admin, cliente…). Logado pode escrever; não logado só lê. Perfis e permissões ficam para depois.


O caminho em 4 passos


    

  1. O cliente manda e-mail e senha para POST /api/auth/login — a única rota de escrita sem token (é ela que entrega o token).
    2. 

  2. O servidor confere e devolve o JWT assinado.
    3. 

  3. O cliente guarda o token e o envia em cada pedido de escrita: Authorization: Bearer <token>.
    4. 

  4. O servidor confere assinatura e validade: tudo certo → segue; senão → 401.
    5. 



🔬 Na prática: abra um token e quebre o lacre




    

  1. Clique em 🎫 Gerar token de aula (ou cole no campo um tokenAcesso qualquer — inclusive o que o mock devolveu).
    2. 

  2. Veja as 3 partes coloridas e o que está escrito no payload. Repare: qualquer um lê, sem senha nenhuma.
    3. 

  3. Agora clique em ✏️ Virar admin: o payload é alterado, mas a assinatura continua a antiga → ❌ assinatura não confere. É exatamente o que o servidor faz para recusar um token falsificado (→ 401).
    4. 











—


O token de aula é assinado aqui mesmo, no seu navegador, com a chave secreta de mentira segredo-da-aula-tab4. Nada sai do seu computador.




⚠️ Erros comuns: esquecer a palavra Bearer  (com espaço) antes do token; token vencido (exp); chave secreta diferente entre quem emite e quem confere; achar que base64 esconde os dados (não esconde!). A chave secreta fica em variável de ambiente — nunca no Git.

⑦ 📑 Decisões registradas (ADRs)


ADR = Architecture Decision Record: um registro curto de cada decisão importante — o problema, o que foi decidido, as alternativas e o preço da escolha. Assim, quem chega depois entende o "porquê". 🎬 O que é ADR (YouTube)


ADR-001 · Contrato OpenAPI como fonte únicaAceita


Contexto: frontend e mobile ficavam parados esperando o backend.


Decisão: o contrato OpenAPI 3.1 vem primeiro, negociado na Sala de Contrato, e vira mock no Prism.


Alternativas consideradas: escrever o código primeiro e gerar o contrato depois (rejeitada); GraphQL (fora do escopo).


Consequências: (+) times trabalham em paralelo; (−) exige uma reunião de desenho no início.


Status: Aceita · Stakeholders: Backend, Frontend, QA, Produto.


ADR-005 · JWT stateless, só autenticaçãoAceita


Contexto: a API precisa saber se quem escreve está logado, sem guardar sessão no servidor.


Decisão: token Bearer JWT assinado (HMAC-SHA256). Leitura pública; criar, atualizar e excluir exigem login. Sem perfis/roles nesta etapa.


Alternativas consideradas: sessão no servidor com cookie (rejeitada); perfis de acesso desde já (adiado); OAuth2 completo (adiado).


Consequências: (+) qualquer servidor confere o token, escala fácil; (−) revogar um token antes de vencer exige lista de bloqueio ou refresh token.


Status: Aceita · Stakeholders: Backend, SRE, Segurança.


ADR-007 · Mock Prism com exemplos fixos e validação de pedidosAceita


Contexto: com dados aleatórios (-d), cada pessoa via respostas diferentes e erros de contrato passavam despercebidos.


Decisão: Prism sem -d (devolve os example: do contrato) e com --errors. Pedidos fora do contrato voltam como erro: 401 sem token, 400 para JSON inválido.


Alternativas consideradas: mock com dados aleatórios (rejeitada); mock escrito à mão (rejeitada: sai do contrato).


Consequências: (+) resultados previsíveis para o QA e para a aula; (−) o mock não valida o token de verdade nem guarda dados.


Status: Aceita · Stakeholders: QA, Backend, Frontend.


ADR-008 · Erros no padrão RFC 7807 (application/problem+json)Aceita


Contexto: cada erro vinha num formato diferente, e o cliente não sabia ler.


Decisão: todo erro usa Problem Details (type, title, status, detail), definido uma vez em components/responses.


Alternativas consideradas: formato próprio {erro} (rejeitada, mas a Sala deixa experimentar); páginas de erro em HTML (rejeitada).


Consequências: (+) o cliente trata todos os erros do mesmo jeito; (−) o backend precisa disciplina para sempre responder nesse formato.


Status: Aceita · Stakeholders: Backend, Frontend, QA.





🎯 Teste rápido: 6 perguntas


Clique na resposta. Verde = certo; vermelho = tente entender a explicação antes de seguir.


1. Um POST em /api/produtos sem o header Authorization devolve:
    
Escrever exige login (bearerAuth). Sem token → 401.


2. Por que o ProdutoRequest não tem o campo id?
    
Quem cria o id é o servidor; o cliente só envia nome, preço e estoque.


3. O Prism, sem a opção -d, responde com:
    
Sem -d ele usa os exemplos — o mesmo resultado para todo mundo.


4. Depois de um POST que deu 201 no mock, um GET mostra o produto novo?
    
O mock não tem banco: devolve sempre o exemplo. Guardar é trabalho do backend real.


5. Qual parte do JWT impede que alguém altere o token?
    
A assinatura é calculada com a chave secreta; mudou o payload, ela não confere.


6. PATCH /api/produtos/101, num contrato que só tem get/put/delete nessa rota, devolve:
    
O endereço existe, o verbo não → 405 Method Not Allowed.






⚠️ Problemas comuns e o que fazer:

    

  • Container sobe e cai (bolinha vermelha) → Logs do Docker Desktop. Quase sempre é o contrato: nome errado (openapi.yaml.txt) ou arquivo fora da pasta contracts.
    • 

  • port is already allocated → outro programa usa a 4010. Troque para "4011:4010" no compose e use http://localhost:4011.
    • 

  • 404 em qualquer rota → caminho digitado errado (é /api/produtos, no plural).
    • 

  • Editei o contrato e nada mudou → o Prism só lê o arquivo ao ligar: Docker Desktop → ⟳ Restart no container.
    • 

  • 422 em vez de 400 → seu contrato não tem a resposta '400' naquela rota; o Prism usa o 422 dele. Gere de novo pela Sala.
    • 

  • PowerShell: erro com aspas no JSON → use o testar-mock.ps1 (corpo por arquivo) ou o REST Client.
