💥 O dual-write impossível

Você precisa de duas coisas ao criar um pedido: gravar no banco e avisar os outros. O jeito óbvio é fazer as duas em sequência. O problema é que não existe ordem correta:

OrdemSe o 1º falhaSe o 2º falhaConsequência
salvar() → publicar()nada acontece (ok)pedido existe, ninguém sabeEstoque nunca baixa. O cliente pagou e nada se move.
publicar() → salvar()nada acontece (ok)estoque baixou de um pedido que não existePior: dado fantasma, impossível de rastrear.

MySQL e RabbitMQ são dois sistemas sem transação em comum. Commit em dois passos (2PC/XA) existe, mas é lento, frágil e praticamente ninguém usa em microsserviços. A saída não é "acertar a ordem": é não precisar dos dois ao mesmo tempo.

📮
A analogia da caixa de correio. Você não entrega a carta na casa do destinatário e, na volta, anota no caderno que entregou. Você escreve a carta e põe na sua própria caixa de saída — um ato só, na sua casa. O carteiro passa depois e leva. Se o carteiro atrasar, a carta continua lá. Isso é o Outbox: o evento é gravado no seu banco, no seu commit, e um processo separado o entrega depois.

📐 D-20 Fluxo — Ingênuo vs. Outbox (onde cada um quebra)

⚖️ O trade-off que você está aceitando (diga isso em voz alta)

Outbox não é grátis. Você troca três coisas:

❌ Perde: sincronia

O efeito não acontece junto com o 201. O estoque baixa ~0,5s depois. A API precisa dizer isso ao cliente (status AguardandoEstoque).

❌ Perde: entrega única

A entrega é at-least-once: a mensagem pode chegar 2×. Resolve-se com idempotência no consumidor (Inbox) — e é por isso que a Parte 3 existe.

✅ Ganha: nada se perde

O evento está no seu banco, no seu commit. Broker fora, worker fora, processo morto no meio — o evento sai quando tudo voltar.

A regra: entre "pode duplicar" e "pode perder", escolha pode duplicar. Duplicação se resolve com código (uma tabela e uma chave única). Perda não se resolve com nada — o dado simplesmente não existe mais.

2O domínio: Pedido como Aggregate Root

Mesmo DDD da Tab 7, com uma decisão nova que muda tudo: o id do pedido é um GUID gerado no domínio, não um AUTO_INCREMENT do MySQL.

Por quê? Na Tab 7 o evento era criado dentro de Produto.Criar(), antes de o banco gerar o id — e saía sempre com Id = 0. Com GUID, a entidade já nasce identificada: o evento sai correto, o cliente recebe o id antes do commit e o consumidor tem uma chave estável. O custo (GUID aleatório fragmenta índice) é pago com CHAR(36) e ordenação por criado_em, nunca por id.

LojaEventos.Domain/ValueObjects/Dinheiro.cs 
namespace LojaEventos.Domain.ValueObjects;

// ════════════════════════════════════════════════════════════════════════════
//  VALUE OBJECT (DDD) — igual ao da Tab 7. Mantido para a arquitetura não mudar.
//  "Value Object" = objeto SEM identidade própria. R$ 10,00 é R$ 10,00: não faz
//  sentido perguntar "qual é o id deste dinheiro?". Por isso:
//    • é 'record'  -> imutável + Equals/GetHashCode por VALOR (de graça);
//    • é 'sealed'  -> ninguém herda e quebra a igualdade por valor.
// ════════════════════════════════════════════════════════════════════════════
public sealed record Dinheiro(decimal Valor, string Moeda = "BRL")
{
    // Fábrica com guarda. Preferimos isto ao construtor cru porque o construtor
    // posicional de um record NÃO valida nada — ele só atribui.
    public static Dinheiro De(decimal valor, string moeda = "BRL")
    {
        if (valor < 0) throw new ArgumentOutOfRangeException(nameof(valor), "Dinheiro não pode ser negativo");
        return new Dinheiro(decimal.Round(valor, 2, MidpointRounding.ToEven), moeda);
    }

    public static readonly Dinheiro Zero = new(0m);

    public Dinheiro Somar(Dinheiro outro)
    {
        // Invariante de domínio: não se soma BRL com USD sem câmbio.
        if (Moeda != outro.Moeda)
            throw new InvalidOperationException($"Moedas diferentes: {Moeda} e {outro.Moeda}");
        return new Dinheiro(Valor + outro.Valor, Moeda);
    }

    public Dinheiro Multiplicar(int quantidade) => new(Valor * quantidade, Moeda);

    public override string ToString() => $"{Moeda} {Valor:N2}";
}

//  é buscado isoladamente, e seu ciclo de vida é o do Pedido. Por isso o
//  construtor é 'internal' — só o Pedido (mesmo assembly) pode criar itens.
//  É assim que o agregado protege suas invariantes: ninguém monta um item
//  inválido pelas costas da raiz.
// ════════════════════════════════════════════════════════════════════════════
public class ItemPedido
{
    public long Id { get; private set; }              // id técnico (EF)
    public Guid PedidoId { get; private set; }        // FK para a raiz
    public long ProdutoId { get; private set; }
    public string NomeProduto { get; private set; } = string.Empty;
    public int Quantidade { get; private set; }
    public Dinheiro PrecoUnitario { get; private set; } = Dinheiro.Zero;

    /// <summary>Total da linha. Calculado, nunca persistido — evita dado divergente.</summary>
    public Dinheiro Subtotal => PrecoUnitario.Multiplicar(Quantidade);

    // EF Core precisa de um construtor sem parâmetros para materializar.
    // 'protected' em vez de 'public' para o domínio não oferecer um item vazio.
    protected ItemPedido() { }

    internal ItemPedido(long produtoId, string nomeProduto, int quantidade, Dinheiro precoUnitario)
    {
        if (produtoId <= 0) throw new DomainException("ProdutoId inválido");
        if (quantidade <= 0) throw new DomainException("Quantidade deve ser > 0");
        if (quantidade > 1000) throw new DomainException("Quantidade máxima por item: 1000");
        if (precoUnitario.Valor <= 0) throw new DomainException("Preço unitário deve ser > 0");
        if (string.IsNullOrWhiteSpace(nomeProduto)) throw new DomainException("Nome do produto é obrigatório");

        ProdutoId = produtoId;
        NomeProduto = nomeProduto.Trim();
        Quantidade = quantidade;

        // 'with { }' cria uma CÓPIA do record. Parece inútil (Dinheiro é
        // imutável), mas não é: para o EF Core, um Value Object mapeado com
        // OwnsOne é uma entidade "dona de ninguém mais". Se o item apontasse
        // para a MESMA instância de Dinheiro que o Produto carregado usa, o EF
        // veria um objeto com dois donos e lançaria InvalidOperationException
        // no SaveChanges. Cópia = um dono só.
        PrecoUnitario = precoUnitario with { };
    }
}

using LojaEventos.Domain.Events;

namespace LojaEventos.Domain.Entities;

/// <summary>Estados do pedido. Guardado como STRING no banco (ver AppDbContext).</summary>
public enum StatusPedido
{
    AguardandoEstoque = 0,   // criado; o consumidor de estoque ainda não respondeu
    Confirmado = 1,          // estoque reservado com sucesso
    Rejeitado = 2            // sem estoque → pedido recusado
}

// ════════════════════════════════════════════════════════════════════════════
//  AGGREGATE ROOT (DDD) — a única porta de entrada para mexer no pedido.
//
//  Decisão que vale ouro em arquitetura de eventos: o Id é um **GUID gerado no
//  domínio**, não um auto-increment do banco.
//    • Na Tab 7 o id vinha do MySQL, então o evento era publicado com Id = 0.
//    • Com GUID, a entidade já nasce identificada → o evento sai correto, o
//      cliente pode receber o id antes do commit, e o consumidor tem uma chave
//      estável para deduplicar.
//  Custo: GUID aleatório fragmenta índice no MySQL. Mitigação: gravamos como
//  CHAR(36) e a ordenação cronológica usa 'CriadoEm' (nunca o id).
// ════════════════════════════════════════════════════════════════════════════
public class Pedido
{
    private readonly List<ItemPedido> _itens = new();
    private readonly List<IDomainEvent> _eventos = new();

    public Guid Id { get; private set; }
    public string ClienteEmail { get; private set; } = string.Empty;
    public StatusPedido Status { get; private set; }
    public Dinheiro Total { get; private set; } = Dinheiro.Zero;
    public DateTime CriadoEm { get; private set; }
    public string? MotivoRejeicao { get; private set; }

    /// <summary>Somente leitura: itens só entram pelo método AdicionarItem.</summary>
    public IReadOnlyCollection<ItemPedido> Itens => _itens.AsReadOnly();

    /// <summary>
    /// Eventos de domínio pendentes. Quem drena esta lista é a camada de
    /// aplicação (PedidoService), que os traduz em Integration Events e grava
    /// no OUTBOX — na mesma transação do agregado.
    /// </summary>
    public IReadOnlyCollection<IDomainEvent> EventosPendentes => _eventos.AsReadOnly();

    protected Pedido() { }   // EF Core

    // ── FÁBRICA ─────────────────────────────────────────────────────────────
    // Note que Criar() NÃO publica o evento ainda: só depois dos itens
    // entrarem é que sabemos o Total. Publicar um evento com total zerado é um
    // erro clássico. O evento nasce em Fechar().
    public static Pedido Criar(string clienteEmail)
    {
        if (string.IsNullOrWhiteSpace(clienteEmail))
            throw new DomainException("E-mail do cliente é obrigatório");
        if (!clienteEmail.Contains('@'))
            throw new DomainException("E-mail do cliente inválido");

        return new Pedido
        {
            Id = Guid.NewGuid(),
            ClienteEmail = clienteEmail.Trim().ToLowerInvariant(),
            Status = StatusPedido.AguardandoEstoque,
            CriadoEm = DateTime.UtcNow
        };
    }

    public void AdicionarItem(long produtoId, string nomeProduto, int quantidade, Dinheiro precoUnitario)
    {
        if (Status != StatusPedido.AguardandoEstoque)
            throw new DomainException("Pedido já processado: não aceita novos itens");
        if (_itens.Count >= 50)
            throw new DomainException("Máximo de 50 itens por pedido");
        if (_itens.Any(i => i.ProdutoId == produtoId))
            throw new DomainException($"Produto {produtoId} já está no pedido");

        var item = new ItemPedido(produtoId, nomeProduto, quantidade, precoUnitario);
        _itens.Add(item);
        RecalcularTotal();
    }

    /// <summary>
    /// Fecha o pedido e REGISTRA o fato. Chamado uma única vez, no fim do caso
    /// de uso, quando o agregado já está completo e consistente.
    /// </summary>
    public void Fechar()
    {
        if (_itens.Count == 0) throw new DomainException("Pedido precisa de ao menos 1 item");
        if (_eventos.Count > 0) throw new DomainException("Pedido já foi fechado");

        _eventos.Add(new PedidoCriadoEvent(
            Id, ClienteEmail, Total.Valor, Total.Moeda,
            _itens.Select(i => new PedidoCriadoItem(i.ProdutoId, i.Quantidade, i.PrecoUnitario.Valor)).ToList()));
    }

    // ── TRANSIÇÕES DISPARADAS POR EVENTOS QUE CHEGAM DE VOLTA ───────────────
    // Estes dois métodos são IDEMPOTENTES de propósito: o consumidor pode
    // receber a mesma mensagem duas vezes (at-least-once), e chamar
    // Confirmar() duas vezes não pode explodir nem gerar efeito diferente.
    public void Confirmar()
    {
        if (Status == StatusPedido.Confirmado) return;        // já confirmado → no-op
        if (Status == StatusPedido.Rejeitado)
            throw new DomainException("Pedido rejeitado não pode ser confirmado");
        Status = StatusPedido.Confirmado;
    }

    public void Rejeitar(string motivo)
    {
        if (Status == StatusPedido.Rejeitado) return;         // já rejeitado → no-op
        if (Status == StatusPedido.Confirmado)
            throw new DomainException("Pedido confirmado não pode ser rejeitado");
        Status = StatusPedido.Rejeitado;
        MotivoRejeicao = motivo;
    }

    public void LimparEventos() => _eventos.Clear();

    private void RecalcularTotal() =>
        Total = _itens.Aggregate(Dinheiro.Zero, (acc, i) => acc.Somar(i.Subtotal));

    /// <summary>
    /// RECONSTITUIR ≠ CRIAR. Criar() aplica regras de entrada e gera id novo;
    /// Reconstituir() remonta um pedido que JÁ EXISTE (vindo do banco) sem
    /// disparar evento nenhum. Confundir os dois faz o sistema republicar
    /// eventos antigos a cada leitura.
    /// </summary>
    public static Pedido Reconstituir(Guid id, string clienteEmail, StatusPedido status,
                                      Dinheiro total, DateTime criadoEm, string? motivoRejeicao)
        => new()
        {
            Id = id, ClienteEmail = clienteEmail, Status = status,
            Total = total, CriadoEm = criadoEm, MotivoRejeicao = motivoRejeicao
        };
}

// ════════════════════════════════════════════════════════════════════════════
//  Segundo agregado, propositalmente MAGRO. Existe aqui para o consumidor de
//  estoque ter em quem mexer quando o evento 'pedido-criado' chega.
//
//  Concorrência no estoque — DUAS defesas, para dois caminhos diferentes:
//   • RESERVA (consumidor): UPDATE atômico condicional no repositório
//     ('... WHERE estoque >= @q'). O banco decide; não há read-modify-write.
//   • QUALQUER OUTRA ALTERAÇÃO via EF (ex.: um admin editando o produto):
//     'Versao' é o OPTIMISTIC CONCURRENCY TOKEN. O EF inclui
//     'WHERE versao = @lida' no UPDATE; se outro processo mudou a linha antes,
//     zero linhas são afetadas e o EF lança DbUpdateConcurrencyException em
//     vez de sobrescrever a baixa de estoque em silêncio (lost update).
//   O UPDATE atômico também incrementa 'versao', para as duas defesas
//   conversarem entre si.
// ════════════════════════════════════════════════════════════════════════════
public class Produto
{
    public long Id { get; private set; }
    public string Nome { get; private set; } = string.Empty;
    public Dinheiro Preco { get; private set; } = Dinheiro.Zero;
    public int Estoque { get; private set; }
    public int Versao { get; private set; }

    protected Produto() { }

    public static Produto Criar(string nome, Dinheiro preco, int estoque)
    {
        if (string.IsNullOrWhiteSpace(nome) || nome.Trim().Length < 2)
            throw new DomainException("Nome deve ter >= 2 caracteres");
        if (preco.Valor <= 0) throw new DomainException("Preço deve ser > 0");
        if (estoque < 0) throw new DomainException("Estoque não pode ser negativo");

        return new Produto { Nome = nome.Trim(), Preco = preco, Estoque = estoque };
    }

    /// <summary>
    /// Tenta reservar. Devolve bool em vez de lançar exceção porque "sem
    /// estoque" NÃO é um erro do sistema: é uma resposta de negócio legítima,
    /// e o consumidor precisa saber disso para rejeitar o pedido (não para
    /// tentar de novo). Exceção = tenta de novo; false = decisão tomada.
    /// </summary>
    public bool TentarReservar(int quantidade)
    {
        if (quantidade <= 0) throw new DomainException("Quantidade deve ser > 0");
        if (Estoque < quantidade) return false;
        Estoque -= quantidade;
        Versao++;
        return true;
    }

    public void Devolver(int quantidade)
    {
        if (quantidade <= 0) throw new DomainException("Quantidade deve ser > 0");
        Estoque += quantidade;
        Versao++;
    }

    public static Produto Reconstituir(long id, string nome, Dinheiro preco, int estoque, int versao)
        => new() { Id = id, Nome = nome, Preco = preco, Estoque = estoque, Versao = versao };
}

3O contrato do evento: envelope + versionamento

Aqui mora a distinção mais importante da aba:

🏠 Domain Event

PedidoCriadoEvent. Nasce dentro do agregado, vive em memória, é código seu. Pode mudar de forma quando quiser.

🌍 Integration Event

O EventEnvelope que vai para a fila. É contrato público: outros serviços dependem dele. Mudar um campo quebra terceiros → precisa de .v1, .v2.

🔁 A tradução

Acontece no caso de uso (Passo 5), e o resultado é gravado no outbox no mesmo commit do agregado. É essa tradução que dá a garantia.

//  DOMAIN EVENT vs INTEGRATION EVENT — a distinção mais importante desta aba
// ════════════════════════════════════════════════════════════════════════════
//  DOMAIN EVENT (isto aqui):
//    • nasce DENTRO do agregado ("algo de negócio aconteceu");
//    • vive no processo, em memória, até a transação terminar;
//    • pode mudar de forma quando quisermos: é código NOSSO, interno.
//
//  INTEGRATION EVENT (o que vai para o RabbitMQ — ver EventEnvelope):
//    • é CONTRATO PÚBLICO: outros serviços dependem do formato dele;
//    • sai do processo, atravessa a rede, pode chegar 2x e fora de ordem;
//    • mudar um campo dele quebra os outros = precisa de versionamento.
//

//  despachava). Aqui ele é TRADUZIDO em Integration Event e gravado no OUTBOX
//  dentro da MESMA transação do agregado. É essa tradução que garante a entrega.
// ════════════════════════════════════════════════════════════════════════════
public interface IDomainEvent
{
    /// <summary>Quando o fato aconteceu (sempre UTC — fuso é problema da borda).</summary>

    /// <summary>
    /// Nome do evento no contrato público, no formato "contexto.fato.vN".
    /// Fica aqui (e não no publicador) para o nome ser decidido pelo DOMÍNIO,
    /// não pela infraestrutura. Se amanhã trocarmos RabbitMQ por Kafka, o nome

    /// </summary>

using System.Text.Json;
using System.Text.Json.Serialization;

namespace LojaEventos.Application.Messaging;

// ════════════════════════════════════════════════════════════════════════════
//  ENVELOPE — o CONTRATO PÚBLICO que viaja pela fila.
//
//  Por que separar envelope de payload? Porque o consumidor precisa decidir
//  "já vi isso?" e "sei ler esta versão?" ANTES de desserializar o payload.
//  Metadado na casca, negócio no recheio.
//
//  Campo por campo, e por que cada um existe:
//   • MessageId  → chave de DEDUPLICAÇÃO. É o que o inbox do consumidor guarda.
//                  Sem ele, at-least-once vira "processei o pedido 2x".
//   • Tipo       → "pedidos.pedido-criado.v1". Roteamento + versionamento.
//   • OcorreuEm  → quando o FATO aconteceu (não quando a mensagem foi enviada).
//   • CorrelationId → amarra tudo o que nasceu de uma mesma requisição HTTP.
//                  É o que faz o log distribuído ser legível.
//   • CausationId→ qual mensagem causou esta. Monta a árvore de causa e efeito.
//   • Payload    → JSON cru. Fica como string e não como objeto para o
//                  despachante do outbox NÃO precisar conhecer os tipos de
//                  domínio: ele só repassa bytes. Acoplamento mínimo.
// ════════════════════════════════════════════════════════════════════════════
public sealed record EventEnvelope(
    [property: JsonPropertyName("messageId")] Guid MessageId,
    [property: JsonPropertyName("tipo")] string Tipo,
    [property: JsonPropertyName("ocorreuEm")] DateTime OcorreuEm,
    [property: JsonPropertyName("correlationId")] string CorrelationId,
    [property: JsonPropertyName("causationId")] string? CausationId,
    [property: JsonPropertyName("payload")] string Payload)
{
    /// <summary>
    /// Opções de serialização ÚNICAS para todo o sistema. Centralizar isto é
    /// obrigatório: se a API serializa camelCase e o worker desserializa
    /// PascalCase, o payload chega com todos os campos nulos e o bug é
    /// silencioso — nada estoura, o pedido simplesmente fica com total 0.
    /// </summary>
    public static readonly JsonSerializerOptions Json = new()
    {
        PropertyNamingPolicy = JsonNamingPolicy.CamelCase,
        PropertyNameCaseInsensitive = true,
        DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull
    };

    /// <summary>Desserializa o recheio no tipo esperado pelo consumidor.</summary>
    public T LerPayload<T>() =>
        JsonSerializer.Deserialize<T>(Payload, Json)
        ?? throw new InvalidOperationException($"Payload vazio no evento {Tipo} ({MessageId})");

    /// <summary>
    /// "pedidos.pedido-criado.v1" → 1. O consumidor usa isso para ignorar com
    /// elegância uma versão que não conhece, em vez de explodir em loop.
    /// </summary>
    public int Versao =>
        Tipo.LastIndexOf(".v", StringComparison.Ordinal) is var i && i >= 0
        && int.TryParse(Tipo[(i + 2)..], out var v) ? v : 1;
}
⚠️ O bug silencioso nº 1 de mensageria: a API serializa em camelCase e o worker desserializa esperando PascalCase. Nada estoura: o payload chega com todos os campos nulos/zerados e o pedido vira total 0. Por isso EventEnvelope.Json é static readonly e compartilhado pelos dois processos — uma única fonte de verdade para a serialização.

Versionamento na prática: o nome carrega a versão (pedidos.pedido-criado.v1) e o consumidor declara até qual versão sabe ler. Quando o payload mudar de forma incompatível, nasce a .v2 e as duas convivem durante a transição: consumidor novo lê v2, antigo continua lendo v1, e você atualiza um por vez sem big-bang.

namespace LojaEventos.Infrastructure.Data;

// ════════════════════════════════════════════════════════════════════════════
//  A TABELA OUTBOX. Olhe para ela como uma FILA DENTRO DO SEU BANCO.
//
//  Ela existe por um motivo só: transformar "gravar no MySQL + publicar no
//  RabbitMQ" (duas escritas, dois sistemas, sem transação em comum) em
//  "gravar no MySQL" (uma escrita, um sistema, transação trivial).
//
//  O preço: a entrega passa a ser ASSÍNCRONA e AT-LEAST-ONCE. O evento pode
//  chegar 300ms depois, e pode chegar duas vezes (se o processo cair entre o
//  publicar e o marcar como processado). Em troca, ele NUNCA se perde.
//  Esse trade-off é a espinha dorsal de arquitetura orientada a eventos:
//  você escolhe "pode duplicar" em vez de "pode perder", porque duplicação
//  se resolve com idempotência no consumidor e perda não se resolve com nada.
// ════════════════════════════════════════════════════════════════════════════
public class OutboxMessage
{
    /// <summary>
    /// Auto-increment. É de propósito: a ORDEM de publicação precisa ser a
    /// ordem de gravação, e um BIGINT sequencial dá isso de graça. Com GUID
    /// aleatório você perderia a ordem e a localidade do índice.
    /// </summary>
    public long Id { get; set; }

    /// <summary>Id da MENSAGEM — é o que o consumidor deduplica (inbox).</summary>
    public Guid MessageId { get; set; }

    public string Tipo { get; set; } = string.Empty;
    public string RoutingKey { get; set; } = string.Empty;
    public string Payload { get; set; } = string.Empty;
    public string CorrelationId { get; set; } = string.Empty;
    public string? CausationId { get; set; }
    public DateTime OcorreuEm { get; set; }
    public DateTime CriadoEm { get; set; }

    /// <summary>
    /// NULL = ainda não publicado. Preenchido = o broker CONFIRMOU.
    /// Nunca marque antes da confirmação: você estaria apagando a única cópia
    /// do evento com base em esperança.
    /// </summary>
    public DateTime? ProcessadoEm { get; set; }

    /// <summary>Quantas vezes já tentamos publicar (para backoff e alarme).</summary>
    public int Tentativas { get; set; }

    /// <summary>Quando a próxima tentativa é permitida (backoff exponencial).</summary>
    public DateTime ProximaTentativaEm { get; set; }

    /// <summary>Último erro — é isto que você lê às 3h da manhã.</summary>
    public string? UltimoErro { get; set; }
}

namespace LojaEventos.Infrastructure.Data;

// ════════════════════════════════════════════════════════════════════════════
//  A TABELA DE IDEMPOTÊNCIA HTTP.
//
//  Por que guardar o CORPO DA RESPOSTA e não só um "já fiz"?
//  Porque o cliente que repete a requisição precisa do MESMO resultado —
//  inclusive do id do pedido criado. Responder "202, já processei" obrigaria o
//  cliente a sair caçando o pedido, e ele não tem como saber qual é.
//
//  'ExpiraEm': estes registros PRECISAM morrer. Guardar chaves de idempotência
//  para sempre é vazamento de disco garantido. 24h a 7 dias é o usual — o
//  prazo precisa ser maior que o retry mais longo dos seus clientes.
//  A limpeza é um DELETE agendado (ver scripts/limpeza.sql na aba).
// ════════════════════════════════════════════════════════════════════════════
public class IdempotencyRecord
{
    /// <summary>A Idempotency-Key enviada pelo cliente. É a chave primária.</summary>
    public string Chave { get; set; } = string.Empty;

    /// <summary>Rota de origem — a mesma chave em rotas diferentes é outra coisa.</summary>
    public string Rota { get; set; } = string.Empty;

    /// <summary>SHA-256 do corpo canônico — detecta reuso indevido da chave.</summary>
    public string HashCorpo { get; set; } = string.Empty;

    public int StatusCode { get; set; }
    public string CorpoResposta { get; set; } = string.Empty;
    public DateTime CriadoEm { get; set; }

LojaEventos.Domain/Interfaces/IUnitOfWork.cs 
namespace LojaEventos.Domain.Interfaces;

// ════════════════════════════════════════════════════════════════════════════
//  UNIT OF WORK — o coração da garantia desta aba.
//
//  O caso de uso precisa gravar TRÊS coisas e, ou as três entram, ou nenhuma:
//     1. o agregado Pedido (+ itens)
//     2. a linha do OUTBOX com o evento a publicar
//     3. o registro de IDEMPOTÊNCIA da requisição HTTP
//
//  Com uma única transação no MySQL isso é trivial. O que NÃO é possível é
//  incluir o "publicar no RabbitMQ" nessa transação: são dois sistemas
//  diferentes, sem commit em dois passos (2PC). É exatamente esse buraco que o
//  outbox fecha — trocando "gravar + publicar" (2 sistemas) por "gravar"
//  (1 sistema) e deixando a publicação para um processo separado.
// ════════════════════════════════════════════════════════════════════════════
public interface IUnitOfWork
{
    /// <summary>Confirma tudo o que foi registrado desde o início da transação.</summary>
    Task<int> CommitAsync(CancellationToken ct = default);

    /// <summary>
    /// Executa a ação dentro de UMA transação explícita, com rollback
    /// automático em caso de exceção. Usado pelos consumidores, que precisam
    /// gravar o efeito + a marca de "já processei" juntos (ver inbox).
    /// </summary>
    Task ExecutarEmTransacaoAsync(Func<CancellationToken, Task> acao, CancellationToken ct = default);
}

namespace LojaEventos.Infrastructure.Data;

// ════════════════════════════════════════════════════════════════════════════
//  DbContext — cinco tabelas, três delas de INFRAESTRUTURA DE MENSAGERIA
//  (outbox, inbox, idempotência). Elas moram no mesmo banco das tabelas de
//  negócio POR DESIGN: só assim o commit é um só.
//
//  Guardar o outbox em outro banco (ou no Redis) destruiria o padrão — você
//  voltaria a ter duas escritas em dois sistemas, que é exatamente o problema
//  que o outbox existe para resolver.
// ════════════════════════════════════════════════════════════════════════════
public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

    public DbSet<Pedido> Pedidos => Set<Pedido>();
    public DbSet<ItemPedido> ItensPedido => Set<ItemPedido>();
    public DbSet<Produto> Produtos => Set<Produto>();
    public DbSet<OutboxMessage> Outbox => Set<OutboxMessage>();
    public DbSet<InboxMessage> Inbox => Set<InboxMessage>();
    public DbSet<IdempotencyRecord> Idempotencia => Set<IdempotencyRecord>();

    protected override void OnModelCreating(ModelBuilder mb)
    {
        // ── PEDIDO (Aggregate Root) ─────────────────────────────────────────
        mb.Entity<Pedido>(e =>
        {
            e.ToTable("pedidos");
            e.HasKey(p => p.Id);
            e.Property(p => p.Id).HasColumnName("id").HasColumnType("char(36)").ValueGeneratedNever();
            //                                                        ↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑
            // ValueGeneratedNever é ESSENCIAL: o Guid vem do domínio, não do
            // banco. Sem isso o EF acha que ele é gerado no insert e ignora o
            // valor que o agregado já definiu — e o evento publicado passaria a
            // apontar para um id que não existe na tabela.

            e.Property(p => p.ClienteEmail).HasColumnName("cliente_email").HasMaxLength(180).IsRequired();
            e.Property(p => p.CriadoEm).HasColumnName("criado_em").IsRequired();
            e.Property(p => p.MotivoRejeicao).HasColumnName("motivo_rejeicao").HasMaxLength(200);

            // Enum como STRING, nunca como int. Com int, inserir um valor novo
            // no meio do enum renumera tudo e os dados antigos passam a
            // significar outra coisa. Com string, o banco continua legível e
            // a ordem do enum deixa de importar.
            e.Property(p => p.Status).HasColumnName("status").HasMaxLength(30)
             .HasConversion<string>().IsRequired();

            // VALUE OBJECT: as DUAS propriedades são mapeadas.
            // (Na Tab 7 havia 'Ignore(p => p.Preco)' logo antes de 'OwnsOne' —
            //  o EF lança InvalidOperationException nessa combinação — e um
            //  'Ignore(x => x.Moeda)' que impedia o EF de bindar o construtor
            //  posicional do record. Aqui nada é ignorado.)
            e.OwnsOne(p => p.Total, d =>
            {
                d.Property(x => x.Valor).HasColumnName("total").HasColumnType("decimal(12,2)").IsRequired();
                d.Property(x => x.Moeda).HasColumnName("total_moeda").HasMaxLength(3).IsRequired();
            });

            // Coleção do agregado via BACKING FIELD: ninguém adiciona item
            // pela navegação, só pelo método AdicionarItem da raiz.
            e.HasMany(p => p.Itens)
             .WithOne()
             .HasForeignKey(i => i.PedidoId)
             .OnDelete(DeleteBehavior.Cascade);
            e.Navigation(p => p.Itens).UsePropertyAccessMode(PropertyAccessMode.Field);

            e.Ignore(p => p.EventosPendentes);   // eventos vivem em memória, nunca na tabela

            e.HasIndex(p => p.CriadoEm).HasDatabaseName("ix_pedidos_criado_em");
            e.HasIndex(p => p.ClienteEmail).HasDatabaseName("ix_pedidos_cliente");
        });

        // ── ITEM DO PEDIDO (membro do agregado) ─────────────────────────────
        mb.Entity<ItemPedido>(e =>
        {
            e.ToTable("itens_pedido");
            e.HasKey(i => i.Id);
            e.Property(i => i.Id).HasColumnName("id");
            e.Property(i => i.PedidoId).HasColumnName("pedido_id").HasColumnType("char(36)").IsRequired();
            e.Property(i => i.ProdutoId).HasColumnName("produto_id").IsRequired();
            e.Property(i => i.NomeProduto).HasColumnName("nome_produto").HasMaxLength(120).IsRequired();
            e.Property(i => i.Quantidade).HasColumnName("quantidade").IsRequired();
            e.OwnsOne(i => i.PrecoUnitario, d =>
            {
                d.Property(x => x.Valor).HasColumnName("preco_unitario").HasColumnType("decimal(12,2)").IsRequired();
                d.Property(x => x.Moeda).HasColumnName("preco_moeda").HasMaxLength(3).IsRequired();
            });
            e.Ignore(i => i.Subtotal);   // calculado: persistir seria convidar divergência
            e.HasIndex(i => i.PedidoId).HasDatabaseName("ix_itens_pedido");
        });

        // ── PRODUTO ─────────────────────────────────────────────────────────
        mb.Entity<Produto>(e =>
        {
            e.ToTable("produtos");
            e.HasKey(p => p.Id);
            e.Property(p => p.Id).HasColumnName("id");
            e.Property(p => p.Nome).HasColumnName("nome").HasMaxLength(120).IsRequired();
            e.Property(p => p.Estoque).HasColumnName("estoque").IsRequired();

            e.Property(p => p.Versao).HasColumnName("versao").IsConcurrencyToken().IsRequired();

                d.Property(x => x.Valor).HasColumnName("preco").HasColumnType("decimal(12,2)").IsRequired();
                d.Property(x => x.Moeda).HasColumnName("preco_moeda").HasMaxLength(3).IsRequired();

        });

        mb.Entity<OutboxMessage>(e =>
        {
            e.ToTable("outbox_messages");
            e.HasKey(o => o.Id);
            e.Property(o => o.Id).HasColumnName("id");
            e.Property(o => o.MessageId).HasColumnName("message_id").HasColumnType("char(36)").IsRequired();
            e.Property(o => o.Tipo).HasColumnName("tipo").HasMaxLength(120).IsRequired();
            e.Property(o => o.RoutingKey).HasColumnName("routing_key").HasMaxLength(120).IsRequired();
            e.Property(o => o.Payload).HasColumnName("payload").HasColumnType("json").IsRequired();
            e.Property(o => o.CorrelationId).HasColumnName("correlation_id").HasMaxLength(64).IsRequired();
            e.Property(o => o.CausationId).HasColumnName("causation_id").HasMaxLength(64);
            e.Property(o => o.OcorreuEm).HasColumnName("ocorreu_em").IsRequired();
            e.Property(o => o.CriadoEm).HasColumnName("criado_em").IsRequired();

using LojaEventos.Domain.Interfaces;
using Microsoft.EntityFrameworkCore;

namespace LojaEventos.Infrastructure.Data;

// ════════════════════════════════════════════════════════════════════════════
//  Adapter do IUnitOfWork sobre o DbContext do EF Core.
//
//  Detalhe importante: o EF já agrupa TODO 'SaveChangesAsync' numa transação
//  implícita. Então por que abrir uma explícita? Porque o consumidor de
//  estoque mistura SQL cru (o UPDATE atômico de reserva) com o SaveChanges do
//  inbox e do pedido. Dois comandos diferentes só ficam atômicos se estiverem
//  dentro da MESMA transação explícita — é ela que costura tudo.
//
//  ┌─ ARMADILHA REAL: retry automático + transação explícita ────────────────┐
//  │ O AddInfraestrutura liga 'EnableRetryOnFailure' (o EF repete sozinho     │
//  │ comandos que falharam por queda momentânea do MySQL). Com isso ligado, o │
//  │ EF PROÍBE 'BeginTransactionAsync' solto e lança:                         │
//  │   InvalidOperationException: The configured execution strategy           │
//  │   'MySqlRetryingExecutionStrategy' does not support user-initiated       │
//  │   transactions.                                                         │
//  │ Motivo: se a falha acontecer no meio da transação, o EF não tem como     │
//  │ repetir só o último comando — precisa repetir o BLOCO inteiro. A saída   │
//  │ é entregar o bloco para a estratégia: 'CreateExecutionStrategy()' +      │
//  │ 'ExecuteAsync'. Ela abre a transação, roda tudo e, se cair, repete tudo. │
//  └─────────────────────────────────────────────────────────────────────────┘
// ════════════════════════════════════════════════════════════════════════════
public class UnitOfWork : IUnitOfWork
{
    private readonly AppDbContext _ctx;
    public UnitOfWork(AppDbContext ctx) { _ctx = ctx; }

    public Task<int> CommitAsync(CancellationToken ct = default) => _ctx.SaveChangesAsync(ct);

    public async Task ExecutarEmTransacaoAsync(Func<CancellationToken, Task> acao, CancellationToken ct = default)
    {
        // Se já existe transação em andamento (ex.: chamada aninhada), apenas
        // participa dela. Abrir transação dentro de transação no MySQL cria um
        // savepoint e confunde o rollback.
        if (_ctx.Database.CurrentTransaction is not null) { await acao(ct); return; }

        var estrategia = _ctx.Database.CreateExecutionStrategy();
        var tentativa = 0;

        await estrategia.ExecuteAsync(async () =>
        {
            // Numa REPETIÇÃO, o change tracker ainda guarda o que a tentativa
            // anterior adicionou (o SaveChanges falhou, então tudo segue como
            // "Added"). Se não limparmos, a nova execução da ação adiciona de
            // novo: duas linhas no outbox para o mesmo evento. Por isso a ação
            // precisa ser REPETÍVEL: tudo o que ela grava, ela mesma registra.
            if (tentativa++ > 0) _ctx.ChangeTracker.Clear();

            // 'await using' garante o rollback: se a ação lançar, a transação
            // é descartada sem commit e NADA fica gravado.
            await using var tx = await _ctx.Database.BeginTransactionAsync(ct);
            await acao(ct);
            await tx.CommitAsync(ct);
        });
    }
}

5⭐ O caso de uso: UMA transação, TRÊS gravações

Este é o arquivo mais importante da aba. Leia os comentários dele linha por linha.

Dentro de CriarAsync, em um único commit:

  1. a chave de idempotência — para a mesma requisição não virar dois pedidos;
  2. o agregado Pedido (+ itens) — o dado;
  3. o evento no outbox — a promessa de avisar os outros;
  4. a resposta HTTP serializada — para o replay devolver exatamente igual.

E o que não acontece: nenhuma linha deste arquivo fala com o RabbitMQ. Essa ausência é a decisão de arquitetura.

//
//  Em 'CriarAsync' acontecem, em UMA ÚNICA TRANSAÇÃO:

{

    private readonly IProdutoRepository _produtos;
    private readonly IOutbox _outbox;
    private readonly IIdempotencyStore _idempotencia;
    private readonly IUnitOfWork _uow;
    private readonly ILogger<PedidoService> _log;

    public PedidoService(IPedidoRepository pedidos, IProdutoRepository produtos, IOutbox outbox,
                         IIdempotencyStore idempotencia, IUnitOfWork uow, ILogger<PedidoService> log)
    {
        _pedidos = pedidos; _produtos = produtos; _outbox = outbox;
        _idempotencia = idempotencia; _uow = uow; _log = log;
    }

    public async Task<(PedidoResponse, bool)> CriarAsync(
        CriarPedidoRequest request, string idempotencyKey, string correlationId, CancellationToken ct = default)
    {
        if (string.IsNullOrWhiteSpace(idempotencyKey))
            throw new DomainException("Cabeçalho Idempotency-Key é obrigatório no POST");

        // ── PASSO 1: a requisição é nova? ───────────────────────────────────
        // O hash é do CORPO CANÔNICO (ver CalcularHash): um JSON com as mesmas
        // informações em outra ordem continua sendo "o mesmo pedido", e um JSON
        // com valores diferentes é detectado como conflito.
        const string rota = "POST /api/pedidos";
        var hash = CalcularHash(request);

        var (resultado, guardada) = await _idempotencia.ConsultarAsync(idempotencyKey, hash, ct);

        if (resultado == ResultadoIdempotencia.Replay)
        {
            // Caminho felizmente chato: devolvemos o que já respondemos antes.
            // Nada é criado, nada é publicado, o estoque não se move.
            _log.LogInformation("Replay idempotente da chave {Chave}", idempotencyKey);
            return (Desserializar(guardada!.Corpo), true);
        }

        if (resultado == ResultadoIdempotencia.ConflitoDeCorpo)
            throw new CorpoDivergenteException(
                $"A Idempotency-Key '{idempotencyKey}' já foi usada com outro corpo. " +
                "Gere uma chave nova para uma requisição diferente.");

        // ── PASSO 2: montar o agregado (regras de negócio) ──────────────────
        // Tudo isto é em memória: nada tocou o banco ainda. Se uma invariante
        // estourar aqui, a transação nem começou.
        if (request.Itens is null || request.Itens.Count == 0)
            throw new DomainException("Pedido precisa de ao menos 1 item");

        var pedido = Pedido.Criar(request.ClienteEmail);

        foreach (var item in request.Itens)
        {
            // Lemos o produto só para fixar NOME e PREÇO do momento da compra
            // (preço é dado histórico do pedido: se o produto encarecer amanhã,
            // o pedido de hoje não muda de valor).
            //
            // Note que NÃO verificamos estoque aqui. Checar agora seria leitura
            // suja: entre a checagem e a reserva, outro pedido leva a última
            // peça. Quem reserva é o consumidor de estoque, atomicamente.
            var produto = await _produtos.BuscarPorIdAsync(item.ProdutoId, ct)
                          ?? throw new NaoEncontradoException("Produto", item.ProdutoId);

            pedido.AdicionarItem(produto.Id, produto.Nome, item.Quantidade, produto.Preco);
        }

        pedido.Fechar();   // agregado completo → agora o fato pode ser registrado

        // ── PASSO 3: UMA transação, três gravações ──────────────────────────
        var resposta = PedidoMapper.ToResponse(pedido);
        var corpoResposta = JsonSerializer.Serialize(resposta, EventEnvelope.Json);

        try
        {
            await _uow.ExecutarEmTransacaoAsync(async token =>
            {
                // (a) O DADO
                await _pedidos.AdicionarAsync(pedido, token);

                // (b) A PROMESSA DE AVISAR OS OUTROS
                foreach (var evento in pedido.EventosPendentes)
                {
                    var envelope = new EventEnvelope(
                        MessageId: Guid.NewGuid(),   // identidade da MENSAGEM (≠ id do pedido)
                        Tipo: evento.TipoEvento,
                        OcorreuEm: evento.OcorreuEm,
                        CorrelationId: correlationId,
                        CausationId: null,           // nasceu de um POST, não de outra mensagem
                        Payload: JsonSerializer.Serialize((PedidoCriadoEvent)evento, EventEnvelope.Json));

                    // routingKey = tipo do evento. Quem quiser ouvir faz o bind;
                    // o produtor não sabe (nem precisa saber) quem são os ouvintes.
                    // É isso que permite acrescentar um consumidor novo amanhã
                    // sem recompilar nem reiniciar a API.
                    await _outbox.RegistrarAsync(envelope, evento.TipoEvento, token);
                }

                // (c) A RESPOSTA, para o replay devolver exatamente igual
                await _idempotencia.RegistrarAsync(idempotencyKey, rota, hash, 201, corpoResposta, token);

                await _uow.CommitAsync(token);
            }, ct);
        }
        catch (Exception ex) when (_idempotencia.EhChaveDuplicada(ex))
        {
            // Duas requisições com a MESMA chave chegaram ao mesmo tempo: ambas
            // passaram pelo ConsultarAsync, ambas tentaram gravar, e a chave
            // primária única barrou esta. A outra venceu e JÁ criou o pedido —
            // então relemos e devolvemos a resposta dela. O cliente nem percebe.
            _log.LogWarning("Corrida na chave {Chave}: outra requisição venceu; devolvendo replay", idempotencyKey);
            var (_, agoraGuardada) = await _idempotencia.ConsultarAsync(idempotencyKey, hash, ct);
            if (agoraGuardada is not null) return (Desserializar(agoraGuardada.Corpo), true);
            throw new ConflitoException($"A Idempotency-Key '{idempotencyKey}' está em uso. Tente novamente.");
        }

        // Daqui para a frente o evento está SEGURO: ele está no banco, no mesmo
        // commit do pedido. Se o processo morrer neste exato instante, o
        // OutboxPublisherService publica assim que alguém subir. Não há perda.
        pedido.LimparEventos();

        _log.LogInformation("Pedido {PedidoId} criado · {Itens} itens · total {Total} · correlation {Corr}",
            pedido.Id, pedido.Itens.Count, pedido.Total, correlationId);

        return (resposta, false);
    }

6O despachante: FOR UPDATE SKIP LOCKED e backoff

A outra metade do padrão. Ele faz uma coisa só, em laço: lê um lote de linhas pendentes, publica cada uma e marca como processada. Simples na superfície — e com quatro decisões que separam uma implementação correta de uma que corrompe dados:

DecisãoSe você fizer diferente
FOR UPDATE SKIP LOCKEDDuas réplicas do worker leem o mesmo lote e publicam tudo em dobro. (Sem SKIP LOCKED, a segunda espera em vez de pular, e a vazão cai pela metade.)
Publicar antes de marcarNa ordem inversa, uma queda no meio gera perda. Nesta ordem gera duplicata — que o Inbox resolve. Escolha sempre o problema tratável.
tentativas + proxima_tentativa_emUma mensagem com payload quebrado trava a fila inteira: o despachante tenta a mesma linha para sempre e nenhuma outra passa.
Um commit por loteCommit linha a linha triplica o custo e segura os locks por muito mais tempo.

// ════════════════════════════════════════════════════════════════════════════
//  O DESPACHANTE DO OUTBOX — a outra metade do padrão.
//
//  Ele faz uma coisa só, em laço: lê um lote de linhas não publicadas, publica
//  cada uma no broker e marca como processada. Simples na superfície, mas há
//  QUATRO decisões que separam uma implementação correta de uma que corrompe
//  dados em produção:
//
//  1) FOR UPDATE SKIP LOCKED
//     Se você rodar DUAS instâncias do worker (e vai rodar, por HA), as duas
//     leem o mesmo lote e publicam tudo em DOBRO. SKIP LOCKED faz a segunda
//     instância PULAR as linhas que a primeira já travou, em vez de esperar.
//     É o jeito de usar uma tabela MySQL como fila concorrente.
//
//  2) PUBLICAR ANTES DE MARCAR
//     Nesta ordem, uma queda entre o publish e o update gera DUPLICATA
//     (a linha continua pendente e será publicada de novo).
//     Na ordem inversa geraria PERDA. Duplicata o consumidor resolve com o
//     inbox; perda não se resolve com nada. Escolhemos o problema tratável.
//
//  3) BACKOFF E ISOLAMENTO DA FALHA
//     Uma mensagem com payload quebrado não pode travar a fila inteira. Cada
//     linha tem 'tentativas' e 'proxima_tentativa_em': ela se afasta sozinha
//     no tempo e as outras seguem passando.
//
//  4) O COMMIT NO FIM DO LOTE
//     As marcações do lote inteiro vão num único commit, dentro da mesma
//     transação que segura os locks. Commitar linha a linha triplica o custo.
// ════════════════════════════════════════════════════════════════════════════
public class OutboxDispatcher
{
    private readonly AppDbContext _ctx;
    private readonly IEventPublisher _publisher;
    private readonly IUnitOfWork _uow;
    private readonly ILogger<OutboxDispatcher> _log;

    /// <summary>Tamanho do lote. Grande demais segura locks por muito tempo.</summary>
    public const int TamanhoLote = 50;

    /// <summary>Depois disto a linha é considerada "presa" e vira alarme.</summary>
    public const int MaxTentativas = 10;

    public OutboxDispatcher(AppDbContext ctx, IEventPublisher publisher, IUnitOfWork uow,
                            ILogger<OutboxDispatcher> log)
    { _ctx = ctx; _publisher = publisher; _uow = uow; _log = log; }

    /// <summary>Processa um lote. Devolve quantas mensagens foram publicadas.</summary>
    public async Task<int> DespacharLoteAsync(CancellationToken ct = default)
    {
        var publicadas = 0;

        await _uow.ExecutarEmTransacaoAsync(async token =>
        {
            // ── A QUERY DO PADRÃO ───────────────────────────────────────────
            // FromSqlRaw porque 'FOR UPDATE SKIP LOCKED' não existe no LINQ.
            // ORDER BY id garante ordem de publicação = ordem de gravação.
            var pendentes = await _ctx.Outbox
                .FromSqlRaw(
                    "SELECT * FROM outbox_messages " +
                    "WHERE processado_em IS NULL AND proxima_tentativa_em <= UTC_TIMESTAMP() " +
                    "ORDER BY id LIMIT " + TamanhoLote + " FOR UPDATE SKIP LOCKED")
                .ToListAsync(token);

            if (pendentes.Count == 0) return;

            publicadas = await PublicarLoteAsync(pendentes, token);

            await _uow.CommitAsync(token);   // um commit para o lote inteiro
        }, ct);

        return publicadas;
    }

    /// <summary>
    /// A REGRA DO PADRÃO, isolada da query: publica cada linha e decide o que
    /// marcar. Fica separada (e pública) por um motivo prático — o provider
    /// InMemory dos testes não executa 'FOR UPDATE SKIP LOCKED', mas ESTA
    /// parte ele executa. Assim o teste exercita o código de produção de
    /// verdade, e não uma cópia dele escrita dentro do teste.
    /// Não dá commit: quem commita é o DespacharLoteAsync, uma vez por lote.
    /// </summary>
    public async Task<int> PublicarLoteAsync(IReadOnlyList<OutboxMessage> lote, CancellationToken ct = default)
    {
        var publicadas = 0;

        foreach (var msg in lote)
        {
            try
            {
                var envelope = new EventEnvelope(
                    msg.MessageId, msg.Tipo, msg.OcorreuEm,
                    msg.CorrelationId, msg.CausationId, msg.Payload);

                // Só retorna quando o broker confirma (publisher confirms).
                await _publisher.PublicarAsync(envelope, msg.RoutingKey, ct);

                msg.ProcessadoEm = DateTime.UtcNow;   // ← SÓ DEPOIS da confirmação
                msg.UltimoErro = null;
                publicadas++;
            }
            catch (Exception ex) when (ex is not OperationCanceledException || !ct.IsCancellationRequested)
            {
                // Falhou? A linha CONTINUA pendente (processado_em segue
                // NULL) e se afasta no tempo. O evento não se perde: ele
                // está no banco e vai ser tentado de novo. E — ponto 3 do
                // cabeçalho — as OUTRAS linhas do lote seguem sendo publicadas.
                msg.Tentativas++;
                msg.UltimoErro = Truncar(ex.Message, 1000);
                msg.ProximaTentativaEm = DateTime.UtcNow.Add(Backoff(msg.Tentativas));

                if (msg.Tentativas >= MaxTentativas)
                    _log.LogError(ex,
                        "Outbox #{Id} ({Tipo}) presa após {N} tentativas — INVESTIGAR. " +
                        "Provável payload inválido ou routing key sem fila ligada.",
                        msg.Id, msg.Tipo, msg.Tentativas);
                else
                    _log.LogWarning(ex, "Falha ao publicar outbox #{Id}; tentativa {N}, próxima em {Prox}",
                        msg.Id, msg.Tentativas, msg.ProximaTentativaEm);
            }
        }

        return publicadas;
    }

    /// <summary>
    /// Backoff exponencial com teto: 2s, 4s, 8s, 16s … até 5 min.
    /// O teto existe para a mensagem não ir para 2047 segundos de espera.
    /// (Em produção, acrescente jitter aleatório: sem ele, mil mensagens que
    ///  falharam juntas voltam juntas e derrubam o broker outra vez —
    ///  é o "thundering herd".)
    /// </summary>
    private static TimeSpan Backoff(int tentativas)
    {
        var segundos = Math.Min(Math.Pow(2, Math.Min(tentativas, 8)), 300);
        return TimeSpan.FromSeconds(segundos);
    }

    private static string Truncar(string s, int max) => s.Length <= max ? s : s[..max];

    /// <summary>
    /// MÉTRICA DE OURO DESTA ARQUITETURA: quantos eventos estão esperando.
    /// Se este número só sobe, o despachante parou ou o broker está fora —
    /// e você descobre ANTES do cliente ligar reclamando.
    /// </summary>
    public Task<int> ContarPendentesAsync(CancellationToken ct = default)
        => _ctx.Outbox.CountAsync(o => o.ProcessadoEm == null, ct);

    /// <summary>
    /// Idade do evento pendente mais antigo, em segundos (o "lag" do outbox).
    /// Alarme em produção: lag > 60s.
    /// </summary>
    public async Task<double> LagSegundosAsync(CancellationToken ct = default)
    {
        var maisAntigo = await _ctx.Outbox.Where(o => o.ProcessadoEm == null)
                                          .MinAsync(o => (DateTime?)o.CriadoEm, ct);
        return maisAntigo is null ? 0 : (DateTime.UtcNow - maisAntigo.Value).TotalSeconds;
    }
}

namespace LojaEventos.Worker;

// ════════════════════════════════════════════════════════════════════════════
//  O PROCESSO QUE FAZ O OUTBOX VIRAR MENSAGEM.
//
//  Estratégia: POLLING (consulta periódica). Simples, portável, sem
//  dependência de recurso exótico do banco. O custo é LATÊNCIA: o evento
//  espera, em média, metade do intervalo.
//
//  As alternativas, e por que não as usamos aqui:
//   • CDC / binlog (Debezium): latência de milissegundos e zero carga de
//     consulta, mas exige Kafka Connect, acesso ao binlog e muito mais infra
//     para operar. É a escolha certa em escala grande — e é demais para uma aula.
//   • LISTEN/NOTIFY: resolve bem, mas é PostgreSQL. O MySQL não tem.
//   • Publicar junto com o commit (no SaveChanges): tentador e ERRADO —
//     se o publish falha depois do commit, você volta ao dual-write.
//
//  Com 1 segundo de intervalo, o evento chega ao consumidor em ~0,5s em média.
//  Para checkout isso é mais que suficiente: o cliente já recebeu o 201.
// ════════════════════════════════════════════════════════════════════════════
public class OutboxPublisherService : BackgroundService
{
    private readonly IServiceProvider _sp;
    private readonly IConfiguration _cfg;
    private readonly ILogger<OutboxPublisherService> _log;

    public OutboxPublisherService(IServiceProvider sp, IConfiguration cfg, ILogger<OutboxPublisherService> log)
    { _sp = sp; _cfg = cfg; _log = log; }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var intervalo = TimeSpan.FromMilliseconds(_cfg.GetValue("Outbox:IntervaloMs", 1000));
        _log.LogInformation("OutboxPublisher iniciado · intervalo {Ms}ms · lote {Lote}",
            intervalo.TotalMilliseconds, OutboxDispatcher.TamanhoLote);

        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                // ── UM ESCOPO POR CICLO ─────────────────────────────────────
                // O DbContext é Scoped e NÃO é thread-safe. Um BackgroundService
                // é Singleton, então injetar AppDbContext no construtor dele é
                // um bug clássico (captive dependency): o mesmo contexto viveria
                // para sempre, acumulando entidades rastreadas até estourar a
                // memória. A regra: escopo novo a cada ciclo de trabalho.
                using var escopo = _sp.CreateScope();
                var dispatcher = escopo.ServiceProvider.GetRequiredService<OutboxDispatcher>();

                var n = await dispatcher.DespacharLoteAsync(stoppingToken);

                if (n > 0)
                {
                    _log.LogInformation("Outbox: {N} evento(s) publicado(s)", n);
                    // Lote cheio = provável backlog. Não dorme: volta direto ao
                    // trabalho para drenar a fila rápido. Sem isto, 10 mil
                    // eventos acumulados levariam 200 segundos para sair.
                    if (n >= OutboxDispatcher.TamanhoLote) continue;
                }
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                break;   // desligamento normal: não é erro
            }
            catch (Exception ex)
            {
                // NUNCA deixe a exceção escapar de ExecuteAsync: ela mata o
                // BackgroundService em silêncio e o processo continua "vivo",
                // sem publicar nada. É um dos bugs mais difíceis de notar.
                _log.LogError(ex, "Ciclo do outbox falhou; tentando de novo em {Ms}ms", intervalo.TotalMilliseconds);
            }

            try { await Task.Delay(intervalo, stoppingToken); }
            catch (OperationCanceledException) { break; }
        }

        _log.LogInformation("OutboxPublisher encerrado");
    }
}
🕒 Polling vs. CDC: usamos polling de 1 segundo — simples, portável, sem infra extra; o custo é latência de ~0,5s em média. As alternativas: CDC / binlog (Debezium) dá milissegundos e zero carga de consulta, mas exige Kafka Connect e acesso ao binlog; LISTEN/NOTIFY resolve bem, mas é PostgreSQL (o MySQL não tem). Para checkout, 0,5s é de sobra: o cliente já recebeu o 201.
⚠️ Dois erros que matam um BackgroundService em silêncio: (1) injetar AppDbContext no construtor do serviço — ele é Singleton e o DbContext é Scoped: a captive dependency vive para sempre, acumulando entidades rastreadas até estourar a memória (por isso criamos um escopo por ciclo); (2) deixar uma exceção escapar de ExecuteAsync — isso mata o serviço sem derrubar o processo, e nada no log grita: a aplicação fica "viva" e simplesmente não publica mais nada.

Backoff com jitter: o backoff aqui é exponencial com teto (2s → 4s → … → 5min). Em produção acrescente jitter aleatório: sem ele, mil mensagens que falharam juntas voltam juntas e derrubam o broker outra vez — o thundering herd.

🧩 Idempotência não é uma coisa: são três

A palavra é a mesma, mas o problema, a chave e o remédio são diferentes em cada camada. Confundi-las é o motivo mais comum de "implementei idempotência e ainda duplica".

A analogia da catraca. Camada 1 é o bilhete do passageiro: se ele passar o mesmo bilhete duas vezes, a catraca mostra "você já entrou" em vez de cobrar outra passagem. Camada 3 é a catraca registrando o número de série do bilhete: ela não confia na memória do funcionário, confia no caderno. E a camada 2 é o funcionário que, na dúvida, grita o número duas vezes — porque é melhor repetir do que esquecer.

A garantia combinada: entrega at-least-once (camada 2) + deduplicação (camada 3) = exactly-once no EFEITO. Exactly-once na entrega não existe: o broker não tem como saber se você morreu antes ou depois de processar. Quem promete exactly-once na entrega está, na prática, vendendo at-least-once + dedup.

Aprofundar: IETF — The Idempotency-Key HTTP Header Field · RFC 9110 §9.2.2 — Idempotent Methods · Richardson — Idempotent Consumer.

7Camada 1 — POST idempotente com Idempotency-Key

O contrato que a API passa a oferecer:

SituaçãoStatusCorpoCabeçalho
sem Idempotency-Key400problem+json explicando—
chave nova201o pedido criadoLocation · Idempotent-Replay: false
mesma chave, mesmo corpo200a mesma resposta de antesIdempotent-Replay: true
mesma chave, corpo diferente422problem+json: chave reutilizada — gere outra—
mesma chave, mesmo corpo, ao mesmo tempo (corrida)200a perdedora leva erro 1062 no commit e devolve a resposta da vencedoraIdempotent-Replay: true

Por que 200 no replay e não 201? Porque 201 Created afirma "acabei de criar um recurso" — e no replay nada foi criado. Devolver 201 faria o cliente achar que criou dois pedidos. (Alguns provedores devolvem 201 mesmo no replay; o essencial é documentar e ser consistente, e o cabeçalho Idempotent-Replay remove toda a ambiguidade.)

Por que guardar o hash do corpo? Porque "mesma chave, corpo diferente" é um bug do cliente (reaproveitou a chave para outra compra). Devolver a resposta antiga ali seria confirmar um pedido que nunca existiu.

Por que 422 e não 409? É a recomendação do draft da IETF "The Idempotency-Key HTTP Header Field": 422 quando a chave já pertence a outra operação (repetir não adianta — gere uma chave nova) e 409 quando a mesma operação ainda está em andamento (repetir daqui a pouco resolve). Nesta aba o 409 quase nunca aparece: como a chave é gravada na mesma transação do pedido, o MySQL faz a requisição perdedora esperar a vencedora terminar e só então acusa a chave duplicada — e aí a resposta da vencedora já existe para ser devolvida. O 409 fica como rede de segurança para o caso raro de a resposta não ser encontrada.

namespace LojaEventos.Application.Ports;

/// <summary>Veredito sobre uma Idempotency-Key recebida.</summary>
public enum ResultadoIdempotencia
{
    /// <summary>Chave nunca vista: processe a requisição normalmente.</summary>
    Novo,
    /// <summary>Chave já concluída com o MESMO corpo: devolva a resposta guardada.</summary>
    Replay,
    /// <summary>Chave já usada com um corpo DIFERENTE: erro do cliente → 422.</summary>
    ConflitoDeCorpo
}

public sealed record RespostaGuardada(int StatusCode, string Corpo);

// ════════════════════════════════════════════════════════════════════════════
//  PORTA DA IDEMPOTÊNCIA HTTP (camada 1 das três desta aba).
//
//  O problema concreto: o cliente manda POST /api/pedidos, a rede cai antes da
//  resposta voltar, e o app dele tenta de novo. Sem chave de idempotência você
//  acabou de criar DOIS pedidos idênticos e cobrar o cliente duas vezes.
//  Nenhum cuidado do lado do cliente resolve isso: a correção é do SERVIDOR.
//
//  Por que guardar o HASH DO CORPO e não só a chave?
//  Porque "mesma chave, corpo diferente" é um BUG do cliente (ele reaproveitou
//  a chave para outra compra). Devolver a resposta antiga ali seria confirmar
//  um pedido que nunca foi criado. Por isso: 422, explicitamente
//  (é o status que o draft da IETF sobre Idempotency-Key recomenda).
//
//  ┌─ POR QUE NÃO EXISTE UM ESTADO "EM ANDAMENTO" AQUI ──────────────────────┐
//  │ Muitas implementações gravam a chave como EM_ANDAMENTO, processam, e só  │
//  │ depois marcam CONCLUÍDO. Isso exige DUAS gravações — e se o processo cai │
//  │ no meio, a chave fica travada para sempre, obrigando um job de limpeza.  │
//  │                                                                         │
//  │ Aqui a chave é gravada UMA vez, já com a resposta, dentro da MESMA       │
//  │ transação do pedido. Ou tudo existe, ou nada existe — nunca uma chave    │
//  │ órfã. O preço: duas requisições simultâneas com a mesma chave podem      │
//  │ ambas passar pelo 'ConsultarAsync' e tentar gravar. Quem perde a corrida │
//  │ leva erro de chave duplicada do MySQL — e nós traduzimos isso em Replay  │
//  │ (ver 'EhChaveDuplicada' + o catch no PedidoService). A chave primária    │
//  │ única é a ÚNICA exclusão mútua realmente confiável que temos.            │
//  └─────────────────────────────────────────────────────────────────────────┘
// ════════════════════════════════════════════════════════════════════════════
public interface IIdempotencyStore
{
    /// <summary>Consulta o veredito (sem gravar nada).</summary>
    Task<(ResultadoIdempotencia Resultado, RespostaGuardada? Guardada)> ConsultarAsync(
        string chave, string hashCorpo, CancellationToken ct = default);

    /// <summary>
    /// Enfileira a gravação da chave + resposta na Unit of Work em curso.
    /// NÃO dá commit: quem commita é o caso de uso, junto com o agregado e o
    /// outbox. É essa união que torna a idempotência confiável.
    /// </summary>
    Task RegistrarAsync(string chave, string rota, string hashCorpo,
                        int statusCode, string corpoResposta, CancellationToken ct = default);

    /// <summary>
    /// true se a exceção for violação de chave única (MySQL 1062).
    /// Fica na porta porque só o adapter conhece o código de erro do banco —
    /// o caso de uso não pode depender de MySqlException.
    /// </summary>
    bool EhChaveDuplicada(Exception ex);
}

using LojaEventos.Application.Ports;
using LojaEventos.Infrastructure.Data;
using Microsoft.EntityFrameworkCore;
using MySqlConnector;

namespace LojaEventos.Infrastructure.Idempotency;

public class EfIdempotencyStore : IIdempotencyStore
{
    /// <summary>Janela de validade da chave. Maior que o retry mais longo do cliente.</summary>
    private static readonly TimeSpan Validade = TimeSpan.FromHours(24);

    private readonly AppDbContext _ctx;
    public EfIdempotencyStore(AppDbContext ctx) { _ctx = ctx; }

    public async Task<(ResultadoIdempotencia, RespostaGuardada?)> ConsultarAsync(
        string chave, string hashCorpo, CancellationToken ct = default)
    {
        var reg = await _ctx.Idempotencia.AsNoTracking()
                            .FirstOrDefaultAsync(i => i.Chave == chave, ct);

        if (reg is null) return (ResultadoIdempotencia.Novo, null);

        // Expirada vale como inexistente: o cliente pode reusar a chave depois
        // da janela. (O DELETE da limpeza pode ainda não ter rodado.)
        if (reg.ExpiraEm <= DateTime.UtcNow) return (ResultadoIdempotencia.Novo, null);

        // Comparação em tempo constante não é necessária aqui (não é segredo),
        // mas a comparação precisa ser ordinal: 'a' != 'A' num hash hex.
        if (!string.Equals(reg.HashCorpo, hashCorpo, StringComparison.Ordinal))
            return (ResultadoIdempotencia.ConflitoDeCorpo, null);

        return (ResultadoIdempotencia.Replay, new RespostaGuardada(reg.StatusCode, reg.CorpoResposta));
    }

    public async Task RegistrarAsync(string chave, string rota, string hashCorpo,
                                     int statusCode, string corpoResposta, CancellationToken ct = default)
    {
        var agora = DateTime.UtcNow;
        await _ctx.Idempotencia.AddAsync(new IdempotencyRecord
        {
            Chave = chave,
            Rota = rota,
            HashCorpo = hashCorpo,
            StatusCode = statusCode,
            CorpoResposta = corpoResposta,
            CriadoEm = agora,
            ExpiraEm = agora.Add(Validade)
        }, ct);
        // Sem SaveChanges de propósito: a gravação entra no commit do caso de uso.
    }

    /// <summary>
    /// MySQL devolve o erro 1062 ("Duplicate entry ... for key") quando duas
    /// requisições concorrentes tentam gravar a MESMA Idempotency-Key. O EF
    /// embrulha isso numa DbUpdateException, então precisamos olhar a inner.
    /// </summary>
    public bool EhChaveDuplicada(Exception ex)
    {
        for (Exception? e = ex; e is not null; e = e.InnerException)
            if (e is MySqlException my &&
                (my.Number == 1062 || my.ErrorCode == MySqlErrorCode.DuplicateKeyEntry))
                return true;
        return false;
    }
}

🧮 O hash tem que ser CANÔNICO. Se você hashear o JSON cru, a mesma compra com os campos em outra ordem gera hash diferente → a API devolve 422 numa repetição legítima e o cliente não consegue comprar. Por isso CalcularHash normaliza o e-mail (trim + minúsculas) e ordena os itens por produtoId antes de hashear. Há 6 testes só para travar isso (IdempotenciaHashTests).
⚠️ Por que NÃO existe um estado "EM_ANDAMENTO" aqui. A implementação comum grava a chave como em andamento, processa, e depois marca concluído — duas gravações. Se o processo cai no meio, a chave fica travada para sempre e você precisa de um job de limpeza. Nesta aba a chave é gravada uma vez, já com a resposta, dentro da transação do pedido: ou tudo existe, ou nada existe. O preço: duas requisições simultâneas com a mesma chave podem ambas passar pela consulta — e quem perde a corrida leva erro 1062 (chave duplicada) do MySQL, que o caso de uso traduz em replay. A chave primária única é a única exclusão mútua realmente confiável que você tem.
⚠️ E um filtro/middleware de idempotência resolveria? Não sozinho. Um filtro roda fora da transação do caso de uso, então existe uma janela em que a chave já foi gravada e o pedido ainda não (ou o contrário). Filtro serve para o caminho rápido (devolver replay sem tocar no domínio); a gravação atômica tem que estar dentro do caso de uso.

8Camada 3 — o Inbox do consumidor

O RabbitMQ entrega at-least-once: se o consumidor processa e morre antes do ACK, o broker reentrega — e está certo, porque do ponto de vista dele você pode ter morrido antes de processar. Ele não tem como saber.

A solução: antes de agir, gravar o message_id numa tabela com chave única, na mesma transação do efeito. Se a gravação falha por duplicidade, já foi processado → ACK e segue.

LojaEventos.Application/Ports/IInbox.cs 
namespace LojaEventos.Application.Ports;

// ════════════════════════════════════════════════════════════════════════════
//  PORTA DO INBOX (camada 3 das três idempotências).
//
//  O RabbitMQ entrega AT-LEAST-ONCE: se o seu consumidor processa a mensagem e
//  morre antes de mandar o ACK, o broker reentrega — e está certo em fazer
//  isso, porque do ponto de vista dele você pode ter morrido ANTES de
//  processar. O broker não tem como saber. Logo:
//
//     exactly-once na ENTREGA não existe;
//     exactly-once no EFEITO existe, e se chama inbox (ou dedup store).
//
//  Como funciona: antes de agir, o consumidor tenta gravar o MessageId numa
//  tabela com chave primária única. Se a gravação falha por duplicidade, a
//  mensagem já foi processada → ACK e segue a vida. A gravação acontece na
//  MESMA transação do efeito, senão você volta a ter dois sistemas e o mesmo
//  buraco de antes, só mudado de lugar.
// ════════════════════════════════════════════════════════════════════════════
public interface IInbox
{
    /// <summary>
    /// true  = mensagem nova, pode processar (a marca já está na transação);
    /// false = já processada antes, apenas confirme (ACK) e ignore.
    /// </summary>

namespace LojaEventos.Infrastructure.Messaging;

// ════════════════════════════════════════════════════════════════════════════
//  TOPOLOGIA — o desenho das filas. Declarada em CÓDIGO, no boot, e sempre de
//  forma IDEMPOTENTE: 'ExchangeDeclare'/'QueueDeclare' no RabbitMQ não dão
//  erro se o objeto já existe (só se existir com argumentos DIFERENTES).
//  Por isso criar topologia na mão pela UI é péssima prática: no próximo
//  ambiente ninguém lembra o que foi clicado.
//
//  ┌─ O DESENHO ─────────────────────────────────────────────────────────────┐
//  │                         exchange "loja.eventos" (topic)                 │
//  │                                     │                                   │
//  │       routing key "pedidos.pedido-criado.v1"  → fan-out para quem ouve  │
//  │                     ├──────────────────────────┬──────────────────────┐ │
//  │              estoque.pedido-criado    notificacao.pedido-criado        │ │
//  │                     │                          │                       │ │
//  │              falhou? republica em        falhou? idem                   │ │
//  │              estoque.retry.10s → 1m → 10m   (TTL expira e a mensagem   │ │
//  │                     │                        volta pela routing key    │ │
//  │              esgotou? estoque.dlq            "reentrega.<consumidor>") │ │
//  └─────────────────────────────────────────────────────────────────────────┘
//
//  POR QUE RETRY COM FILA DE TTL, E NÃO 'nack(requeue: true)'?
//  Porque 'requeue: true' devolve a mensagem para a FRENTE da fila
//  IMEDIATAMENTE. Se a causa da falha é o banco estar fora, você entra num
//  laço fechado consumindo 100% de CPU e enchendo o log — o famoso
//  "requeue loop". A fila de TTL faz a mensagem ESPERAR sem ocupar ninguém.
//
//  POR QUE TRÊS FILAS DE TTL EM VEZ DE UMA?
//  Porque TTL no RabbitMQ é por FILA. Backoff exponencial (10s → 1m → 10m)
//  precisa de uma fila por degrau. A alternativa é TTL por mensagem
//  ('props.Expiration'), mas ela tem head-of-line blocking: uma mensagem de
//  10 minutos na frente segura todas as de 10 segundos atrás dela.
//  (Na vida real: plugin rabbitmq_delayed_message_exchange resolve isso.)
// ════════════════════════════════════════════════════════════════════════════
public static class RabbitMqTopology
{
    /// <summary>Consumidores que ouvem o evento de pedido criado.</summary>
    public static readonly string[] Consumidores = { "estoque", "notificacao" };

    public const string EventoPedidoCriado = "pedidos.pedido-criado.v1";

    /// <summary>Degraus do backoff: nome do sufixo → TTL em milissegundos.</summary>
    public static readonly (string Sufixo, int TtlMs)[] Degraus =
    {
        ("retry.10s", 10_000),
        ("retry.1m",  60_000),
        ("retry.10m", 600_000)
    };

    public static string FilaPrincipal(string consumidor) => $"{consumidor}.pedido-criado";
    public static string FilaRetry(string consumidor, int tentativa)
        => $"{consumidor}.{Degraus[Math.Min(tentativa, Degraus.Length - 1)].Sufixo}";
    public static string FilaDlq(string consumidor) => $"{consumidor}.dlq";
    public static string ChaveReentrega(string consumidor) => $"reentrega.{consumidor}";

    public static async Task DeclararAsync(IChannel ch, string exchange, CancellationToken ct = default)
    {
        // durable: true → a definição do exchange sobrevive a um restart do broker.
        await ch.ExchangeDeclareAsync(exchange, ExchangeType.Topic,
            durable: true, autoDelete: false, cancellationToken: ct);

        foreach (var c in Consumidores)
        {
            var principal = FilaPrincipal(c);

            // durable: true    → a FILA sobrevive ao restart
            // (mensagem persistente + fila durável + publisher confirm = a
            //  tríade mínima para "não perdi a mensagem". Faltando um dos três,
            //  o RabbitMQ descarta sem avisar e você só descobre em produção.)
            await ch.QueueDeclareAsync(principal, durable: true, exclusive: false,
                autoDelete: false, cancellationToken: ct);

            // Bind 1: recebe o evento original.
            await ch.QueueBindAsync(principal, exchange, EventoPedidoCriado, cancellationToken: ct);
            // Bind 2: recebe as REENTREGAS vindas das filas de retry — chave
            // privada deste consumidor, para o retry do estoque não acordar o
            // consumidor de notificação de novo.
            await ch.QueueBindAsync(principal, exchange, ChaveReentrega(c), cancellationToken: ct);

            foreach (var (sufixo, ttl) in Degraus)
            {
                await ch.QueueDeclareAsync($"{c}.{sufixo}", durable: true, exclusive: false,
                    autoDelete: false,
                    arguments: new Dictionary<string, object?>
                    {
                        // Quando o TTL expira, o RabbitMQ "dead-letter" a mensagem
                        // para este exchange/chave — que é o bind 2 acima.
                        ["x-message-ttl"] = ttl,
                        ["x-dead-letter-exchange"] = exchange,
                        ["x-dead-letter-routing-key"] = ChaveReentrega(c)
                    }, cancellationToken: ct);
            }

            // DLQ = estacionamento. Mensagem aqui NÃO volta sozinha: alguém
            // precisa olhar, entender e reprocessar na mão. Fila de DLQ com
            // profundidade > 0 é alarme de plantão, não é "normal".
            await ch.QueueDeclareAsync(FilaDlq(c), durable: true, exclusive: false,
                autoDelete: false, cancellationToken: ct);
        }
    }
}

using Microsoft.Extensions.Logging;
using Microsoft.Extensions.Options;
using RabbitMQ.Client;

namespace LojaEventos.Infrastructure.Messaging;

// ════════════════════════════════════════════════════════════════════════════
//  CONEXÃO COMPARTILHADA (Singleton).
//
//  Regra de ouro do RabbitMQ: conexão TCP é CARA, canal (IChannel) é BARATO.
//  Uma conexão por processo, um canal por thread/tarefa. Abrir conexão por
//  mensagem é o erro de performance nº 1 de quem começa — e ele só aparece
//  sob carga, quando o broker recusa novas conexões.
//
//  'AutomaticRecoveryEnabled' faz o cliente reconectar e REDECLARAR a
//  topologia sozinho quando o broker volta. Sem isso, um restart do RabbitMQ
//  deixa seu worker vivo mas surdo — e nada no log grita.
// ════════════════════════════════════════════════════════════════════════════
public sealed class RabbitMqConnection : IAsyncDisposable
{
    private readonly RabbitMqOptions _opt;
    private readonly ILogger<RabbitMqConnection> _log;
    private readonly SemaphoreSlim _lock = new(1, 1);
    private IConnection? _conn;

    public RabbitMqConnection(IOptions<RabbitMqOptions> opt, ILogger<RabbitMqConnection> log)
    { _opt = opt.Value; _log = log; }

    public async Task<IConnection> ObterAsync(CancellationToken ct = default)
    {
        if (_conn is { IsOpen: true }) return _conn;

        await _lock.WaitAsync(ct);
        try
        {
            if (_conn is { IsOpen: true }) return _conn;

            var factory = new ConnectionFactory
            {
                Uri = new Uri(_opt.Uri),
                ClientProvidedName = _opt.NomeCliente,
                AutomaticRecoveryEnabled = true,
                TopologyRecoveryEnabled = true,
                NetworkRecoveryInterval = TimeSpan.FromSeconds(5)
            };

            _conn = await factory.CreateConnectionAsync(ct);
            _log.LogInformation("Conectado ao RabbitMQ como {Nome}", _opt.NomeCliente);
            return _conn;
        }
        finally { _lock.Release(); }
    }

    /// <summary>Abre um canal e garante a topologia declarada.</summary>
    public async Task<IChannel> AbrirCanalAsync(bool comConfirmacao, CancellationToken ct = default)
    {
        var conn = await ObterAsync(ct);

        // ── PUBLISHER CONFIRMS ──────────────────────────────────────────────
        // Com 'publisherConfirmationsEnabled', 'BasicPublishAsync' só retorna
        // depois que o BROKER confirmou que gravou a mensagem. Sem isso, o
        // publish é "fire and forget": retorna na hora, e se o broker cair no
        // mesmo instante, a mensagem evaporou — e o outbox já teria marcado a
        // linha como processada. Você perdeu o evento achando que entregou.
        var opcoes = comConfirmacao
            ? new CreateChannelOptions(publisherConfirmationsEnabled: true,
                                       publisherConfirmationTrackingEnabled: true)
            : new CreateChannelOptions(publisherConfirmationsEnabled: false,
                                       publisherConfirmationTrackingEnabled: false);

        var ch = await conn.CreateChannelAsync(opcoes, ct);
        await RabbitMqTopology.DeclararAsync(ch, _opt.Exchange, ct);
        return ch;
    }

    public async ValueTask DisposeAsync()
    {
        if (_conn is not null) await _conn.DisposeAsync();
        _lock.Dispose();
    }
}

// ════════════════════════════════════════════════════════════════════════════
//  ADAPTER DE PUBLICAÇÃO. Único lugar do sistema que conhece o RabbitMQ para
//  escrever. Trocar por Kafka = escrever outra classe que implementa
//  IEventPublisher e mudar uma linha no DI. Nada mais.
// ════════════════════════════════════════════════════════════════════════════
public sealed class RabbitMqEventPublisher : IEventPublisher, IAsyncDisposable
{
    private readonly RabbitMqConnection _conexao;
    private readonly RabbitMqOptions _opt;
    private readonly ILogger<RabbitMqEventPublisher> _log;
    private readonly SemaphoreSlim _lock = new(1, 1);
    private IChannel? _canal;

    public RabbitMqEventPublisher(RabbitMqConnection conexao, IOptions<RabbitMqOptions> opt,
                                  ILogger<RabbitMqEventPublisher> log)
    { _conexao = conexao; _opt = opt.Value; _log = log; }

    public async Task PublicarAsync(EventEnvelope envelope, string routingKey, CancellationToken ct = default)
    {
        var canal = await ObterCanalAsync(ct);

        var props = new BasicProperties
        {
            // MessageId no PROTOCOLO, não só no JSON: assim quem for depurar
            // enxerga a chave de deduplicação direto na UI do RabbitMQ, sem
            // precisar abrir o payload.
            MessageId = envelope.MessageId.ToString(),
            CorrelationId = envelope.CorrelationId,
            Type = envelope.Tipo,
            ContentType = "application/json",
            ContentEncoding = "utf-8",
            Timestamp = new AmqpTimestamp(new DateTimeOffset(envelope.OcorreuEm, TimeSpan.Zero).ToUnixTimeSeconds()),

            // Persistent = true → o broker grava a mensagem em disco.
            // Sem isto, um restart do RabbitMQ apaga tudo o que estava na fila,
            // mesmo que a fila seja durável. Fila durável guarda a FILA;
            // Persistent guarda a MENSAGEM. São duas coisas diferentes.
            Persistent = true,

            Headers = new Dictionary<string, object?>
            {
                ["x-tentativas"] = 0,
                ["x-causation-id"] = envelope.CausationId
            }
        };

        var corpo = Encoding.UTF8.GetBytes(JsonEnvelope(envelope));

        // mandatory: true → se NENHUMA fila estiver ligada a esta routing key,
        // o broker devolve a mensagem em vez de descartá-la em silêncio.
        // Sem 'mandatory', um bind escrito errado faz os eventos desaparecerem
        // e tudo "funciona" — até alguém notar que o estoque nunca baixa.
        await canal.BasicPublishAsync(
            exchange: _opt.Exchange,
            routingKey: routingKey,
            mandatory: true,
            basicProperties: props,
            body: corpo,
            cancellationToken: ct);

        // Se chegamos aqui sem exceção, o broker CONFIRMOU. Só agora o
        // despachante do outbox tem direito de marcar a linha como processada.
        _log.LogDebug("Publicado {Tipo} ({MessageId}) em {Exchange}/{Key}",
            envelope.Tipo, envelope.MessageId, _opt.Exchange, routingKey);
    }

    /// <summary>O envelope inteiro vai no corpo: metadado + payload juntos.</summary>
    private static string JsonEnvelope(EventEnvelope e) =>
        System.Text.Json.JsonSerializer.Serialize(e, EventEnvelope.Json);

    private async Task<IChannel> ObterCanalAsync(CancellationToken ct)
    {
        if (_canal is { IsOpen: true }) return _canal;
        await _lock.WaitAsync(ct);
        try
        {
            if (_canal is { IsOpen: true }) return _canal;
            _canal = await _conexao.AbrirCanalAsync(comConfirmacao: true, ct);
            return _canal;
        }
        finally { _lock.Release(); }
    }

    public async ValueTask DisposeAsync()
    {
        if (_canal is not null) await _canal.DisposeAsync();
        _lock.Dispose();
    }
}

📐 D-21 Arquitetura — Topologia: exchange, filas, retry escalonado e DLQ

🚫 Por que retry com fila de TTL e não nack(requeue: true)

BasicNack(requeue: true) devolve a mensagem para a frente da fila, imediatamente. Se a causa da falha é o banco estar fora, você entra num laço fechado: consome 100% de CPU, enche o log com milhares de linhas por segundo e não deixa nenhuma outra mensagem passar. É o requeue loop, e é o erro nº 1 de quem começa com RabbitMQ.

A fila de TTL faz a mensagem esperar sem ocupar ninguém: ela fica parada 10s, o TTL expira, o broker a dead-letter de volta para o exchange e ela volta para o consumidor.

E por que três filas de TTL? Porque TTL no RabbitMQ é por fila. Backoff exponencial (10s → 1m → 10m) precisa de uma fila por degrau. A alternativa — TTL por mensagem (props.Expiration) — tem head-of-line blocking: uma mensagem de 10 minutos na frente segura todas as de 10 segundos atrás dela. Em produção, o plugin rabbitmq_delayed_message_exchange resolve isso com um exchange só.

⚠️ A tríade "não perdi a mensagem" — faltando UM dos três, o RabbitMQ descarta em silêncio: (1) durable: true na fila (sobrevive ao restart do broker); (2) Persistent = true na mensagem (é gravada em disco) — fila durável guarda a fila, Persistent guarda a mensagem, são coisas diferentes; (3) publisher confirms (você só sabe que chegou quando o broker confirma). Sem o (3), o publish é fire and forget: retorna na hora, e se o broker cair no mesmo instante a mensagem evaporou — e o outbox já teria marcado a linha como processada. Você perdeu o evento achando que entregou.
📭 mandatory: true: se nenhuma fila estiver ligada à routing key, o broker devolve a mensagem em vez de descartá-la calado. Sem mandatory, um QueueBind escrito errado faz os eventos desaparecerem e tudo parece funcionar — até alguém notar, semanas depois, que o estoque nunca baixa.

10O consumidor: o roteiro de 7 passos

Todo consumidor repete o mesmo roteiro. Em vez de copiá-lo, extraímos para uma base — um bug corrigido ali corrige todos:

  1. Desserializar o envelope. Falhou? A mensagem é venenosa (poison message): nenhum retry conserta um JSON quebrado. Vai direto para a DLQ. Retentar veneno é o jeito mais fácil de travar uma fila para sempre.
  2. Checar a versão do contrato. Versão desconhecida também não melhora com retry → DLQ com log claro. É isto que permite publicar .v2 antes de todos os consumidores estarem atualizados.
  3. Abrir escopo de DI. Um escopo por mensagem (DbContext é Scoped; o consumidor é Singleton).
  4. Transação: marcar no Inbox + executar o efeito. Juntos, no mesmo commit.
  5. ACK. Só depois do commit. autoAck: true é o erro clássico: o broker esquece a mensagem e, se o processamento falhar, ela não existe mais em lugar nenhum.
  6. Falha técnica → fila de retry com x-tentativas incrementado.
  7. Tentativas esgotadas → DLQ e alarme.

// ════════════════════════════════════════════════════════════════════════════
//  BASE DE TODO CONSUMIDOR — o roteiro de 7 passos que você repetiria em cada
//  consumidor, extraído para um lugar só (DRY + um bug corrigido corrige todos).
//
//  Os 7 passos, em ordem, e o porquê de cada um:
//
//  1. DESSERIALIZAR O ENVELOPE
//     Se falhar aqui a mensagem é VENENOSA (poison message): nenhuma
//     quantidade de retry vai consertar um JSON quebrado. Vai direto para a
//     DLQ. Retentar veneno é o jeito mais fácil de travar uma fila para sempre.
//
//  2. CHECAR A VERSÃO DO CONTRATO
//     Versão desconhecida (v2 chegando num consumidor que só sabe v1) também
//     não melhora com retry: DLQ, com log claro. Isto é o que permite
//     publicar v2 antes de todos os consumidores estarem atualizados.
//
//  3. ABRIR ESCOPO DE DI
//     DbContext é Scoped; o consumidor é Singleton. Um escopo por MENSAGEM.
//
//  4. TRANSAÇÃO: MARCAR NO INBOX + EXECUTAR O EFEITO
//     Juntos, no mesmo commit. Se separados, uma queda no meio deixa a marca
//     sem o efeito (perda) ou o efeito sem a marca (duplicação).
//
//  5. ACK
//     Só depois do commit. ACK antes de processar ("autoAck") é o erro
//     clássico: o broker esquece a mensagem e, se o processamento falhar, ela
//     não existe mais em lugar nenhum.
//
//  6. FALHA TRANSITÓRIA → REPUBLICAR NA FILA DE RETRY
//     Com 'x-tentativas' incrementado e ACK na original.
//
//  7. TENTATIVAS ESGOTADAS → DLQ
//     E alarme. DLQ não é lixeira: é caixa de entrada do plantão.
// ════════════════════════════════════════════════════════════════════════════
public abstract class ConsumidorBase : BackgroundService
{
    private readonly RabbitMqConnection _conexao;
    private readonly IServiceProvider _sp;
    protected readonly RabbitMqOptions Opcoes;
    protected readonly ILogger Log;

    /// <summary>Nome lógico — vira nome de fila e chave do inbox.</summary>
    protected abstract string NomeConsumidor { get; }

    /// <summary>Maior versão do contrato que este consumidor sabe ler.</summary>
    protected virtual int VersaoMaximaSuportada => 1;

    protected ConsumidorBase(RabbitMqConnection conexao, IServiceProvider sp,
                             IOptions<RabbitMqOptions> opcoes, ILogger log)
    { _conexao = conexao; _sp = sp; Opcoes = opcoes.Value; Log = log; }

    /// <summary>O efeito de negócio. Roda DENTRO da transação do inbox.</summary>
    protected abstract Task ProcessarAsync(EventEnvelope envelope, IServiceProvider escopo, CancellationToken ct);

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var fila = RabbitMqTopology.FilaPrincipal(NomeConsumidor);

        // Espera o broker subir. Em docker compose a ordem de boot não é
        // garantida, e 'depends_on' sozinho não espera o RabbitMQ estar PRONTO
        // (só criado). Tentar com paciência é mais robusto que depender disso.
        IChannel canal = null!;
        for (var tentativa = 1; ; tentativa++)
        {
            try { canal = await _conexao.AbrirCanalAsync(comConfirmacao: true, stoppingToken); break; }
            catch (Exception ex) when (tentativa <= 30 && !stoppingToken.IsCancellationRequested)
            {
                Log.LogWarning("RabbitMQ indisponível (tentativa {N}): {Msg}", tentativa, ex.Message);
                await Task.Delay(TimeSpan.FromSeconds(2), stoppingToken);
            }
        }

        // ── QoS / PREFETCH ─────────────────────────────────────────────────
        // Sem prefetch, o broker empurra a fila INTEIRA para o primeiro
        // consumidor que conectar. Com 3 réplicas, duas ficam ociosas e uma
        // afoga. prefetchCount limita quantas mensagens não confirmadas cada
        // consumidor segura — é o balanceamento de carga do RabbitMQ.
        await canal.BasicQosAsync(prefetchSize: 0, prefetchCount: Opcoes.Prefetch, global: false, stoppingToken);

        var consumer = new AsyncEventingBasicConsumer(canal);
        consumer.ReceivedAsync += (_, ea) => TratarAsync(canal, ea, stoppingToken);

        // autoAck: FALSE. Nunca true em consumidor que faz trabalho real.
        await canal.BasicConsumeAsync(fila, autoAck: false, consumer: consumer, cancellationToken: stoppingToken);

        Log.LogInformation("Consumidor '{Nome}' ouvindo a fila {Fila} (prefetch {P})",
            NomeConsumidor, fila, Opcoes.Prefetch);

        // O consumo é orientado a evento (callback). Este Delay só mantém o
        // BackgroundService vivo até o host pedir para parar.
        try { await Task.Delay(Timeout.Infinite, stoppingToken); }
        catch (OperationCanceledException) { /* desligamento normal */ }
    }

    private async Task TratarAsync(IChannel canal, BasicDeliverEventArgs ea, CancellationToken ct)
    {
        var tentativas = LerTentativas(ea);
        EventEnvelope? envelope = null;

        // ── PASSO 1: desserializar ──────────────────────────────────────────
        try
        {
            var json = Encoding.UTF8.GetString(ea.Body.Span);
            envelope = JsonSerializer.Deserialize<EventEnvelope>(json, EventEnvelope.Json);
        }
        catch (Exception ex)
        {
            Log.LogError(ex, "[{Nome}] Mensagem ilegível — enviando direto para a DLQ", NomeConsumidor);
            await ParaDlqAsync(canal, ea, "payload ilegível", ct);
            return;
        }

        if (envelope is null)
        {
            await ParaDlqAsync(canal, ea, "envelope nulo", ct);
            return;
        }

        // ── PASSO 2: versão do contrato ─────────────────────────────────────
        if (envelope.Versao > VersaoMaximaSuportada)
        {
            Log.LogError("[{Nome}] Evento {Tipo} é v{V}, suporto até v{Max} — DLQ. " +
                         "Atualize este consumidor antes de reprocessar.",
                         NomeConsumidor, envelope.Tipo, envelope.Versao, VersaoMaximaSuportada);
            await ParaDlqAsync(canal, ea, "versão não suportada", ct);
            return;
        }

        try
        {
            // ── PASSO 3: escopo de DI por mensagem ──────────────────────────
            using var escopo = _sp.CreateScope();
            var inbox = escopo.ServiceProvider.GetRequiredService<IInbox>();
            var uow = escopo.ServiceProvider.GetRequiredService<IUnitOfWork>();
            var idem = escopo.ServiceProvider.GetRequiredService<IIdempotencyStore>();

            var processou = false;

            try
            {
                // ── PASSO 4: inbox + efeito, na MESMA transação ─────────────
                await uow.ExecutarEmTransacaoAsync(async token =>
                {
                    if (!await inbox.TentarMarcarAsync(envelope.MessageId, NomeConsumidor, token))
                    {
                        // Já processada. Não é erro — é o at-least-once
                        // funcionando como previsto. Aqui está a prova de que
                        // o inbox vale: sem ele, o estoque baixaria 2x.
                        Log.LogInformation("[{Nome}] Mensagem {Id} já processada — ignorando (dedup)",
                            NomeConsumidor, envelope.MessageId);
                        return;
                    }

                    await ProcessarAsync(envelope, escopo.ServiceProvider, token);
                    await uow.CommitAsync(token);
                    processou = true;
                }, ct);
            }
            catch (Exception ex) when (idem.EhChaveDuplicada(ex))
            {
                // Duas réplicas do worker pegaram a MESMA mensagem (pode
                // acontecer numa reentrega durante o restart). A chave
                // primária composta do inbox barrou a segunda — que é
                // exatamente o comportamento desejado.
                Log.LogInformation("[{Nome}] Corrida no inbox para {Id} — outra réplica processou",
                    NomeConsumidor, envelope.MessageId);
            }

            // ── PASSO 5: ACK ────────────────────────────────────────────────
            await canal.BasicAckAsync(ea.DeliveryTag, multiple: false, ct);

            if (processou)
                Log.LogInformation("[{Nome}] {Tipo} processado · msg {Id} · correlation {Corr}",
                    NomeConsumidor, envelope.Tipo, envelope.MessageId, envelope.CorrelationId);
        }
        catch (Exception ex)
        {
            // ── PASSOS 6 e 7: retry com backoff, depois DLQ ─────────────────
            if (tentativas + 1 >= Opcoes.MaxTentativas)
            {
                Log.LogError(ex, "[{Nome}] Esgotou {N} tentativas para a msg {Id} — DLQ",
                    NomeConsumidor, Opcoes.MaxTentativas, envelope.MessageId);
                await ParaDlqAsync(canal, ea, ex.Message, ct);
            }
            else
            {
                var fila = RabbitMqTopology.FilaRetry(NomeConsumidor, tentativas);
                Log.LogWarning(ex, "[{Nome}] Falha na msg {Id}; tentativa {N} → fila {Fila}",
                    NomeConsumidor, envelope.MessageId, tentativas + 1, fila);
                await RepublicarAsync(canal, ea, fila, tentativas + 1, ex.Message, ct);
            }
        }
    }

    /// <summary>
    /// Republica numa fila de espera. Publicar no exchange DEFAULT ("") com
    /// routingKey = nome da fila entrega direto nela, sem precisar de bind.
    /// Depois do ACK, a mensagem original deixa de existir e só resta a copiada.
    /// </summary>
    private async Task RepublicarAsync(IChannel canal, BasicDeliverEventArgs ea, string fila,
                                       int tentativas, string erro, CancellationToken ct)
    {
        var props = ClonarProps(ea, tentativas, erro);
        await canal.BasicPublishAsync("", fila, mandatory: true, basicProperties: props,
                                      body: ea.Body.ToArray(), cancellationToken: ct);
        await canal.BasicAckAsync(ea.DeliveryTag, multiple: false, ct);
    }

    private async Task ParaDlqAsync(IChannel canal, BasicDeliverEventArgs ea, string motivo, CancellationToken ct)
    {
        var props = ClonarProps(ea, LerTentativas(ea), motivo);
        await canal.BasicPublishAsync("", RabbitMqTopology.FilaDlq(NomeConsumidor),
                                      mandatory: true, basicProperties: props,
                                      body: ea.Body.ToArray(), cancellationToken: ct);
        await canal.BasicAckAsync(ea.DeliveryTag, multiple: false, ct);
    }

    /// <summary>
    /// Copia as propriedades originais e carimba o diagnóstico. Preservar
    /// MessageId é VITAL: é por ele que o inbox deduplica. Se a republicação
    /// gerasse um id novo, o retry viraria duplicação de efeito.
    /// </summary>
    private static BasicProperties ClonarProps(BasicDeliverEventArgs ea, int tentativas, string erro)
    {
        var cabecalhos = new Dictionary<string, object?>
        {
            ["x-tentativas"] = tentativas,
            ["x-ultimo-erro"] = erro.Length > 400 ? erro[..400] : erro,
            ["x-falhou-em"] = DateTime.UtcNow.ToString("O")
        };

        return new BasicProperties
        {
            MessageId = ea.BasicProperties.MessageId,
            CorrelationId = ea.BasicProperties.CorrelationId,
            Type = ea.BasicProperties.Type,
            ContentType = ea.BasicProperties.ContentType ?? "application/json",
            ContentEncoding = ea.BasicProperties.ContentEncoding,
            Persistent = true,
            Headers = cabecalhos
        };
    }

    /// <summary>
    /// Lê 'x-tentativas'. O AMQP transporta string como byte[], então um
    /// header que foi int volta int, mas um que passou por outra ferramenta
    /// pode voltar byte[]. Tratamos os dois para não quebrar na integração.
    /// </summary>
    private static int LerTentativas(BasicDeliverEventArgs ea)
    {
        if (ea.BasicProperties.Headers is null) return 0;
        if (!ea.BasicProperties.Headers.TryGetValue("x-tentativas", out var valor) || valor is null) return 0;

        return valor switch
        {
            int i => i,
            long l => (int)l,
            byte[] b => int.TryParse(Encoding.UTF8.GetString(b), out var p) ? p : 0,
            string s => int.TryParse(s, out var p) ? p : 0,
            _ => 0
        };
    }
}

// ════════════════════════════════════════════════════════════════════════════
//  CONSUMIDOR DE ESTOQUE — o efeito colateral de verdade.
//
//  Ele reserva estoque item por item e, dependendo do resultado, CONFIRMA ou
//  REJEITA o pedido. Três cuidados que valem a leitura:
//
//  1. RESERVA ATÔMICA (IProdutoRepository.ReservarAsync)
//     É um UPDATE condicional, não um read-modify-write. Ver o repositório.
//
//  2. COMPENSAÇÃO (não rollback!)
//     Se o item 3 falhar depois de os itens 1 e 2 terem sido reservados,
//     devolvemos os dois ao estoque explicitamente. Por que não confiar só no
//     rollback da transação? Porque aqui ele até funcionaria (é um banco só),
//     mas em arquitetura de eventos o normal é cada passo estar em um serviço
//     diferente — e aí não existe transação em comum: existe SAGA, e o
//     desfazer é uma ação de negócio, não um comando do banco. O código está
//     escrito nesse formato para o padrão ficar visível.
//
//  3. "SEM ESTOQUE" NÃO É ERRO
//     É resposta de negócio: rejeitamos o pedido e seguimos. Lançar exceção
//     aqui faria a mensagem ser retentada 3 vezes e cair na DLQ — e o cliente
//     nunca saberia que o pedido foi recusado. Retry é para falha TÉCNICA
//     (banco fora, timeout); decisão de negócio se resolve na hora.
// ════════════════════════════════════════════════════════════════════════════
public class EstoqueConsumer : ConsumidorBase
{
    protected override string NomeConsumidor => "estoque";

    public EstoqueConsumer(RabbitMqConnection conexao, IServiceProvider sp,
                           IOptions<RabbitMqOptions> opcoes, ILogger<EstoqueConsumer> log)
        : base(conexao, sp, opcoes, log) { }

    protected override async Task ProcessarAsync(EventEnvelope envelope, IServiceProvider escopo, CancellationToken ct)
    {
        var evento = envelope.LerPayload<PedidoCriadoEvent>();

        var produtos = escopo.GetRequiredService<IProdutoRepository>();
        var pedidos = escopo.GetRequiredService<IPedidoRepository>();

        var pedido = await pedidos.BuscarPorIdAsync(evento.PedidoId, ct);
        if (pedido is null)
        {
            // Pode acontecer legitimamente: a mensagem é mais rápida que a
            // réplica de leitura, ou alguém limpou o banco. Lançar exceção faz
            // a mensagem voltar pela fila de retry daqui a 10s — que é
            // exatamente o comportamento desejado.
            throw new InvalidOperationException(
                $"Pedido {evento.PedidoId} ainda não visível; vai retentar");
        }

        var reservados = new List<(long ProdutoId, int Quantidade)>();
        string? faltou = null;

        foreach (var item in evento.Itens)
        {
            if (await produtos.ReservarAsync(item.ProdutoId, item.Quantidade, ct))
            {
                reservados.Add((item.ProdutoId, item.Quantidade));
            }
            else
            {
                faltou = $"Sem estoque do produto {item.ProdutoId} (pedido de {item.Quantidade})";
                break;
            }
        }

        if (faltou is not null)
        {
            // COMPENSAÇÃO: devolve o que já havia sido reservado.
            foreach (var (produtoId, qtd) in reservados)
                await produtos.DevolverAsync(produtoId, qtd, ct);

            pedido.Rejeitar(faltou);
            Log.LogWarning("Pedido {Id} REJEITADO: {Motivo} (compensados {N} itens)",
                pedido.Id, faltou, reservados.Count);
        }
        else
        {
            pedido.Confirmar();
            Log.LogInformation("Pedido {Id} CONFIRMADO · {N} itens reservados", pedido.Id, reservados.Count);
        }

        // Sem SaveChanges aqui: o commit é da transação do ConsumidorBase,
        // junto com a marca do inbox. Reserva, decisão e dedup num só commit.
    }
}

    {

namespace LojaEventos.Api.Middleware;

// ════════════════════════════════════════════════════════════════════════════
//  CORRELATION ID — o fio que costura o log distribuído.
//
//  Em arquitetura de eventos, UMA requisição HTTP vira: 1 linha de pedido +
//  1 linha de outbox + 1 mensagem no broker + 2 consumidores agindo + 2 linhas
//  de inbox. Sem um id em comum, investigar "o que aconteceu com o pedido do
//  cliente X às 14h32" é arqueologia.
//
//  O id entra aqui, viaja no envelope do evento, é lido pelo consumidor e
//  colocado de volta no escopo de log dele. Resultado: um 'grep' por um id
//  mostra a história completa, da chamada HTTP ao e-mail enviado.
// ════════════════════════════════════════════════════════════════════════════
public class CorrelationIdMiddleware
{
    public const string Header = "X-Correlation-Id";
    private readonly RequestDelegate _next;
    private readonly ILogger<CorrelationIdMiddleware> _log;

    public CorrelationIdMiddleware(RequestDelegate next, ILogger<CorrelationIdMiddleware> log)
    { _next = next; _log = log; }

    public async Task Invoke(HttpContext ctx)
    {
        // Se o cliente mandou um, respeitamos (ele pode estar costurando
        // chamadas de vários serviços). Se não, geramos.
        var id = ctx.Request.Headers[Header].FirstOrDefault();
        if (string.IsNullOrWhiteSpace(id)) id = Guid.NewGuid().ToString("N")[..16];

        ctx.Items[Header] = id;

        // Devolvemos no response ANTES de processar: se a requisição explodir,
        // o cliente ainda tem o id para reportar no ticket.
        ctx.Response.Headers[Header] = id;

        using (_log.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = id }))
            await _next(ctx);
    }
}

public static class HttpContextExtensions
{
    public static string CorrelationId(this HttpContext ctx) =>
        ctx.Items[CorrelationIdMiddleware.Header] as string ?? "sem-correlation";
}

//  Três correções em relação à Tab 7:
//   1. mapeia CADA exceção para o status certo (404 era devolvido como 400);
//   2. tem um catch genérico — na Tab 7 qualquer exceção fora de
//      DomainException vazava sem problem+json;
//   3. checa 'Response.HasStarted'. Sem essa checagem, se a exceção acontecer
//      DEPOIS do primeiro byte ter saído, tentar escrever o corpo de erro
//      lança OUTRA exceção e você perde o log do erro original.
// ════════════════════════════════════════════════════════════════════════════
public class ExceptionMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<ExceptionMiddleware> _log;

    public ExceptionMiddleware(RequestDelegate next, ILogger<ExceptionMiddleware> log)
    { _next = next; _log = log; }

    public async Task Invoke(HttpContext ctx)
    {
        try
        {
            await _next(ctx);
        }
        catch (Exception ex)
        {
            // O mapeamento é por TIPO, nunca por texto da mensagem.
            var (status, titulo, tipoUri) = ex switch
            {
                NaoEncontradoException => (404, "Recurso não encontrado", "https://loja.exemplo/erros/nao-encontrado"),
                ConflitoException      => (409, "Conflito de estado",     "https://loja.exemplo/erros/conflito"),
                CorpoDivergenteException => (422, "Idempotency-Key reutilizada com outro corpo", "https://loja.exemplo/erros/chave-reutilizada"),
                DomainException        => (400, "Regra de negócio violada", "https://loja.exemplo/erros/dominio"),
                OperationCanceledException => (499, "Requisição cancelada pelo cliente", "https://loja.exemplo/erros/cancelado"),
                _                      => (500, "Erro interno",          "https://loja.exemplo/erros/interno")
            };

            if (status >= 500) _log.LogError(ex, "Erro não tratado em {Rota}", ctx.Request.Path);
            else _log.LogInformation("{Status} em {Rota}: {Msg}", status, ctx.Request.Path, ex.Message);

            if (ctx.Response.HasStarted)
            {
                _log.LogWarning("Resposta já iniciada: não foi possível devolver problem+json");
                return;
            }

            // Clear() apaga também os CABEÇALHOS já definidos — inclusive o
            // X-Correlation-Id que o CorrelationIdMiddleware colocou. Logo a
            // resposta de erro, que é justamente quando o cliente mais precisa
            // do id para abrir chamado, sairia sem ele. Por isso o recolocamos.
            ctx.Response.Clear();
            ctx.Response.Headers[CorrelationIdMiddleware.Header] = ctx.CorrelationId();
            ctx.Response.StatusCode = status;
            ctx.Response.ContentType = "application/problem+json";

            await ctx.Response.WriteAsync(JsonSerializer.Serialize(new
            {
                type = tipoUri,
                title = titulo,
                status,
                // Em 500 NÃO devolvemos ex.Message: pode conter connection
                // string, nome de tabela, caminho de arquivo. O detalhe fica
                // no log do servidor; o cliente recebe o correlationId.
                detail = status >= 500 ? "Consulte o suporte com o correlationId." : ex.Message,
                instance = ctx.Request.Path.Value,
                correlationId = ctx.CorrelationId()
            }));
        }
    }
}
✅ Três correções em relação ao ExceptionMiddleware da Tab 7: (1) mapeia cada exceção para o status certo — lá 404 era devolvido como 400; (2) tem catch genérico — lá qualquer exceção fora de DomainException vazava sem problem+json; (3) checa Response.HasStarted — sem isso, se a exceção acontecer depois do primeiro byte, tentar escrever o corpo de erro lança outra exceção e você perde o log do erro original. E em 500 o detail não devolve ex.Message: pode conter connection string, nome de tabela, caminho de arquivo.

builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

// ════════════════════════════════════════════════════════════════════════════
//  SEED DO CATÁLOGO — roda no boot da API, logo DEPOIS do EnsureCreated.
//
//  ┌─ ARMADILHA REAL: por que o seed NÃO é um .sql no docker-entrypoint ─────┐
//  │ A ideia óbvia é montar um 'sql/01-seed.sql' em                          │
//  │ /docker-entrypoint-initdb.d com 'CREATE TABLE produtos ...' + INSERT.   │
//  │ Parece funcionar, mas quebra a API em silêncio:                         │
//  │                                                                         │
//  │   'EnsureCreatedAsync()' só cria o schema se o banco NÃO TIVER NENHUMA  │
//  │   TABELA. Achando 'produtos' lá, ele conclui "já está criado" e não     │
//  │   cria pedidos, itens_pedido, outbox_messages, inbox_messages nem       │
//  │   idempotency_keys. O primeiro POST estoura com                         │
//  │   "Table 'loja_eventos.pedidos' doesn't exist".                         │
//  │                                                                         │
//  │ Regra: QUEM CRIA O SCHEMA também faz o seed. Aqui é o EF; em produção,  │
//  │ seriam as migrations (e o seed iria numa migration ou num job).         │
//  └─────────────────────────────────────────────────────────────────────────┘
//
//  Idempotente: se já existe produto, não faz nada. Pode reiniciar a API à
//  vontade (mesmo princípio de idempotência do resto da aba).
// ════════════════════════════════════════════════════════════════════════════
public static class CatalogoSeed
{
    public static async Task SemearAsync(AppDbContext ctx, CancellationToken ct = default)
    {
        if (await ctx.Produtos.AnyAsync(ct)) return;

        // Adicionados em ordem: num banco novo, o AUTO_INCREMENT dá os ids 1 a 5,
        // que são os ids usados no smoke.sh e nos exemplos de curl da aba.
        ctx.Produtos.AddRange(
            Produto.Criar("Teclado Mecânico ABNT2", Dinheiro.De(349.90m), 50),
            Produto.Criar("Mouse Vertical Ergonômico", Dinheiro.De(219.90m), 30),
            Produto.Criar("Monitor 27\" 144Hz", Dinheiro.De(1899.00m), 10),
            Produto.Criar("Headset com Cancelamento", Dinheiro.De(699.00m), 2),   // estoque baixo DE PROPÓSITO
            Produto.Criar("Webcam 4K", Dinheiro.De(459.00m), 0));                 // ZERADO: testa a REJEIÇÃO

⚡ Desempenho: duas métricas, não uma

Em arquitetura de eventos, latência de API e vazão de processamento são métricas separadas. A API pode responder em 20ms e o estoque levar 5 minutos para baixar — e isso não aparece em nenhum p95 de HTTP. Por isso o teste de carga tem duas partes.

perf/carga.js — k6: latência do POST + drenagem do outbox 
// ══════════════════════════════════════════════════════════════════════════════
//  TESTE DE CARGA (k6) — "o desempenho continua adequado?"
//
//  Rodar:
//    docker run --rm -i --network host grafana/k6 run - < perf/carga.js
//
//  O QUE ESTE TESTE MEDE QUE UM TESTE NORMAL NÃO MEDE:
//  Em arquitetura de eventos, latência de API e vazão de processamento são
//  DUAS métricas separadas. A API pode responder em 20ms e o estoque levar
//  5 minutos para baixar — e isso não aparece em p95 de HTTP nenhum.
//  Por isso o teste tem duas partes: carga no POST e, no fim ('teardown'),
//  a verificação de que o outbox DRENOU.
// ══════════════════════════════════════════════════════════════════════════════
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Counter, Trend } from 'k6/metrics';

const API = __ENV.API || 'http://localhost:8080';

const criados = new Counter('pedidos_criados');
const replays = new Counter('replays_idempotentes');
const latenciaPost = new Trend('latencia_post_ms');

export const options = {
  scenarios: {
    // Cenário 1: tráfego normal, cada usuário com sua própria chave.
    normal: {
      executor: 'ramping-vus',
      startVUs: 1,
      stages: [
        { duration: '20s', target: 20 },
        { duration: '40s', target: 20 },
        { duration: '10s', target: 0 },
      ],
      exec: 'pedidoNovo',
    },
    // Cenário 2: o cliente nervoso que clica 5x no botão "Finalizar".
    // TODAS as repetições usam a MESMA chave. Se a idempotência funciona,
    // isto gera 1 pedido por usuário virtual, não 5.
    duploClique: {
      executor: 'constant-vus',
      vus: 5,
      duration: '60s',
      exec: 'duploClique',
      startTime: '10s',
    },
  },
  thresholds: {
    // Latência do POST: o caminho crítico é só "grava no MySQL".
    // Não há chamada de rede a serviço nenhum aqui — por isso dá para
    // exigir p95 baixo. (Compare com a Tab 9, onde o POST chamava outro
    // serviço por HTTP e somava a latência dele.)
    'latencia_post_ms': ['p(95)<400'],
    'http_req_failed': ['rate<0.01'],
  },
};

function uuid() {
  return 'xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx'.replace(/[xy]/g, c => {
    const r = Math.random() * 16 | 0;
    return (c === 'x' ? r : (r & 0x3 | 0x8)).toString(16);
  });
}

function postarPedido(chave, produtoId) {
  const corpo = JSON.stringify({
    clienteEmail: `carga${__VU}@exemplo.com`,
    itens: [{ produtoId, quantidade: 1 }],
  });
  const res = http.post(`${API}/api/pedidos`, corpo, {
    headers: { 'Content-Type': 'application/json', 'Idempotency-Key': chave },
    tags: { name: 'POST /api/pedidos' },
  });
  latenciaPost.add(res.timings.duration);
  if (res.status === 201) criados.add(1);
  if (res.headers['Idempotent-Replay'] === 'true') replays.add(1);
  return res;
}

export function pedidoNovo() {
  // produto 1 e 2 têm estoque de sobra; 3 tem 10 (vai rejeitar alguns, o que
  // é ótimo: queremos ver o caminho de rejeição sob carga também).
  const res = postarPedido(uuid(), 1 + (__ITER % 3));
  check(res, { 'criou (201)': r => r.status === 201 });
  sleep(0.3);
}

export function duploClique() {
  const chave = uuid();           // uma chave por rodada...
  let primeiroId = null;
  for (let i = 0; i < 5; i++) {   // ...reutilizada 5 vezes de propósito
    const res = postarPedido(chave, 2);
    const id = res.json('id');
    if (i === 0) primeiroId = id;
    check(res, {
      'status 201 ou 200': r => r.status === 201 || r.status === 200,
      'mesmo pedido em toda repetição': () => id === primeiroId,
    });
  }
  sleep(1);
}

// ── A VERIFICAÇÃO QUE IMPORTA: o outbox acompanhou o ritmo? ─────────────────
export function teardown() {
  console.log('\n── Drenagem do outbox após a carga ──');
  for (let i = 0; i < 60; i++) {
    const d = http.get(`${API}/api/diagnostico/outbox`).json();
    console.log(`  pendentes=${d.pendentes} lag=${d.lagSegundos}s presas=${d.presas} publicadas=${d.publicadas}`);
    if (d.pendentes === 0) {
      console.log('  ✅ outbox drenado: a publicação acompanhou a escrita.');
      return;
    }
    sleep(2);
  }
  console.log('  ⚠️ ainda há pendentes depois de 2 min — suba mais réplicas do worker');
  console.log('     (docker compose up -d --scale worker=3) ou aumente o TamanhoLote.');
}

-- ═══════════════════════════════════════════════════════════════════════════
--  MANUTENÇÃO — rode diariamente (cron, Hangfire, EventBridge, o que preferir).
--
--  Sem isto, três tabelas crescem para sempre e o desempenho cai devagar, de
--  um jeito difícil de diagnosticar: a query do outbox continua usando índice,
--  mas o índice não para de crescer.
-- ═══════════════════════════════════════════════════════════════════════════

USE loja_eventos;

-- 1) OUTBOX: apaga o que já foi publicado há mais de 7 dias.
--    Mantemos uma semana para ser possível auditar ("este evento saiu mesmo?").
--    LIMIT para não travar a tabela num DELETE gigante — rode em laço.
DELETE FROM outbox_messages
 WHERE processado_em IS NOT NULL
   AND processado_em < UTC_TIMESTAMP() - INTERVAL 7 DAY
 LIMIT 10000;

-- 2) INBOX: a marca de dedup só precisa viver mais que a janela de reentrega
--    do broker. 30 dias é folgado e barato.
DELETE FROM inbox_messages
 WHERE processado_em < UTC_TIMESTAMP() - INTERVAL 30 DAY
 LIMIT 10000;

-- 3) IDEMPOTÊNCIA: expirou, morreu.
DELETE FROM idempotency_keys
 WHERE expira_em < UTC_TIMESTAMP()
 LIMIT 10000;

-- ── O QUE MONITORAR (rode isto num dashboard) ─────────────────────────────
-- Eventos presos: se der > 0, alguém precisa olhar.
SELECT COUNT(*) AS presos FROM outbox_messages

🪤 As 16 armadilhas — clique para abrir

1. "Publiquei direto no service, é mais simples" — e o dual-write voltou
É a regressão mais comum. Uma linha await _publisher.PublicarAsync(...) dentro do caso de uso e a garantia inteira morre em silêncio — os testes continuam verdes, o sistema continua funcionando, e um dia o broker cai e você perde eventos. Defesa: IEventPublisher só é consumido pelo OutboxDispatcher; coloque isso no checklist de code review.
2. Marcar processado_em antes de o broker confirmar
Você apaga a única cópia do evento com base em esperança. Sem publisher confirms, o publish retorna na hora; se o broker cair no mesmo instante, a mensagem evaporou e a linha já está marcada. O evento não existe mais em lugar nenhum. A ordem é sempre: publicar → esperar confirmação → marcar.
3. autoAck: true no consumidor
O broker esquece a mensagem no instante em que a entrega. Se o processamento falhar — ou o processo morrer — ela não existe mais. autoAck só serve para telemetria descartável. Em consumidor que faz trabalho real: autoAck: false e ACK depois do commit.
4. nack(requeue: true) como retry
Devolve a mensagem para a frente da fila imediatamente. Com o banco fora, você entra num laço fechado: 100% de CPU, milhares de linhas de log por segundo e nenhuma outra mensagem passa. Use fila de TTL (ou o plugin de delayed exchange).
5. Retentar poison message
JSON quebrado e versão desconhecida não melhoram com repetição. Retentar veneno trava a fila para sempre e queima suas tentativas. Esses dois casos vão direto para a DLQ, no passo 1 e 2 do roteiro do consumidor.
6. Tratar "sem estoque" como erro técnico
Vira 3 retries e DLQ — e o cliente nunca descobre que o pedido foi recusado. Retry é para falha técnica (banco fora, timeout); decisão de negócio se resolve na hora (rejeita o pedido e segue). Por isso TentarReservar devolve bool e não lança.
7. Inbox com chave só no message_id
A mesma mensagem vai para vários consumidores. Com chave simples, o primeiro a processar bloqueia os outros — o estoque baixa e o e-mail nunca sai. A chave é composta: (message_id, consumidor).
8. Hash do corpo não canônico na idempotência
Hashear o JSON cru faz a mesma compra com campos em outra ordem gerar hash diferente → 422 numa repetição legítima, e o cliente não consegue comprar. Normalize (trim, minúsculas, ordene as listas) antes de hashear.
9. SELECT sem SKIP LOCKED no outbox
Sem FOR UPDATE, duas réplicas leem o mesmo lote e publicam tudo em dobro. Com FOR UPDATE mas sem SKIP LOCKED, a segunda espera em vez de pular e a vazão cai pela metade. Os dois juntos transformam uma tabela MySQL numa fila concorrente.
10. DbContext no construtor de um BackgroundService
Captive dependency: o serviço é Singleton, o contexto é Scoped. O mesmo DbContext vive para sempre, acumulando entidades rastreadas até estourar a memória — e o change tracker fica cada vez mais lento. Crie um IServiceScope por ciclo de trabalho (ou por mensagem).
11. Deixar exceção escapar de ExecuteAsync
Mata o BackgroundService sem derrubar o processo. O container continua "healthy", o log não grita, e a aplicação simplesmente para de publicar. Envolva o laço inteiro em try/catch — e monitore lagSegundos, que é o que denuncia esse silêncio.
12. Serialização divergente entre API e Worker
A API grava camelCase, o worker lê esperando PascalCase: nada estoura, o payload chega com todos os campos nulos e o pedido vira total 0. Uma única JsonSerializerOptions static readonly, compartilhada pelos dois processos.
13. EnableRetryOnFailure + BeginTransactionAsync solto
Com o retry automático do EF ligado, abrir transação "na mão" lança InvalidOperationException: The configured execution strategy 'MySqlRetryingExecutionStrategy' does not support user-initiated transactions — em todo POST. O EF não sabe repetir só o último comando de uma transação: precisa repetir o bloco inteiro. Solução no UnitOfWork: Database.CreateExecutionStrategy().ExecuteAsync(...) envolvendo a transação, e ChangeTracker.Clear() antes de cada repetição para não gravar o evento duas vezes no outbox.
14. Seed em .sql + EnsureCreated
Um script de init que cria uma tabela faz o EnsureCreatedAsync() achar que o banco já está pronto e não criar nenhuma das outras. Quem cria o schema faz o seed (ver CatalogoSeed.cs).
15. O mesmo Value Object em duas entidades
Para o EF, um VO mapeado com OwnsOne é uma entidade com um dono só. Se o item do pedido recebe a mesma instância de Dinheiro que o Produto carregado usa, o SaveChanges enxerga um objeto com dois donos e lança exceção. O ItemPedido guarda uma cópia (precoUnitario with { }) e o repositório lê o produto com AsNoTracking().
16. --default-authentication-plugin no MySQL 8.4
A opção foi removida no MySQL 8.4 (estava depreciada desde a 8.0.27). Com ela no command: do compose, o mysqld morre no boot com unknown variable e o healthcheck nunca fica verde. Muito tutorial antigo ainda a traz: apague a linha.

📑 ADRs da Tab 7-B

ADR-013 · Outbox transacional em vez de publicação direta 🔷 C#Aceita

Contexto: criar um pedido exige gravar no MySQL e publicar no RabbitMQ. São dois sistemas sem transação em comum; qualquer ordem de execução tem um ponto de falha que deixa os dois lados divergentes.

Decisão: gravar o evento numa tabela outbox_messages no mesmo commit do agregado. Um processo separado (OutboxPublisherService) lê a tabela e publica, marcando a linha só após a confirmação do broker.

Alternativas consideradas: 2PC/XA (rejeitada: lento, frágil, pouco suportado); publicar antes de salvar (rejeitada: estoque baixa de pedido inexistente); publicar depois de salvar sem outbox (rejeitada: perde o evento); CDC/Debezium (adiada: resolve bem e com menor latência, mas exige Kafka Connect e acesso ao binlog — complexidade desproporcional para o escopo).

Consequências: (+) nenhum evento se perde, broker fora não derruba o checkout, rollback é trivial; (−) consistência eventual (~0,5s), entrega at-least-once (exige dedup), uma tabela a mais para operar e arquivar.

Status: Aceita · Stakeholders: Backend C#, SRE, Produto.

ADR-014 · Idempotency-Key obrigatória no POST 🔷 C#Aceita

Contexto: a rede cai antes da resposta chegar e o cliente tenta de novo; o usuário clica duas vezes em "Finalizar". Sem proteção, nascem dois pedidos e o cliente é cobrado duas vezes.

Decisão: exigir o cabeçalho Idempotency-Key (400 se faltar) e guardar chave + hash canônico do corpo + resposta em idempotency_keys, gravado na mesma transação do pedido. Replay devolve 200 com a resposta original e Idempotent-Replay: true; chave reutilizada com corpo diferente devolve 422 (recomendação do draft da IETF); a corrida entre duas requisições com a mesma chave vira replay (a perdedora leva 1062 e devolve a resposta da vencedora), com 409 só como rede de segurança.

Alternativas consideradas: gerar a chave no servidor (rejeitada: muda a cada tentativa, não protege de nada); deduplicar por hash do corpo sem chave (rejeitada: duas compras legítimas e idênticas seriam recusadas); filtro/middleware isolado (rejeitada como solução única: roda fora da transação, abre janela de inconsistência); estado EM_ANDAMENTO em duas gravações (rejeitada: deixa chaves travadas se o processo cai).

Consequências: (+) POST seguro para retry, cliente distingue "criei" de "já existia"; (−) contrato mais exigente para o cliente, tabela que precisa de expiração e limpeza, corrida resolvida via erro 1062 traduzido em replay.

Status: Aceita · Stakeholders: Backend C#, Mobile, QA.

ADR-015 · Inbox (consumidor idempotente) com chave composta 🔷 C#Aceita

Contexto: o RabbitMQ entrega at-least-once. Exactly-once na entrega não existe: o broker não sabe se o consumidor morreu antes ou depois de processar.

Decisão: cada consumidor grava (message_id, consumidor) em inbox_messages na mesma transação do efeito. Duplicidade na chave = já processado → ACK e ignora. Além disso, os métodos de transição do agregado (Confirmar, Rejeitar) são no-op quando o estado já é o esperado.

Alternativas consideradas: chave simples por message_id (rejeitada: um consumidor bloquearia os outros); dedup em cache distribuído (rejeitada: não é transacional com o efeito); confiar em exactly-once do broker (rejeitada: não existe).

Consequências: (+) efeito exactly-once, réplicas do worker podem escalar livremente; (−) uma tabela a mais, que cresce e precisa de expurgo; efeitos externos (e-mail) continuam fora da transação e exigem decisão explícita de ordem.

Status: Aceita · Stakeholders: Backend C#, SRE.

ADR-016 · RabbitMQ (topic) em vez de Kafka 🔷 C#Aceita

Contexto: precisamos de pub/sub com múltiplos consumidores do mesmo evento, retry com backoff, DLQ e observabilidade acessível em ambiente de aprendizado e de produção pequena.

Decisão: RabbitMQ com exchange topic, filas duráveis por consumidor, três filas de TTL para backoff escalonado (10s/1m/10m) e uma DLQ por consumidor. Topologia declarada em código no boot.

Alternativas consideradas: Kafka/Redpanda (rejeitada para este escopo: log particionado e replay são superiores em escala alta, mas custa mais infra, não tem DLQ nativa e a UI é menos didática); Azure Service Bus / SQS (rejeitadas: amarram a um provedor de nuvem); banco como fila sem broker (rejeitada: não dá fan-out nem push).

Consequências: (+) UI web excelente para depurar, DLQ e TTL nativos, leve no compose; (−) sem replay histórico (mensagem consumida sai da fila), ordenação só por fila, retry escalonado exige uma fila por degrau. A porta IEventPublisher mantém a troca por Kafka como mudança de um adapter.

Status: Aceita · Stakeholders: Backend C#, SRE, Arquitetura.

ADR-017 · API e Worker em processos separados 🔷 C#Aceita

Contexto: o despachante do outbox e os consumidores poderiam rodar como BackgroundService dentro da própria API, economizando um deploy.

Decisão: dois executáveis — LojaEventos.Api (só HTTP) e LojaEventos.Worker (outbox + consumidores) — compartilhando DependencyInjection.AddInfraestrutura para não divergirem.

Alternativas consideradas: tudo na API (rejeitada: 10 réplicas de API seriam 10 despachantes brigando pelas mesmas linhas, e um consumidor travado afetaria o checkout); um processo por consumidor (adiada: granularidade útil em escala, excesso de operação agora).

Consequências: (+) escala e falha independentes, deploy do worker sem derrubar a API; (−) duas imagens, duas configurações, e a disciplina de manter o registro de DI em um lugar só.

Status: Aceita · Stakeholders: Backend C#, SRE, DevOps.

ADR-018 · Id do pedido como GUID gerado no domínio 🔷 C#Aceita

Contexto: com AUTO_INCREMENT, a identidade só existe após o insert — e o evento de domínio, criado antes, saía com Id = 0 (bug observado na Tab 7).

Decisão: Guid gerado em Pedido.Criar(), mapeado como CHAR(36) com ValueGeneratedNever().

Alternativas consideradas: auto-increment + publicar o evento após o commit (rejeitada: o evento sairia de fora da transação, reabrindo o dual-write); sequência via tabela counters (rejeitada aqui: solução da Tab 9-B para o MongoDB, desnecessária tendo GUID); ULID/UUIDv7 (recomendada como evolução: mantém a vantagem e recupera a ordenação do índice).

Consequências: (+) evento nasce com a identidade correta, cliente recebe o id antes do commit, consumidor tem chave estável; (−) GUID aleatório fragmenta índice (mitigado com CHAR(36) e ordenação por criado_em), 36 bytes por chave.

Status: Aceita · Stakeholders: Backend C#, DBA.
