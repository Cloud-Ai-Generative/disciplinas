📜 O requisito: evoluir o banco sem quebrar a API

O enunciado da evolução tem 5 pontos — e cada um vira critério de aceitação desta aba:

  • Substituir o banco de dados existente pelo MongoDB;
  • Adaptar as APIs para serem compatíveis com o novo banco;
  • O sistema continuar funcionando como antes (mesmos endpoints, mesmos JSON, mesmos status);
  • Migrar os dados existentes com precisão (nada se perde, nada se altera);
  • Manter o desempenho adequado após a movimentação.

A regra de ouro: o contrato HTTP não muda. Controllers, services, JWT, middleware e os 21 testes da Tab 9 permanecem intactos — só a camada de persistência é trocada.

📄 Agregado = documento: o que era JOIN vira embed

No MySQL, a fronteira era tabela por agregado + tabelas filhas. No MongoDB, a fronteira vira documento por agregado: filhos que não vivem fora do pai são embutidos (embed), eliminando JOINs (que não existem no Mongo).

🔌 Uma porta, duas implementações (DIP aplicado 4×)

A Tab 9 já plantou o padrão no Auth (IUsuarioRepository). Agora ele vira regra dos 4 contextos: cada módulo expõe uma porta (interface) e ganha duas implementações — Ef*Repository (MySQL) e Mongo*Repository (MongoDB.Driver). Quem decide qual entra em produção é uma única chave de configuração: Storage:Provider = MySql | Mongo.

  • Services e controllers: zero alterações (dependem só da interface);
  • DI: o host registra Ef* ou Mongo* conforme o provider;
  • Rollback: voltar para MySQL = trocar a chave e reiniciar.
