🧩 Do relacional aos documentos: o mapeamento

No MySQL, um agregado do DDD fica "espalhado" em várias tabelas ligadas por chaves estrangeiras. No MongoDB, um agregado vira um documento: o que pertence a ele vai embutido. Como a Tab 9 já organizou os repositórios por agregado, o encaixe é direto.

MySQL (Tab 9)MongoDB (Tab 9-B)Decisão e porquê
auth_db.usuariosauth_db.usuarios_id = o mesmo Guid (UUID padrão): os tokens já emitidos (claim sub) continuam válidos
catalogo_db.produtoscatalogo_db.produtos_id inteiro; preço em Decimal128 (exato, sem perder centavos)
clientes_db.clientes + enderecos (FK)clientes_db.clientes com enderecos: [ ... ]Endereço embutido, mas mantendo seu id — Pedidos referencia enderecoId
pedidos_db.pedidos + pedido_itens (FK)pedidos_db.pedidos com itens: [ ... ]Item embutido e sem chave própria; reservaIds passa a ser persistido
AUTO_INCREMENTcoleção counters + $incMantém ids inteiros → URLs e contrato da API não mudam
4 databases (1 por contexto)4 databases (1 por contexto)A fronteira de dados do monolito modular é preservada
🗂️
Analogia da pasta de arquivo: no relacional, o pedido é uma ficha numa gaveta e os itens são fichas em outra gaveta, ligadas pelo número do pedido. No MongoDB, o pedido é uma pasta com os itens grampeados dentro: abriu a pasta, está tudo ali — sem ir a outra gaveta (sem JOIN).

🧠 Três decisões que guiam toda a migração

  1. Modelo de persistência separado do domínio. Não gravamos Produto direto no Mongo. Cada módulo ganha classes *Document (formato do banco, com [BsonElement]) e converte com FromDomain(...) / ToDomain() — esta última usando o Reconstituir(...) preparado na Tab 9. O formato no banco fica explícito e o domínio continua limpo.
  2. Mesmo comportamento observável. Cada método do adapter Mongo reproduz exatamente o efeito do adapter EF: mesma ordenação, mesma normalização de login, mesma reserva atômica (agora com $expr + $inc), mesmos códigos HTTP.
  3. Migração reversível e provada. O MySQL fica intacto durante a validação; voltar é trocar Provider para MySql. E "funciona igual" não é opinião: é relatório de validação, testes e smoke test.

🧩 Passo 1 — Desenhar os documentos (antes de escrever código)

Modelar é decidir o que fica junto. A regra prática: embuta o que pertence ao agregado e é lido junto; referencie (por id) o que é de outro agregado ou outro contexto. Por isso o pedido embute os itens, mas guarda clienteId, enderecoId e produtoId como referências — são de outros contextos.

documentos de exemplo (formato mongosh) 
// auth_db.usuarios
{ _id: UUID("3f2b..."), login: "admin", nome: "Administrador",
  senha: "admin123", criadoEm: ISODate("2026-10-24T22:00:00.000Z") }

// catalogo_db.produtos
{ _id: 1, nome: "Teclado Mecânico RGB", preco: NumberDecimal("349.90"),
  estoque: 15, reservado: 0 }

// clientes_db.clientes  → endereços EMBUTIDOS (com id preservado)
{ _id: 1, nome: "Ana Souza", email: "ana@example.com", ativo: true,
  enderecos: [ { id: 1, logradouro: "Rua A, 123", cidade: "São Paulo",
                 uf: "SP", cep: "01001-000" } ] }

// pedidos_db.pedidos  → itens EMBUTIDOS; cliente/endereço/produto por REFERÊNCIA
{ _id: 1, usuario: "3f2b...", clienteId: 1, enderecoId: 1, status: "RESERVADO",
  itens: [ { produtoId: 1, quantidade: 2, precoUnitario: NumberDecimal("349.90") } ],
  reservaIds: [ "a1b2c3d4" ] }

// <qualquer database>.counters  → substitui o AUTO_INCREMENT
{ _id: "produtos", seq: 3 }
⚖️
Embutir ou referenciar? Embutir dá leitura em 1 acesso e escrita atômica do agregado inteiro; o custo é duplicar dados se a mesma informação for compartilhada. Como itens e endereços pertencem a um só pedido/cliente, embutir é a escolha certa. Já o produto é compartilhado por muitos pedidos — por isso o pedido guarda só produtoId + o snapshot do preço.

# ══════════════════════════════════════════════════════════

# Pré-requisito: o compose da Tab 9 já rodando (ele cria a rede
# loja_multi_network, usada aqui como "external").
#
# Uso:
#   docker compose -f docker-compose.mongo.yml up -d     → sobe o Mongo
#   docker compose -f docker-compose.mongo.yml ps        → status (healthy?)
#   docker compose -f docker-compose.mongo.yml down      → derruba (mantém dados)
#   docker compose -f docker-compose.mongo.yml down -v   → derruba e APAGA os dados
# ══════════════════════════════════════════════════════════

services:
  mongo-db:
    # MongoDB 8 (inclui o shell mongosh dentro da imagem)
    image: mongo:8

    # Nome fixo do container (facilita docker exec)
    container_name: dev_mongo_multicontextos

    restart: unless-stopped

    # Usuário administrador criado no PRIMEIRO boot (volume vazio)
    environment:
      MONGO_INITDB_ROOT_USERNAME: root
      MONGO_INITDB_ROOT_PASSWORD: root123
      TZ: America/Sao_Paulo

    # Porta padrão do MongoDB
    ports:
      - "27017:27017"

    volumes:
      # Volume nomeado: dados persistem entre down/up
      - mongo_multi_data:/data/db

    networks:
      - loja_multi_network

    # Healthcheck: "ping" administrativo via mongosh
    healthcheck:
      test: ["CMD", "mongosh", "--quiet", "-u", "root", "-p", "root123", "--authenticationDatabase", "admin", "--eval", "db.adminCommand('ping').ok"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 20s

volumes:
  mongo_multi_data:
    driver: local

# A rede JÁ EXISTE (criada pelo compose da Tab 9): não recriamos, só usamos.
# Assim a API em container enxerga "mysql-db" E "mongo-db" pelo nome.
networks:
  loja_multi_network:
    external: true

using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.DependencyInjection.Extensions;
using MongoDB.Driver;

namespace LojaApi.Shared.Mongo;

/// <summary>
/// 🍃 Registro da infraestrutura Mongo no DI (chamado por cada módulo).
///
/// Cada módulo chama AddMongoInfra(...) no seu "case Mongo". Como os 4 módulos
/// chamam, usamos TryAdd*: o PRIMEIRO registra, os outros reaproveitam.
/// Resultado: UM único IMongoClient para a aplicação inteira.
/// </summary>
public static class MongoSetup
{
    /// <summary>
    /// Registra IMongoClient (singleton) e o serviço que cria os índices na
    /// inicialização.
    /// </summary>
    public static IServiceCollection AddMongoInfra(
        this IServiceCollection services,
        string? connectionString,
        string modulo)
    {
        // Fail fast: sem connection string, a API nem sobe
        if (string.IsNullOrWhiteSpace(connectionString))
            throw new InvalidOperationException(
                $"[{modulo}] ConnectionStrings:Mongo ausente. " +
                "Ex.: mongodb://root:root123@localhost:27017/?authSource=admin");

        // ⚡ DESEMPENHO: o MongoClient guarda o POOL DE CONEXÕES.
        // Ele é thread-safe e caro de criar → SINGLETON, sempre.
        // (Criar um MongoClient por request esgota conexões e derruba a performance.)
        services.TryAddSingleton<IMongoClient>(_ =>
        {
            var settings = MongoClientSettings.FromConnectionString(connectionString);

            // Se o Mongo estiver fora do ar, falha em 5s (o padrão é 30s)
            settings.ServerSelectionTimeout = TimeSpan.FromSeconds(5);

            return new MongoClient(settings);
        });

        // Cria os índices de todos os módulos ao iniciar (ver MongoIndexes.cs).
        // AddHostedService não duplica: registrar 4 vezes = 1 serviço.
        services.AddHostedService<MongoIndexHostedService>();

        return services;
    }
}

LojaApi.Shared.Kernel/PersistenceProviders.cs 
namespace LojaApi.Shared.Kernel;

/// <summary>
/// 🔀 PONTO DE TROCA DO BANCO.
///
/// O appsettings.json tem a chave "Persistence:Provider". Cada módulo lê
/// esse valor no seu ModuleExtensions e decide QUAL implementação dos
/// repositórios registrar no DI:
///
///   "MySql" → Ef*Repository    (EF Core + Pomelo)   ← Tab 9
///   "Mongo" → Mongo*Repository (MongoDB.Driver)     ← Tab 9-B (agora!)
///
/// Por que uma CHAVE de configuração e não "trocar o código"?
/// 1) A troca vira uma decisão de DEPLOY, não de programação.
/// 2) Rollback trivial: se o Mongo der problema, volta para "MySql".
/// 3) Os dois adapters convivem no mesmo build — dá para rodar os mesmos
///    testes e scripts contra os dois e PROVAR que o comportamento é idêntico.
/// </summary>
public static class PersistenceProviders
{
    /// <summary>MySQL via EF Core.</summary>
    public const string MySql = "MySql";

    /// <summary>MongoDB via MongoDB.Driver.</summary>
    public const string Mongo = "Mongo";

    /// <summary>
    /// Garante que a connection string exigida pelo provider foi informada.
    /// Com Provider = "Mongo", as connection strings do MySQL podem ficar vazias
    /// (e vice-versa) — cada módulo só exige a que vai usar.
    /// </summary>
    public static string ExigirConnectionString(string? valor, string nome, string modulo) =>
        string.IsNullOrWhiteSpace(valor)
            ? throw new InvalidOperationException(
                $"[{modulo}] ConnectionStrings:{nome} ausente (exigida pelo provider atual).")
            : valor;

    /// <summary>Erro para valores desconhecidos na configuração.</summary>
    public static InvalidOperationException ProviderInvalido(string modulo, string? valor) =>
        new($"[{modulo}] Persistence:Provider inválido: \"{valor}\". " +
            $"Valores aceitos: \"{MySql}\" ou \"{Mongo}\".");
}

Ids: o MongoDB não tem AUTO_INCREMENT, e o id nativo (ObjectId) quebraria as URLs da API (/api/catalogo/produtos/1). A solução clássica é a coleção counters com $inc atômico.

using MongoDB.Bson.Serialization.Attributes;
using MongoDB.Driver;

namespace LojaApi.Shared.Mongo;

/// <summary>
/// Documento da coleção "counters": um contador por sequência.
/// Exemplo no banco: { _id: "produtos", seq: 3 }
/// </summary>
public class ContadorDocument
{
    /// <summary>Nome da sequência (ex.: "produtos", "pedidos").</summary>
    [BsonId]
    public string Id { get; set; } = string.Empty;

    /// <summary>Último valor entregue.</summary>
    [BsonElement("seq")]
    public int Seq { get; set; }
}

/// <summary>
/// 🔢 GERADOR DE IDS INTEIROS para o MongoDB.
///
/// O problema: o MySQL tem AUTO_INCREMENT; o Mongo não. O id "nativo" do
/// Mongo é o ObjectId (ex.: "65f1c2..."), que QUEBRARIA o contrato da API
/// (Tab 8 usa ids inteiros: /api/catalogo/produtos/1).
///
/// A solução clássica: uma coleção "counters" e um $inc atômico.
///   db.counters.findOneAndUpdate(
///       { _id: "produtos" },
///       { $inc: { seq: 1 } },
///       { upsert: true, returnDocument: "after" })
/// Duas requests simultâneas NUNCA recebem o mesmo número: o $inc num único
/// documento é atômico.
/// </summary>
public static class IdGenerator
{
    /// <summary>Nome da coleção de contadores (uma por database/contexto).</summary>
    public const string Colecao = "counters";

    /// <summary>
    /// Reserva e devolve o próximo id da sequência (1, 2, 3...).
    /// Se a sequência não existir, o upsert a cria começando em 1.
    /// </summary>
    public static async Task<int> ProximoAsync(
        IMongoDatabase db,
        string sequencia,
        CancellationToken ct = default)
    {
        var contadores = db.GetCollection<ContadorDocument>(Colecao);

        var atualizado = await contadores.FindOneAndUpdateAsync(
            Builders<ContadorDocument>.Filter.Eq(c => c.Id, sequencia),
            Builders<ContadorDocument>.Update.Inc(c => c.Seq, 1),
            new FindOneAndUpdateOptions<ContadorDocument>
            {
                IsUpsert = true,                         // cria se não existir
                ReturnDocument = ReturnDocument.After    // devolve o valor JÁ incrementado
            },
            ct);

        return atualizado.Seq;
    }

    /// <summary>
    /// Garante que a sequência esteja, NO MÍNIMO, em <paramref name="valorMinimo"/>.
    /// Usado pelo MIGRADOR: depois de copiar produtos com ids 1..3, o contador
    /// precisa ficar em 3 — senão o próximo produto criado receberia o id 1
    /// (duplicado!). $max nunca diminui o contador → rodar 2x é seguro.
    /// </summary>
    public static Task AjustarMinimoAsync(
        IMongoDatabase db,
        string sequencia,
        int valorMinimo,
        CancellationToken ct = default)
    {
        var contadores = db.GetCollection<ContadorDocument>(Colecao);

        return contadores.UpdateOneAsync(
            Builders<ContadorDocument>.Filter.Eq(c => c.Id, sequencia),
            Builders<ContadorDocument>.Update.Max(c => c.Seq, valorMinimo),
            new UpdateOptions { IsUpsert = true },
            ct);
    }
}

Índices: são o principal fator de desempenho. Recriamos no Mongo os mesmos índices que o MySQL tinha. Um serviço de inicialização chama o CriarIndicesAsync de cada módulo quando a API sobe (createIndex é idempotente).

using Microsoft.Extensions.Hosting;

namespace LojaApi.Shared.Mongo;

/// <summary>
/// Contrato implementado por cada "MongoContext" de módulo que precisa de índices.
/// </summary>
public interface IMongoIndexInitializer
{
    /// <summary>Cria (se ainda não existirem) os índices do módulo.</summary>
    Task CriarIndicesAsync(CancellationToken ct);
}

/// <summary>
/// ⚡ Cria os índices de TODOS os módulos quando a API inicia.
///
/// Por que índices importam tanto (requisito "manter o desempenho")?
/// No MySQL, o init-sql já criava índices (ix_pedidos_usuario, login único).
/// No Mongo, sem índice, "meus pedidos" faz COLLSCAN (lê a coleção inteira).
/// Recriar os MESMOS índices é o que mantém o desempenho equivalente.
///
/// createIndex é IDEMPOTENTE: se o índice já existe com a mesma definição,
/// o Mongo não faz nada. Por isso é seguro rodar a cada inicialização.
/// </summary>
public class MongoIndexHostedService : IHostedService
{
    // Todos os módulos que registraram um IMongoIndexInitializer
    private readonly IEnumerable<IMongoIndexInitializer> _inicializadores;

    public MongoIndexHostedService(IEnumerable<IMongoIndexInitializer> inicializadores)
    {
        _inicializadores = inicializadores;
    }

    /// <summary>
    /// Roda na subida da API. Se o Mongo estiver fora do ar, a exceção
    /// impede a API de subir (fail fast) — melhor que falhar na 1ª request.
    /// </summary>
    public async Task StartAsync(CancellationToken ct)
    {
        foreach (var inicializador in _inicializadores)
            await inicializador.CriarIndicesAsync(ct);
    }

    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}

using LojaApi.Modules.Auth.Domain;
using MongoDB.Bson;
using MongoDB.Bson.Serialization.Attributes;

namespace LojaApi.Modules.Auth.Mongo;

/// <summary>
/// 📄 MODELO DE PERSISTÊNCIA do usuário no MongoDB (coleção "usuarios").
///
/// Por que NÃO salvar a entidade Usuario diretamente?
/// 1) Usuario tem setters privados e construtor protegido: o driver até
///    consegue usar reflexão, mas fica "mágico" e frágil.
/// 2) Separar DOMÍNIO (regras) de DOCUMENTO (formato no banco) permite mudar
///    um sem quebrar o outro — e deixa o formato do banco EXPLÍCITO.
/// 3) A conversão usa Usuario.Reconstituir(...), criado na Tab 9 justamente
///    para isto.
///
/// Documento resultante:
/// { _id: UUID("..."), login: "admin", nome: "Administrador",
///   senha: "admin123", criadoEm: ISODate("2026-10-24T22:00:00.000Z") }
/// </summary>
[BsonIgnoreExtraElements] // campos extras no banco (versões futuras) não quebram a leitura
public class UsuarioDocument
{
    /// <summary>
    /// _id = o mesmo Guid do MySQL (preserva o claim "sub" dos tokens!).
    /// GuidRepresentation.Standard = UUID binário (subtipo 4), o formato
    /// portável. Sem isso, o driver 3.x se recusa a gravar Guid.
    /// </summary>
    [BsonId]
    [BsonGuidRepresentation(GuidRepresentation.Standard)]
    public Guid Id { get; set; }

    [BsonElement("login")]
    public string Login { get; set; } = string.Empty;

    [BsonElement("nome")]
    public string Nome { get; set; } = string.Empty;

    /// <summary>Texto puro (didático) — igual ao MySQL. Produção: hash.</summary>
    [BsonElement("senha")]
    public string Senha { get; set; } = string.Empty;

    /// <summary>
    /// Sempre UTC. Atenção à PRECISÃO: o MySQL DATETIME(6) guarda
    /// MICROssegundos; o BSON Date guarda MILIssegundos. O migrador e o
    /// validador tratam essa diferença explicitamente.
    /// </summary>
    [BsonElement("criadoEm")]
    [BsonDateTimeOptions(Kind = DateTimeKind.Utc)]
    public DateTime CriadoEm { get; set; }

    /// <summary>Domínio → documento (para gravar).</summary>
    public static UsuarioDocument FromDomain(Usuario u) => new()
    {
        Id = u.Id,
        Login = u.Login,
        Nome = u.Nome,
        Senha = u.Senha,
        // O EF lê DATETIME do MySQL como Kind=Unspecified. Declaramos que é UTC
        // (o seed usa UTC_TIMESTAMP) para o driver não "converter fuso" errado.
        CriadoEm = DateTime.SpecifyKind(u.CriadoEm, DateTimeKind.Utc)
    };

    /// <summary>Documento → domínio (para ler), via fábrica de reconstituição.</summary>
    public Usuario ToDomain() =>
        Usuario.Reconstituir(Id, Login, Nome, Senha, CriadoEm);
}

using LojaApi.Shared.Mongo;
using MongoDB.Driver;

namespace LojaApi.Modules.Auth.Mongo;

/// <summary>
/// 🍃 "DbContext" do Auth no MongoDB: dá acesso ao database e às coleções.
///
/// Paralelo com a Tab 9:
///   AuthDbContext (EF)   → database auth_db, tabela usuarios
///   AuthMongoContext     → database auth_db, coleção usuarios
/// Mesmos nomes de propósito: a fronteira de dados por contexto continua
/// a mesma (um database por módulo), só muda a tecnologia.
///
/// É SINGLETON: IMongoDatabase e IMongoCollection são thread-safe e baratos.
/// </summary>
public class AuthMongoContext : IMongoIndexInitializer
{
    /// <summary>Nome do database (igual ao do MySQL).</summary>
    public const string Database = "auth_db";

    public IMongoDatabase Db { get; }

    /// <summary>Coleção "usuarios".</summary>
    public IMongoCollection<UsuarioDocument> Usuarios { get; }

    public AuthMongoContext(IMongoClient client)
    {
        Db = client.GetDatabase(Database);
        Usuarios = Db.GetCollection<UsuarioDocument>("usuarios");
    }

    /// <summary>
    /// Índice ÚNICO em login — o mesmo UNIQUE INDEX ix_usuarios_login do MySQL.
    /// Garante a regra (login não se repete) e acelera o login.
    /// mongosh: db.usuarios.createIndex({ login: 1 }, { unique: true })
    /// </summary>

  { _id: 1, $expr: { $gte: [ { $subtract: ["$estoque", "$reservado"] }, 2 ] } },
  { $inc: { reservado: 2 } },

namespace LojaApi.Modules.Catalogo.Repositories;

/// <summary>
/// 🔌 ADAPTER MongoDB da porta IProdutoRepository.
///
/// Tabela de equivalências com o EfProdutoRepository (Tab 9):
/// | Operação           | EF Core / MySQL                      | MongoDB                                  |
/// |--------------------|--------------------------------------|------------------------------------------|
/// | Listar paginado    | OrderBy(Id).Skip.Take                | Find({}).Sort({_id:1}).Skip.Limit        |
/// | Atualizar dados    | ExecuteUpdate (3 colunas)            | updateOne + $set (3 campos)              |
/// | Remover            | ExecuteDelete                        | deleteOne                                |
/// | Reservar (atômico) | UPDATE ... WHERE estoque-reservado&gt;=q | findOneAndUpdate + $expr + $inc          |
/// | Liberar            | SET reservado = CASE ... END         | updateOne com pipeline + $max            |
/// | Novo id            | AUTO_INCREMENT                       | coleção "counters" + $inc                |
/// </summary>
public class MongoProdutoRepository : IProdutoRepository
{
    private readonly CatalogoMongoContext _ctx;

    public MongoProdutoRepository(CatalogoMongoContext ctx)
    {
        _ctx = ctx;
    }

    /// <summary>mongosh: db.produtos.find({}).sort({ _id: 1 }).skip(p*s).limit(s)</summary>
    public async Task<IReadOnlyList<Produto>> ListarAsync(int page, int size, CancellationToken ct = default)
    {
        var docs = await _ctx.Produtos
            .Find(Builders<ProdutoDocument>.Filter.Empty)
            .SortBy(p => p.Id)          // mesma ordem do adapter EF
            .Skip(page * size)
            .Limit(size)
            .ToListAsync(ct);

        return docs.Select(d => d.ToDomain()).ToList();
    }

    /// <summary>mongosh: db.produtos.findOne({ _id: 1 })</summary>
    public async Task<Produto?> ObterAsync(int id, CancellationToken ct = default)
    {
        var doc = await _ctx.Produtos.Find(p => p.Id == id).FirstOrDefaultAsync(ct);
        return doc?.ToDomain();
    }

    /// <summary>
    /// Insere produto NOVO. O id vem da coleção "counters" (não há AUTO_INCREMENT).
    /// Como Produto.Id tem setter privado, devolvemos um NOVO objeto
    /// reconstituído com o id — por isso a porta diz "use o retorno".
    /// </summary>
    public async Task<Produto> AdicionarAsync(Produto produto, CancellationToken ct = default)
    {
        var doc = ProdutoDocument.FromDomain(produto);

        // Id = 0 → "o banco gera" (mesma convenção do EF)
        if (doc.Id == 0)
            doc.Id = await IdGenerator.ProximoAsync(_ctx.Db, CatalogoMongoContext.SequenciaProdutos, ct);

        await _ctx.Produtos.InsertOneAsync(doc, cancellationToken: ct);

        return doc.ToDomain();
    }

    /// <summary>
    /// mongosh: db.produtos.updateOne({ _id: 1 },
    ///            { $set: { nome: "...", preco: NumberDecimal("..."), estoque: 10 } })
    /// "reservado" fica de fora (evita lost update — igual ao adapter EF).
    /// </summary>
    public async Task<bool> AtualizarDadosAsync(Produto produto, CancellationToken ct = default)
    {
        var resultado = await _ctx.Produtos.UpdateOneAsync(
            p => p.Id == produto.Id,
            Builders<ProdutoDocument>.Update
                .Set(p => p.Nome, produto.Nome)
                .Set(p => p.Preco, produto.Preco)
                .Set(p => p.Estoque, produto.Estoque),
            cancellationToken: ct);

        // MatchedCount (e não ModifiedCount): um PUT com os MESMOS valores
        // "encontra" o documento mas não o "modifica" — e isso não é 404.
        return resultado.MatchedCount > 0;
    }

    /// <summary>mongosh: db.produtos.deleteOne({ _id: 1 })</summary>
    public async Task<bool> RemoverAsync(int id, CancellationToken ct = default)
    {
        var resultado = await _ctx.Produtos.DeleteOneAsync(p => p.Id == id, ct);
        return resultado.DeletedCount > 0;
    }

    /// <summary>
    /// ⚛️ RESERVA ATÔMICA — o equivalente exato do UPDATE condicional do MySQL:
    ///
    ///   db.produtos.findOneAndUpdate(
    ///     { _id: 1, $expr: { $gte: [ { $subtract: ["$estoque", "$reservado"] }, 2 ] } },
    ///     { $inc: { reservado: 2 } },
    ///     { returnDocument: "after" })
    ///
    /// - O FILTRO só casa se houver disponível suficiente ($expr permite
    ///   comparar campos do próprio documento: estoque - reservado).
    /// - O $inc só acontece se o filtro casar — tudo numa operação atômica
    ///   no documento. Duas requests disputando a última unidade: só uma vence.
    /// - findOneAndUpdate devolve o documento atualizado → já temos o PREÇO
    ///   para o snapshot, sem uma segunda consulta (o adapter EF precisa de 2).
    /// </summary>
    public async Task<ResultadoReserva> TentarReservarAsync(int id, int quantidade, CancellationToken ct = default)
    {
        // Filtro escrito como BsonDocument: fica IGUAL ao que você digitaria
        // no mongosh — ótimo para estudar e para depurar.
        FilterDefinition<ProdutoDocument> filtro = new BsonDocument
        {
            { "_id", id },
            { "$expr", new BsonDocument("$gte", new BsonArray
                {
                    new BsonDocument("$subtract", new BsonArray { "$estoque", "$reservado" }),
                    quantidade
                })
            }
        };

        var atualizado = await _ctx.Produtos.FindOneAndUpdateAsync(
            filtro,
            Builders<ProdutoDocument>.Update.Inc(p => p.Reservado, quantidade),
            new FindOneAndUpdateOptions<ProdutoDocument>
            {
                ReturnDocument = ReturnDocument.After
            },
            ct);

        if (atualizado is not null)
            return new ResultadoReserva(StatusReserva.Reservado, atualizado.Preco);

        // Nenhum documento casou: ou não existe, ou faltou estoque (404 vs 409)
        var existe = await _ctx.Produtos.CountDocumentsAsync(
            p => p.Id == id,
            new CountOptions { Limit = 1 },   // para no 1º encontrado: barato
            ct) > 0;

        return new ResultadoReserva(existe
            ? StatusReserva.EstoqueInsuficiente
            : StatusReserva.ProdutoInexistente);
    }

    /// <summary>
    /// Libera reserva sem deixar "reservado" negativo, de forma atômica.
    /// Usa um UPDATE COM PIPELINE (MongoDB 4.2+), que permite expressões:
    ///
    ///   db.produtos.updateOne({ _id: 1 },
    ///     [ { $set: { reservado: { $max: [ 0, { $subtract: ["$reservado", 2] } ] } } } ])
    ///
    /// É a mesma regra de Produto.Liberar: Math.Max(0, Reservado - qtd).
    /// </summary>
    public async Task<bool> LiberarAsync(int id, int quantidade, CancellationToken ct = default)
    {
        var pipeline = new BsonDocument[]
        {
            new BsonDocument("$set", new BsonDocument("reservado",
                new BsonDocument("$max", new BsonArray
                {
                    0,
                    new BsonDocument("$subtract", new BsonArray { "$reservado", quantidade })
                })))
        };

        var resultado = await _ctx.Produtos.UpdateOneAsync(
            Builders<ProdutoDocument>.Filter.Eq(p => p.Id, id),
            Builders<ProdutoDocument>.Update.Pipeline(pipeline),
            cancellationToken: ct);

        return resultado.MatchedCount > 0;
    }
}

/// <summary>
/// 🔌 ADAPTER MongoDB da porta IClienteRepository.
///
/// No EF, ObterAsync precisava de Include (JOIN com enderecos).
/// Aqui o agregado inteiro já é UM documento: um findOne basta.
/// </summary>
public class MongoClienteRepository : IClienteRepository
{
    private readonly ClientesMongoContext _ctx;

    public MongoClienteRepository(ClientesMongoContext ctx)
    {
        _ctx = ctx;
    }

    /// <summary>Insere cliente NOVO com id da coleção "counters".</summary>
    public async Task<Cliente> AdicionarAsync(Cliente cliente, CancellationToken ct = default)
    {
        var doc = ClienteDocument.FromDomain(cliente);

        if (doc.Id == 0)
            doc.Id = await IdGenerator.ProximoAsync(_ctx.Db, ClientesMongoContext.SequenciaClientes, ct);

        // Endereços novos (id 0) também ganham id da sua própria sequência,
        // para continuarem únicos e referenciáveis por "enderecoId".
        foreach (var e in doc.Enderecos.Where(e => e.Id == 0))
            e.Id = await IdGenerator.ProximoAsync(_ctx.Db, ClientesMongoContext.SequenciaEnderecos, ct);

        await _ctx.Clientes.InsertOneAsync(doc, cancellationToken: ct);

        return doc.ToDomain();
    }

    /// <summary>mongosh: db.clientes.findOne({ _id: 1 })  → endereços já vêm junto</summary>
    public async Task<Cliente?> ObterAsync(int id, CancellationToken ct = default)
    {
        var doc = await _ctx.Clientes.Find(c => c.Id == id).FirstOrDefaultAsync(ct);
        return doc?.ToDomain();
    }

    /// <summary>
    /// mongosh: db.clientes.updateOne({ _id: 1 },
    ///            { $set: { nome: "...", email: "...", ativo: false } })
    /// </summary>
    public async Task<bool> AtualizarDadosAsync(Cliente cliente, CancellationToken ct = default)
    {
        var resultado = await _ctx.Clientes.UpdateOneAsync(
            c => c.Id == cliente.Id,
            Builders<ClienteDocument>.Update
                .Set(c => c.Nome, cliente.Nome)
                .Set(c => c.Email, cliente.Email)
                .Set(c => c.Ativo, cliente.Ativo),
            cancellationToken: ct);

        return resultado.MatchedCount > 0;
    }

    /// <summary>mongosh: db.clientes.countDocuments({ _id: 1 }, { limit: 1 })</summary>
    public async Task<bool> ExisteAsync(int id, CancellationToken ct = default)
        => await _ctx.Clientes.CountDocumentsAsync(
            c => c.Id == id,
            new CountOptions { Limit = 1 },
            ct) > 0;

    /// <summary>
    /// ⚡ PROJEÇÃO: traz SÓ o array de endereços, não o documento inteiro.
    /// mongosh: db.clientes.findOne({ _id: 1 }, { enderecos: 1, _id: 0 })
    /// Menos bytes na rede = mais desempenho (o checkout chama isto sempre).
    /// </summary>
    public async Task<IReadOnlyList<Endereco>> ListarEnderecosAsync(int clienteId, CancellationToken ct = default)
    {
        var enderecos = await _ctx.Clientes
            .Find(c => c.Id == clienteId)
            .Project(c => c.Enderecos)
            .FirstOrDefaultAsync(ct);

        return (enderecos ?? new List<EnderecoDocument>())
            .Select(e => e.ToDomain())
            .ToList();
    }
}

/// 📄 Item do pedido EMBUTIDO no documento do pedido (sem coleção própria).
///
/// No MySQL o item tinha Id e PedidoId (chaves técnicas do relacional).
/// Aqui elas SOMEM: o item mora dentro do pedido, então não precisa de chave
/// própria nem de FK. É o encaixe natural "agregado DDD = documento".

public class ItemPedidoDocument

    public int ProdutoId { get; set; }

    [BsonElement("quantidade")]
    public int Quantidade { get; set; }

    /// <summary>Snapshot do preço — Decimal128 para não perder centavos.</summary>
    [BsonElement("precoUnitario")]
    [BsonRepresentation(BsonType.Decimal128)]
    public decimal PrecoUnitario { get; set; }

/// <summary>
/// 📄 MODELO DE PERSISTÊNCIA do pedido (coleção "pedidos").
///
/// Documento resultante:
/// { _id: 1, usuario: "c0a8...", clienteId: 1, enderecoId: 1, status: "RESERVADO",
///   itens: [ { produtoId: 1, quantidade: 2, precoUnitario: NumberDecimal("349.90") } ],
///   reservaIds: [ "a1b2c3d4" ] }
///
/// Relacional (Tab 9): 2 tabelas + JOIN. Documento: 1 leitura traz tudo.
/// </summary>
[BsonIgnoreExtraElements]
public class PedidoDocument
{
    [BsonId]
    public int Id { get; set; }

    /// <summary>Id do usuário (claim sub). Tem índice: "meus pedidos".</summary>
    [BsonElement("usuario")]
    public string Usuario { get; set; } = string.Empty;

    [BsonElement("clienteId")]
    public int ClienteId { get; set; }

    [BsonElement("enderecoId")]
    public int EnderecoId { get; set; }

    /// <summary>
    /// Enum gravado como TEXTO ("RESERVADO"), igual ao MySQL. Gravar como
    /// número (2) quebraria os dados se alguém reordenasse o enum.
    /// </summary>
    [BsonElement("status")]
    [BsonRepresentation(BsonType.String)]
    public PedidoStatus Status { get; set; }

    [BsonElement("itens")]
    public List<ItemPedidoDocument> Itens { get; set; } = new();

    /// <summary>
    /// No MySQL era ignorado (exigiria outra tabela). Aqui é só um array —
    /// o modelo de documentos guarda listas simples "de graça".
    /// </summary>
    [BsonElement("reservaIds")]
    public List<string> ReservaIds { get; set; } = new();

    /// <summary>Domínio → documento.</summary>
    public static PedidoDocument FromDomain(Pedido p) => new()
    {
        Id = p.Id,
        Usuario = p.Usuario,
        ClienteId = p.ClienteId,
        EnderecoId = p.EnderecoId,
        Status = p.Status,
        Itens = p.Itens.Select(i => new ItemPedidoDocument
        {
            ProdutoId = i.ProdutoId,
            Quantidade = i.Quantidade,
            PrecoUnitario = i.PrecoUnitario
        }).ToList(),
        ReservaIds = p.ReservaIds.ToList()
    };

    /// <summary>Documento → domínio, via fábrica de reconstituição.</summary>
    public Pedido ToDomain() => Pedido.Reconstituir(
        Id,
        Usuario,
        ClienteId,
        EnderecoId,
        Status,
        Itens.Select(i => new ItemPedido(i.ProdutoId, i.Quantidade, i.PrecoUnitario)),
        ReservaIds);
}

using LojaApi.Modules.Catalogo.Mongo;

namespace LojaApi.Migrator;

/// <summary>
/// 🚚 COPIA os dados MySQL → MongoDB, contexto por contexto.
///
/// Três propriedades que tornam a migração CONFIÁVEL:
///
/// 1) FIEL: lê o domínio pelo EF e grava pelo MESMO mapeamento que a API usa
///    (*Document.FromDomain). Ids, datas, status, preços e o flag "ativo"
///    são preservados (Reconstituir garante isso na leitura).
///
/// 2) IDEMPOTENTE: cada documento é gravado com "upsert por _id"
///    (replaceOne com upsert:true). Rodar 2, 3, 10 vezes dá o MESMO resultado,
///    sem duplicar nada. Se a migração cair no meio, é só rodar de novo.
///
/// 3) EFICIENTE: grava em LOTES com bulkWrite (1 ida ao banco a cada N
///    documentos, em vez de N idas). Com ordered:false, o Mongo pode
///    processar o lote em paralelo.
///
/// ⚠️ Rode com a API PARADA (janela de manutenção): se alguém gravar no
/// MySQL durante a cópia, esse dado pode ficar de fora.
/// </summary>
public sealed class Migrador
{
    private readonly Fontes _f;
    private readonly int _tamanhoLote;

    public Migrador(Fontes fontes, int tamanhoLote)
    {
        _f = fontes;
        _tamanhoLote = tamanhoLote;
    }

    public async Task ExecutarAsync(CancellationToken ct)
    {
        Console.WriteLine("🚚 MIGRAÇÃO MySQL → MongoDB");
        Console.WriteLine($"   lote: {_tamanhoLote} documentos por bulkWrite\n");

        // Ordem: não importa para o Mongo (não há FKs), mas seguimos a ordem
        // "de quem é referenciado para quem referencia" por clareza.
        await MigrarUsuariosAsync(ct);
        await MigrarProdutosAsync(ct);
        await MigrarClientesAsync(ct);
        await MigrarPedidosAsync(ct);

        Console.WriteLine("\n✅ Cópia concluída. Agora rode a VALIDAÇÃO (modo \"validar\").");
    }

    // ══════════ AUTH ══════════
    private async Task MigrarUsuariosAsync(CancellationToken ct)
    {
        await using var db = _f.AuthMySql();

        // AsNoTracking: só leitura, sem custo de rastreamento do EF.
        // (Para tabelas com milhões de linhas, leia em páginas por Id —
        //  "keyset pagination" — em vez de trazer tudo para a memória.)
        var usuarios = await db.Usuarios.AsNoTracking().ToListAsync(ct);

        await UpsertEmLotesAsync(
            _f.AuthMongo.Usuarios,
            usuarios.Select(UsuarioDocument.FromDomain),
            d => Builders<UsuarioDocument>.Filter.Eq(x => x.Id, d.Id),
            "auth_db.usuarios",
            ct);

        // Usuários têm id Guid: não usam a coleção "counters".
    }

    // ══════════ CATÁLOGO ══════════
    private async Task MigrarProdutosAsync(CancellationToken ct)
    {
        await using var db = _f.CatalogoMySql();
        var produtos = await db.Produtos.AsNoTracking().OrderBy(p => p.Id).ToListAsync(ct);

        await UpsertEmLotesAsync(
            _f.CatalogoMongo.Produtos,
            produtos.Select(ProdutoDocument.FromDomain),
            d => Builders<ProdutoDocument>.Filter.Eq(x => x.Id, d.Id),
            "catalogo_db.produtos",
            ct);

        // 🔢 O contador precisa "saber" do maior id migrado,
        // senão o próximo produto criado pela API receberia id 1 (duplicado).
        if (produtos.Count > 0)
            await IdGenerator.AjustarMinimoAsync(
                _f.CatalogoMongo.Db, CatalogoMongoContext.SequenciaProdutos, produtos.Max(p => p.Id), ct);
    }

    // ══════════ CLIENTES ══════════
    private async Task MigrarClientesAsync(CancellationToken ct)
    {
        await using var db = _f.ClientesMySql();

        // Include: junta cliente + endereços (2 tabelas) → 1 documento
        var clientes = await db.Clientes
            .AsNoTracking()
            .Include(c => c.Enderecos)
            .OrderBy(c => c.Id)
            .ToListAsync(ct);

        await UpsertEmLotesAsync(
            _f.ClientesMongo.Clientes,
            clientes.Select(ClienteDocument.FromDomain),
            d => Builders<ClienteDocument>.Filter.Eq(x => x.Id, d.Id),
            "clientes_db.clientes",
            ct);

        if (clientes.Count > 0)
            await IdGenerator.AjustarMinimoAsync(
                _f.ClientesMongo.Db, ClientesMongoContext.SequenciaClientes, clientes.Max(c => c.Id), ct);

        // Endereços embutidos também têm sequência própria (ids referenciados por Pedidos)
        var maiorEndereco = clientes.SelectMany(c => c.Enderecos).Select(e => e.Id).DefaultIfEmpty(0).Max();
        if (maiorEndereco > 0)
            await IdGenerator.AjustarMinimoAsync(
                _f.ClientesMongo.Db, ClientesMongoContext.SequenciaEnderecos, maiorEndereco, ct);
    }

    // ══════════ PEDIDOS ══════════
    private async Task MigrarPedidosAsync(CancellationToken ct)
    {
        await using var db = _f.PedidosMySql();

        // Itens são "owned": o EF já os traz junto (pedidos + pedido_itens)
        var pedidos = await db.Pedidos.AsNoTracking().OrderBy(p => p.Id).ToListAsync(ct);

        await UpsertEmLotesAsync(
            _f.PedidosMongo.Pedidos,
            pedidos.Select(PedidoDocument.FromDomain),
            d => Builders<PedidoDocument>.Filter.Eq(x => x.Id, d.Id),
            "pedidos_db.pedidos",
            ct);

        if (pedidos.Count > 0)
            await IdGenerator.AjustarMinimoAsync(
                _f.PedidosMongo.Db, PedidosMongoContext.SequenciaPedidos, pedidos.Max(p => p.Id), ct);
    }

    /// <summary>
    /// Grava documentos em lotes com "upsert por _id" (idempotente).
    /// Equivalente mongosh de UM lote:
    ///   db.produtos.bulkWrite([
    ///     { replaceOne: { filter: { _id: 1 }, replacement: {...}, upsert: true } },
    ///     { replaceOne: { filter: { _id: 2 }, replacement: {...}, upsert: true } }
    ///   ], { ordered: false })
    /// </summary>
    private async Task UpsertEmLotesAsync<TDoc>(
        IMongoCollection<TDoc> colecao,
        IEnumerable<TDoc> documentos,
        Func<TDoc, FilterDefinition<TDoc>> filtroPorId,
        string nome,
        CancellationToken ct)
    {
        var total = 0;

        // Chunk divide a sequência em pedaços de _tamanhoLote itens
        foreach (var lote in documentos.Chunk(_tamanhoLote))
        {
            var operacoes = lote
                .Select(doc => new ReplaceOneModel<TDoc>(filtroPorId(doc), doc) { IsUpsert = true })
                .ToList();

            await colecao.BulkWriteAsync(
                operacoes,
                new BulkWriteOptions { IsOrdered = false },
                ct);

            total += lote.Length;
        }

        Console.WriteLine($"   ✔ {nome,-24} {total,7} documento(s) gravado(s) (upsert)");
    }
}

/// <summary>
/// 🔏 "ASSINATURA" de cada registro: uma string com TODOS os campos que
/// importam, num formato normalizado. Se a assinatura de um produto no MySQL
/// for igual à do mesmo produto no Mongo, os dois são iguais campo a campo.
///
/// As assinaturas são calculadas sobre os objetos de DOMÍNIO dos dois lados
/// (MySQL via EF; Mongo via *Document.ToDomain()). Assim comparamos
/// "o que a API enxerga", não detalhes de formato de cada banco.
///
/// Normalizações (e POR QUÊ):
/// - decimal com 6 casas e cultura invariante → 349.90 e 349.9 são o mesmo valor;
/// - datas truncadas em MILIssegundos e em UTC → o BSON Date não guarda
///   microssegundos (o MySQL DATETIME(6) guarda): é uma perda CONHECIDA e
///   aceitável, e por isso documentada aqui em vez de "escondida";
/// - listas (itens, endereços) ordenadas → a ordem física não é um dado.
/// </summary>
public static class Assinaturas
{
    private static readonly CultureInfo Inv = CultureInfo.InvariantCulture;

    private static string Dec(decimal v) => v.ToString("F6", Inv);

    /// <summary>Trunca para milissegundos e marca como UTC.</summary>
    private static string Data(DateTime d) =>
        new DateTime(d.Ticks - d.Ticks % TimeSpan.TicksPerMillisecond, DateTimeKind.Utc)
            .ToString("O", Inv);

    public static string De(Usuario u) =>
        $"{u.Id}|{u.Login}|{u.Nome}|{u.Senha}|{Data(u.CriadoEm)}";

    public static string De(Produto p) =>
        $"{p.Id}|{p.Nome}|{Dec(p.Preco)}|{p.Estoque}|{p.Reservado}";

    /// <summary>
    /// ReservaIds NÃO entra: no MySQL esse campo nunca foi persistido
    /// (era ignorado pelo EF). Comparar algo que a origem não tem geraria
    /// falso alarme.
    /// </summary>
    public static string De(Pedido p) =>
        $"{p.Id}|{p.Usuario}|{p.ClienteId}|{p.EnderecoId}|{p.Status}|" +
        string.Join(";", p.Itens
            .OrderBy(i => i.ProdutoId).ThenBy(i => i.Quantidade).ThenBy(i => i.PrecoUnitario)
            .Select(i => $"{i.ProdutoId}x{i.Quantidade}@{Dec(i.PrecoUnitario)}"));

    public static string De(Cliente c) =>
        $"{c.Id}|{c.Nome}|{c.Email}|{c.Ativo}|" +
        string.Join(";", c.Enderecos
            .OrderBy(e => e.Id)
            .Select(e => $"{e.Id}:{e.Logradouro}:{e.Cidade}:{e.Uf}:{e.Cep}"));
}

using System.Text;

namespace LojaApi.Migrator;

/// <summary>
/// 📋 Relatório de validação: acumula as verificações e decide se a
/// migração foi APROVADA (todas as linhas OK) ou REPROVADA.
/// Imprime no console e salva em Markdown (evidência para entregar).
/// </summary>
public sealed class Relatorio
{
    private record Linha(string Secao, string Verificacao, string MySql, string Mongo, bool Ok);

    private readonly List<Linha> _linhas = new();
    private readonly List<string> _divergencias = new();

    /// <summary>true somente se NENHUMA verificação falhou.</summary>
    public bool Aprovado => _linhas.All(l => l.Ok);

    /// <summary>
    /// Compara dois conjuntos de registros pela chave e pela assinatura.
    /// Detecta: registros FALTANDO no Mongo, SOBRANDO no Mongo e DIFERENTES.
    /// </summary>
    public void CompararRegistros<T>(
        string secao,
        IReadOnlyCollection<T> mysql,
        IReadOnlyCollection<T> mongo,
        Func<T, string> chave,
        Func<T, string> assinatura)
    {
        var origem = mysql.ToDictionary(chave, assinatura);
        var destino = mongo.ToDictionary(chave, assinatura);

        var faltando = origem.Keys.Except(destino.Keys).ToList();
        var sobrando = destino.Keys.Except(origem.Keys).ToList();
        var diferentes = origem.Keys.Intersect(destino.Keys)
            .Where(k => origem[k] != destino[k])
            .ToList();

        // 1) Contagem
        Adicionar(secao, "quantidade de registros", mysql.Count, mongo.Count);

        // 2) Igualdade campo a campo (via assinatura)
        var identicos = origem.Count - faltando.Count - diferentes.Count;
        _linhas.Add(new Linha(secao, "registros idênticos (campo a campo)",
            $"{origem.Count}", $"{identicos}",
            faltando.Count == 0 && sobrando.Count == 0 && diferentes.Count == 0));

        // Detalhes (no máximo 5 por tipo, para não poluir)
        foreach (var k in faltando.Take(5)) _divergencias.Add($"[{secao}] FALTANDO no Mongo: id {k}");
        foreach (var k in sobrando.Take(5)) _divergencias.Add($"[{secao}] SOBRANDO no Mongo: id {k}");
        foreach (var k in diferentes.Take(5))
            _divergencias.Add($"[{secao}] DIFERENTE id {k}\n      MySQL: {origem[k]}\n      Mongo: {destino[k]}");
    }

    /// <summary>Soma/contagem de controle: o total precisa bater EXATAMENTE.</summary>
    public void Adicionar<TValor>(string secao, string verificacao, TValor mysql, TValor mongo)
        where TValor : IEquatable<TValor>
    {
        _linhas.Add(new Linha(secao, verificacao, $"{mysql}", $"{mongo}", mysql.Equals(mongo)));
    }

    /// <summary>Verificação booleana livre (ex.: contador &gt;= maior id).</summary>
    public void Verificar(string secao, string verificacao, string detalhe, bool ok)
    {
        _linhas.Add(new Linha(secao, verificacao, "—", detalhe, ok));
    }

    /// <summary>Imprime no console.</summary>
    public void Imprimir()
    {
        Console.WriteLine();
        Console.WriteLine($"{"SEÇÃO",-10} {"VERIFICAÇÃO",-40} {"MySQL",14} {"Mongo",14}  OK");
        Console.WriteLine(new string('─', 88));
        foreach (var l in _linhas)
            Console.WriteLine($"{l.Secao,-10} {l.Verificacao,-40} {l.MySql,14} {l.Mongo,14}  {(l.Ok ? "✅" : "❌")}");

        if (_divergencias.Count > 0)
        {
            Console.WriteLine("\nDivergências encontradas:");
            foreach (var d in _divergencias) Console.WriteLine($"  • {d}");
        }

        Console.WriteLine();
        Console.WriteLine(Aprovado
            ? "🟢 MIGRAÇÃO APROVADA: origem e destino são equivalentes."
            : "🔴 MIGRAÇÃO REPROVADA: corrija as divergências e rode novamente.");
    }

    /// <summary>Salva o relatório em Markdown (evidência da validação).</summary>
    public void SalvarMarkdown(string caminho)
    {
        var sb = new StringBuilder();
        sb.AppendLine("# Relatório de validação — Migração MySQL → MongoDB");
        sb.AppendLine();
        sb.AppendLine($"Gerado em: {DateTime.UtcNow:yyyy-MM-dd HH:mm:ss} UTC");
        sb.AppendLine();
        sb.AppendLine($"**Resultado: {(Aprovado ? "🟢 APROVADA" : "🔴 REPROVADA")}**");
        sb.AppendLine();
        sb.AppendLine("| Seção | Verificação | MySQL | Mongo | OK |");
        sb.AppendLine("|---|---|---:|---:|:-:|");
        foreach (var l in _linhas)
            sb.AppendLine($"| {l.Secao} | {l.Verificacao} | {l.MySql} | {l.Mongo} | {(l.Ok ? "✅" : "❌")} |");

        if (_divergencias.Count > 0)
        {
            sb.AppendLine();
            sb.AppendLine("## Divergências");
            sb.AppendLine("```");
            foreach (var d in _divergencias) sb.AppendLine(d);
            sb.AppendLine("```");
        }

        File.WriteAllText(caminho, sb.ToString());
        Console.WriteLine($"📝 Relatório salvo em: {Path.GetFullPath(caminho)}");
    }
}

///    Pega: registros perdidos ou duplicados.
/// 2) SOMAS DE CONTROLE — totais de negócio (estoque, reservado, valor dos
///    pedidos, endereços...). Pega: erros de conversão (ex.: decimal virando
///    double e perdendo centavos) mesmo quando a contagem bate.
/// 3) COMPARAÇÃO CAMPO A CAMPO — assinatura de cada registro dos dois lados.
///    Pega: qualquer campo diferente, em qualquer registro.
///    (Bases enormes: compare uma AMOSTRA aleatória + as somas de controle.)
///
/// Também confere os CONTADORES de id (counters &gt;= maior id migrado).
/// </summary>

        _f = fontes;

    public async Task<bool> ExecutarAsync(CancellationToken ct)

        var r = new Relatorio();

        await ValidarUsuariosAsync(r, ct);
        await ValidarProdutosAsync(r, ct);
        await ValidarClientesAsync(r, ct);

    // ══════════ AUTH ══════════
    private async Task ValidarUsuariosAsync(Relatorio r, CancellationToken ct)
    {
        await using var db = _f.AuthMySql();
        var mysql = await db.Usuarios.AsNoTracking().ToListAsync(ct);

        var mongo = (await _f.AuthMongo.Usuarios
                .Find(Builders<UsuarioDocument>.Filter.Empty)
                .ToListAsync(ct))
            .Select(d => d.ToDomain())
            .ToList();

        r.CompararRegistros("usuarios", mysql, mongo, u => u.Id.ToString(), Assinaturas.De);
    }

    // ══════════ CATÁLOGO ══════════
    private async Task ValidarProdutosAsync(Relatorio r, CancellationToken ct)
    {
        await using var db = _f.CatalogoMySql();
        var mysql = await db.Produtos.AsNoTracking().ToListAsync(ct);

        var mongo = (await _f.CatalogoMongo.Produtos
                .Find(Builders<ProdutoDocument>.Filter.Empty)
                .ToListAsync(ct))
            .Select(d => d.ToDomain())
            .ToList();

        r.CompararRegistros("produtos", mysql, mongo, p => p.Id.ToString(), Assinaturas.De);

        // Somas de controle
        r.Adicionar("produtos", "Σ estoque", mysql.Sum(p => p.Estoque), mongo.Sum(p => p.Estoque));
        r.Adicionar("produtos", "Σ reservado", mysql.Sum(p => p.Reservado), mongo.Sum(p => p.Reservado));
        r.Adicionar("produtos", "Σ preço × estoque (R$)",
            mysql.Sum(p => p.Preco * p.Estoque), mongo.Sum(p => p.Preco * p.Estoque));

        await VerificarContadorAsync(r, "produtos", _f.CatalogoMongo.Db,
            CatalogoMongoContext.SequenciaProdutos, mysql.Select(p => p.Id).DefaultIfEmpty(0).Max(), ct);
    }

    // ══════════ CLIENTES ══════════
    private async Task ValidarClientesAsync(Relatorio r, CancellationToken ct)
    {
        await using var db = _f.ClientesMySql();
        var mysql = await db.Clientes.AsNoTracking().Include(c => c.Enderecos).ToListAsync(ct);

        var mongo = (await _f.ClientesMongo.Clientes
                .Find(Builders<ClienteDocument>.Filter.Empty)
                .ToListAsync(ct))
            .Select(d => d.ToDomain())
            .ToList();

        r.CompararRegistros("clientes", mysql, mongo, c => c.Id.ToString(), Assinaturas.De);

        r.Adicionar("clientes", "Σ endereços", mysql.Sum(c => c.Enderecos.Count), mongo.Sum(c => c.Enderecos.Count));
        r.Adicionar("clientes", "clientes ativos", mysql.Count(c => c.Ativo), mongo.Count(c => c.Ativo));

        await VerificarContadorAsync(r, "clientes", _f.ClientesMongo.Db,
            ClientesMongoContext.SequenciaClientes, mysql.Select(c => c.Id).DefaultIfEmpty(0).Max(), ct);
        await VerificarContadorAsync(r, "clientes", _f.ClientesMongo.Db,
            ClientesMongoContext.SequenciaEnderecos,
            mysql.SelectMany(c => c.Enderecos).Select(e => e.Id).DefaultIfEmpty(0).Max(), ct);
    }

    // ══════════ PEDIDOS ══════════
    private async Task ValidarPedidosAsync(Relatorio r, CancellationToken ct)
    {
        await using var db = _f.PedidosMySql();
        var mysql = await db.Pedidos.AsNoTracking().ToListAsync(ct);

        var mongo = (await _f.PedidosMongo.Pedidos
                .Find(Builders<PedidoDocument>.Filter.Empty)
                .ToListAsync(ct))
            .Select(d => d.ToDomain())
            .ToList();

        r.CompararRegistros("pedidos", mysql, mongo, p => p.Id.ToString(), Assinaturas.De);

        r.Adicionar("pedidos", "Σ itens (linhas)", mysql.Sum(p => p.Itens.Count), mongo.Sum(p => p.Itens.Count));
        r.Adicionar("pedidos", "Σ unidades", mysql.Sum(p => p.Itens.Sum(i => i.Quantidade)),
            mongo.Sum(p => p.Itens.Sum(i => i.Quantidade)));
        r.Adicionar("pedidos", "Σ valor total (R$)", mysql.Sum(p => p.Total), mongo.Sum(p => p.Total));

        await VerificarContadorAsync(r, "pedidos", _f.PedidosMongo.Db,
            PedidosMongoContext.SequenciaPedidos, mysql.Select(p => p.Id).DefaultIfEmpty(0).Max(), ct);
    }

    /// <summary>
    /// O contador precisa estar &gt;= maior id migrado; senão a API geraria
    /// ids repetidos ao criar o próximo registro.
    /// </summary>
    private static async Task VerificarContadorAsync(
        Relatorio r, string secao, IMongoDatabase db, string sequencia, int maiorId, CancellationToken ct)
    {
        if (maiorId == 0)
            return; // nada migrado nessa sequência

        var contador = await db.GetCollection<ContadorDocument>(IdGenerator.Colecao)
            .Find(c => c.Id == sequencia)
            .FirstOrDefaultAsync(ct);

        var valor = contador?.Seq ?? 0;
        r.Verificar(secao, $"counters.{sequencia} ≥ maior id ({maiorId})", $"{valor}", valor >= maiorId);
    }
}

# ══════════════════════════════════════════════════════════════
# 🔥 SMOKE TEST de ponta a ponta — "o sistema funciona como antes?"
