① 🏛️ Clean Architecture: o negócio no centro, a tecnologia na borda

🧅
Analogia da cebola (ou do restaurante): no miolo ficam as receitas (as regras do negócio: "preço não pode ser negativo"). Em volta, a cozinha que segue as receitas (os casos de uso). Na casca, o salão e o fornecedor (HTTP, banco de dados). Trocar o fornecedor de tomate não muda a receita. Na API: trocar MySQL por MongoDB não muda nenhuma regra — e é exatamente isso que a Tab 9-B faz.

Criada por Robert C. Martin (2012), juntando ideias da arquitetura Hexagonal (Cockburn) e Onion (Palermo). No .NET, cada camada é um projeto (.csproj) separado, e um projeto só pode apontar para dentro:

🧩 DDD: as peças do domínio

  • Aggregate Root — Produto: a entidade "dona" das regras. Setters privados: ninguém muda o preço sem passar pela validação. Duas portas de entrada: Produto.Criar(...) (produto novo, ainda sem id) e Produto.Reconstituir(...) (um produto que já existe).
  • Value Object — Dinheiro: sem identidade, imutável (record) e comparado pelo valor: dois "R$ 10" são iguais.
  • Domain Event — ProdutoCriadoEvent: um fato do negócio ("um produto foi criado"). Ele só é registrado depois de salvar, quando o banco já deu o id — senão sairia com id 0. E depois? Nesta aba o evento só fica registrado na entidade (e é testado): ninguém o publica ainda. Por que registrar já? Porque o domínio passa a anunciar o que aconteceu sem saber quem vai escutar. Na Tab 7-B, esse mesmo tipo de evento vai para uma fila (RabbitMQ), com garantia de entrega.
  • Exceções de domínio: DomainException (regra quebrada → 400) e NaoEncontradoException (não existe → 404).

🔄 O que é um ORM — e o que o EF Core faz por você

O banco guarda tabelas (linhas e colunas); o seu código trabalha com objetos (classes com campos). Alguém precisa traduzir um para o outro a cada leitura e a cada gravação. ORM (Object-Relational Mapping, "mapeamento objeto-relacional") é a biblioteca que faz essa tradução: você descreve uma vez qual classe é qual tabela, e ela escreve o SQL e copia os valores sozinha.

🗣️
Analogia do intérprete: o seu código fala "objeto", o banco fala "SQL". Sem ORM, você fala os dois idiomas e traduz cada frase à mão. Com ORM, você contrata um intérprete: diz "salve este produto" e ele traduz para INSERT INTO produtos …. Ótimo no dia a dia — mas vale saber o que ele está dizendo por você, porque às vezes traduz de um jeito lento.

Em C#, o ORM oficial é o Entity Framework Core (EF Core). Ele conversa com cada banco por um provider: aqui, o Pomelo, que ensina o EF a falar MySQL. O DbContext é a "sessão" com o banco: sabe quais classes são tabelas e guarda as mudanças até o SaveChanges.

⚖️ O mesmo trabalho, sem e com ORM

sem ORM — ADO.NET puro: você escreve o SQL e copia cada coluna à mão 
// Buscar UM produto pelo id, sem ORM
const string sql = "SELECT id, nome, preco, estoque FROM produtos WHERE id = @id";
await using var con = new MySqlConnection(connectionString);
await con.OpenAsync();
await using var cmd = new MySqlCommand(sql, con);
cmd.Parameters.AddWithValue("@id", id);         // o @id vira o valor (evita SQL injection)
await using var r = await cmd.ExecuteReaderAsync();
if (!await r.ReadAsync()) return null;
return Produto.Reconstituir(                     // coluna por coluna, à mão
    r.GetInt64("id"), r.GetString("nome"),
    new Dinheiro(r.GetDecimal("preco")), r.GetInt32("estoque"));
com ORM — EF Core: você descreve o mapeamento uma vez; o SQL sai sozinho 
// No AppDbContext: "a classe Produto é a tabela produtos"
modelBuilder.Entity<Produto>(e =>
{
    e.ToTable("produtos");
    e.Property(p => p.Nome).HasColumnName("nome");
    // ...
});

// Buscar UM produto pelo id, com ORM: uma linha
var p = await _ctx.Produtos.FirstOrDefaultAsync(x => x.Id == id);
// O EF Core gera e roda:  SELECT ... FROM produtos WHERE id = @p0 LIMIT 1

⚙️ O que o ORM faz por baixo

TarefaO que acontece
MapearLê a descrição (anotações ou configuração) e sabe que o campo preco é a coluna preco, de que tipo, e qual é a chave
Gerar o SQLTransforma cada chamada (buscar, salvar, apagar, paginar) no SELECT, INSERT, UPDATE ou DELETE certo — já com parâmetros, o que evita SQL injection
Copiar os valoresMonta o objeto a partir de cada linha que volta, e o contrário na hora de gravar
Rastrear mudançasLembra como o objeto estava quando foi lido; ao salvar, grava só o que mudou
TransaçãoAgrupa as gravações num pacote só: ou vale tudo, ou nada (o "A" do ACID, Tab 5)
👀 Veja o intérprete trabalhando: Quer ver o SQL que o EF Core gera? No appsettings.json, em Logging → LogLevel, acrescente "Microsoft.EntityFrameworkCore.Database.Command": "Information", rode a API e olhe o terminal: cada consulta aparece como o SQL de verdade.

⚠️ Os cuidados que todo mundo aprende do jeito difícil

ArmadilhaO que aconteceComo evitar
N+1Você lista 100 pedidos e, para cada um, lê os itens: o ORM faz 1 consulta para os pedidos + 100 para os itens. Rápido com 3 registros, lento com 10 milPedir tudo de uma vez: .Include(p => p.Itens), que traz tudo num JOIN só
Carregamento sob demanda (lazy loading)As listas ligadas à entidade (propriedades de navegação (uma lista de itens dentro do pedido) carregadas sob demanda) só são buscadas quando você as usa — e cada uso é uma ida ao banco. É ele que causa o N+1 sem você perceberSaber o que cada tela precisa e carregar só isso, de propósito
Paginar na memóriaLer a tabela inteira e só depois pegar 20 linhasPaginar antes de buscar, para virar LIMIT/OFFSET no SQL (é o que o EfProdutoRepository faz)
Esquecer que existe SQLUma linha bonita no código pode virar uma consulta pesadaLigar o log do SQL (quadro acima) e olhar de vez em quando

Quando não usar: relatórios pesados, consultas muito específicas do banco ou cargas de milhares de linhas por segundo costumam ficar melhores com SQL escrito à mão — em geral com ADO.NET puro ou o Dapper (um "micro-ORM": você escreve o SQL e ele só copia as colunas para a classe). Não é "ORM ou SQL": muitos projetos usam o ORM no dia a dia e SQL à mão nos poucos lugares que precisam.

Nesta aba: o mapeamento está em AppDbContext + a classe Produto, e quem usa o ORM é o EfProdutoRepository. O domínio nunca vê o ORM: se um dia o banco mudar, só esses arquivos mudam.

namespace LojaApi.Domain.ValueObjects;

/// <summary>
/// Value Object "Dinheiro": sem identidade, imutável (record) e comparado por VALOR.
/// new Dinheiro(10m) == new Dinheiro(10m) → true (dois "R$ 10" são iguais).
/// </summary>
public sealed record Dinheiro(decimal Valor, string Moeda = "BRL")
{
    /// <summary>
    /// Construtor vazio e privado, só para o EF Core: o construtor do record pede "Moeda",
    /// que não tem coluna no banco, então o EF não conseguiria usá-lo.
    /// </summary>
    private Dinheiro() : this(0m) { }

    /// <summary>Soma dois valores, mantendo a moeda (não altera nenhum dos dois: imutável).</summary>
    public Dinheiro Add(Dinheiro outro) => new(Valor + outro.Valor, Moeda);
}

👉 O Aggregate Root: os setters são privados, então ninguém muda o preço sem passar pela validação. Repare nas duas fábricas — Criar (produto novo, sem id) e Reconstituir (produto que já existe no banco) — e no ConfirmarCriacao, que registra o evento depois de salvar.

LojaApi.Domain/Entities/Produto.cs (Aggregate Root) 
using LojaApi.Domain.Events;
using LojaApi.Domain.Exceptions;
using LojaApi.Domain.ValueObjects;

namespace LojaApi.Domain.Entities;

/// <summary>
/// Aggregate Root "Produto" — entidade RICA (DDD): os dados e as regras moram juntos.
/// Setters privados: ninguém de fora muda o estado sem passar pelas regras.
/// Mapeia a tabela "produtos" do banco loja_db (Tab 5).
/// </summary>
public class Produto
{
    private readonly List<IDomainEvent> _events = new();

    public long Id { get; private set; }                       // BIGINT no MySQL
    public string Nome { get; private set; } = string.Empty;
    public Dinheiro Preco { get; private set; } = new(0);
    public int Estoque { get; private set; }

    /// <summary>Eventos de domínio pendentes (não vão para o banco).</summary>
    public IReadOnlyCollection<IDomainEvent> DomainEvents => _events.AsReadOnly();

    /// <summary>Construtor vazio e protegido: só o EF Core usa, ao ler do banco.</summary>
    protected Produto() { }

    /// <summary>
    /// Factory Method de CRIAÇÃO: valida as regras. O Id fica 0 até o banco gerar.
    /// </summary>
    public static Produto Criar(string nome, Dinheiro preco, int estoque)
    {
        var p = new Produto();
        p.Aplicar(nome, preco, estoque);
        return p;
    }

    /// <summary>
    /// Factory de RECONSTITUIÇÃO: monta um produto que JÁ existe (com Id).
    /// Usada pelos testes; não publica evento.
    /// </summary>
    public static Produto Reconstituir(long id, string nome, Dinheiro preco, int estoque)
    {
        var p = new Produto { Id = id };
        p.Aplicar(nome, preco, estoque);
        return p;
    }

    /// <summary>
    /// Chamado pelo ProdutoService DEPOIS de salvar: agora o Id é real,
    /// então o evento sai com o número certo.
    /// </summary>
    public void ConfirmarCriacao()
    {
        if (Id <= 0) throw new DomainException("O produto precisa ser salvo antes de confirmar a criação");
        _events.Add(new ProdutoCriadoEvent(Id, Nome));
    }

    /// <summary>Atualização (PUT): mesmas regras da criação.</summary>
    public void AplicarAtualizacao(string nome, Dinheiro preco, int estoque) => Aplicar(nome, preco, estoque);

    /// <summary>Remove estoque com guarda de suficiência.</summary>
    public void RemoverEstoque(int quantidade)
    {
        if (quantidade <= 0) throw new DomainException("Quantidade deve ser > 0");
        if (Estoque < quantidade) throw new DomainException("Estoque insuficiente");
        Estoque -= quantidade;
    }

    /// <summary>Limpa os eventos depois de publicados.</summary>
    public void ClearEvents() => _events.Clear();

    // As regras ficam num lugar só (as mesmas do contrato da Tab 4):
    // nome 2–100 letras, preço > 0, estoque >= 0.
    private void Aplicar(string nome, Dinheiro preco, int estoque)
    {
        if (string.IsNullOrWhiteSpace(nome) || nome.Trim().Length < 2)
            throw new DomainException("O nome deve ter pelo menos 2 caracteres");
        if (nome.Trim().Length > 100)
            throw new DomainException("O nome pode ter no máximo 100 caracteres");
        if (preco is null || preco.Valor <= 0)
            throw new DomainException("O preço deve ser maior que zero");
        if (estoque < 0)
            throw new DomainException("O estoque não pode ser negativo");
        Nome = nome.Trim();
        Preco = preco;
        Estoque = estoque;
    }
}

👉 Os casos de uso: chama o domínio para validar, grava pela porta e confirma a criação. Repare no construtor: ele recebe a interface IProdutoRepository, nunca a classe do EF.

LojaApi.Application/Services/ProdutoService.cs 
using LojaApi.Application.DTOs;
using LojaApi.Domain.Entities;
using LojaApi.Domain.Exceptions;
using LojaApi.Domain.Interfaces;
using LojaApi.Domain.ValueObjects;

namespace LojaApi.Application.Services;

/// <summary>
/// Casos de uso. Recebe a INTERFACE IProdutoRepository no construtor (DIP):
/// não sabe se é MySQL, Mongo ou um mock de teste.
/// </summary>
public class ProdutoService : IProdutoService
{
    private readonly IProdutoRepository _repo;

    public ProdutoService(IProdutoRepository repo) { _repo = repo; }

    public async Task<List<ProdutoResponse>> ListarAsync(int page, int size)
    {
        // Mesmos limites do contrato: page >= 0, size entre 1 e 100
        if (page < 0) throw new DomainException("page deve ser >= 0");
        if (size is < 1 or > 100) throw new DomainException("size deve estar entre 1 e 100");
        var pagina = await _repo.ListarAsync(page, size);
        return pagina.Select(ProdutoMapper.ToResponse).ToList();
    }

    public async Task<ProdutoResponse> ObterPorIdAsync(long id)
    {
        var p = await _repo.BuscarPorIdAsync(id)
            ?? throw new NaoEncontradoException($"Produto {id} não existe");   // → 404
        return ProdutoMapper.ToResponse(p);
    }

    public async Task<ProdutoResponse> CriarAsync(ProdutoRequest req)
    {
        var produto = Produto.Criar(req.Nome, new Dinheiro(req.Preco), req.Estoque);  // regras → 400
        var salvo = await _repo.SalvarAsync(produto);   // o banco gera o Id
        salvo.ConfirmarCriacao();                        // agora o evento sai com o Id certo
        return ProdutoMapper.ToResponse(salvo);
    }

    public async Task<ProdutoResponse> AtualizarAsync(long id, ProdutoRequest req)
    {
        var p = await _repo.BuscarPorIdAsync(id)
            ?? throw new NaoEncontradoException($"Produto {id} não existe");   // → 404
        p.AplicarAtualizacao(req.Nome, new Dinheiro(req.Preco), req.Estoque);  // regras → 400
        var salvo = await _repo.SalvarAsync(p);
        return ProdutoMapper.ToResponse(salvo);
    }

    public async Task ExcluirAsync(long id)
    {
        if (!await _repo.ExistePorIdAsync(id))
            throw new NaoEncontradoException($"Produto {id} não existe");      // → 404
        await _repo.DeletarAsync(id);
    }
}

🏭 Infrastructure — EF Core + MySQL

🐬 A tabela já existe: o EF Core aqui não cria tabela — usa a produtos que o init-sql da Tab 5 criou no loja_db (id BIGINT, nome, preco DECIMAL(10,2), estoque). Por isso o Id é long e o mapeamento diz o nome de cada coluna.

👉 O mapa do EF Core entre a classe Produto e a tabela produtos da Tab 5. Repare no OwnsOne: é ele que guarda o Value Object Dinheiro na coluna preco.

LojaApi.Infrastructure/Data/AppDbContext.cs 
using LojaApi.Domain.Entities;
using Microsoft.EntityFrameworkCore;

namespace LojaApi.Infrastructure.Data;

/// <summary>
/// DbContext do EF Core: diz como a classe Produto vira a tabela "produtos"
/// que JÁ existe no loja_db (criada pelo init-sql da Tab 5). Por isso não usamos migrations aqui.
/// </summary>
public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

    public DbSet<Produto> Produtos => Set<Produto>();

    protected override void OnModelCreating(ModelBuilder mb)
    {
        mb.Entity<Produto>(e =>
        {
            e.ToTable("produtos");
            e.HasKey(p => p.Id);
            e.Property(p => p.Id).HasColumnName("id");
            e.Property(p => p.Nome).HasColumnName("nome").HasMaxLength(100).IsRequired();
            e.Property(p => p.Estoque).HasColumnName("estoque").IsRequired();
            e.Ignore(p => p.DomainEvents);        // eventos não vão para o banco

            // O Value Object Dinheiro vira a coluna "preco" da MESMA tabela (owned type).
            // Atenção: NÃO use e.Ignore(p => p.Preco) junto — o Ignore apagaria a propriedade
            // e o OwnsOne quebraria ao montar o modelo.
            e.OwnsOne(p => p.Preco, d =>
            {
                d.Property(x => x.Valor).HasColumnName("preco").HasColumnType("decimal(10,2)");
                d.Ignore(x => x.Moeda);           // a tabela não tem coluna de moeda (sempre BRL)
            });
            e.Navigation(p => p.Preco).IsRequired();
        });
    }
}

👉 O adapter EF Core + MySQL da porta IProdutoRepository. Repare na paginação: o Skip/Take vem antes do ToListAsync, então vira LIMIT/OFFSET no SQL.

LojaApi.Infrastructure/Repositories/EfProdutoRepository.cs 
using LojaApi.Domain.Entities;
using LojaApi.Domain.Interfaces;
using LojaApi.Infrastructure.Data;
using Microsoft.EntityFrameworkCore;   // traz AsNoTracking, ToListAsync, AnyAsync...

namespace LojaApi.Infrastructure.Repositories;

/// <summary>ADAPTER: implementa a porta IProdutoRepository usando EF Core + MySQL.</summary>
public class EfProdutoRepository : IProdutoRepository
{
    private readonly AppDbContext _ctx;
    public EfProdutoRepository(AppDbContext ctx) { _ctx = ctx; }

    public async Task<Produto> SalvarAsync(Produto p)
    {
        if (p.Id == 0) await _ctx.Produtos.AddAsync(p);   // novo → INSERT
        // já existe: foi lido por BuscarPorIdAsync (rastreado), o EF detecta a mudança → UPDATE
        await _ctx.SaveChangesAsync();
        return p;
    }

    public Task<Produto?> BuscarPorIdAsync(long id) =>
        _ctx.Produtos.FirstOrDefaultAsync(p => p.Id == id);

    // Paginação DE VERDADE: o Skip/Take vira "LIMIT ... OFFSET ..." no SQL.
    public Task<List<Produto>> ListarAsync(int page, int size) =>
        _ctx.Produtos.AsNoTracking()
            .OrderBy(p => p.Id)                // ordem estável entre páginas
            .Skip(page * size).Take(size)
            .ToListAsync();

    public Task<bool> ExistePorIdAsync(long id) => _ctx.Produtos.AnyAsync(p => p.Id == id);

    public async Task DeletarAsync(long id)
    {
        var p = await _ctx.Produtos.FirstOrDefaultAsync(x => x.Id == id);
        if (p is not null) { _ctx.Produtos.Remove(p); await _ctx.SaveChangesAsync(); }
    }
}

using Microsoft.AspNetCore.Mvc;
using Microsoft.IdentityModel.Tokens;
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;

namespace LojaApi.Api.Controllers;

/// <summary>
/// Login público que emite o JWT — no formato do contrato da Tab 4:
/// recebe { email, senha } e devolve { tokenAcesso, tipo, expiraEm }.
/// Didático: o usuário é fixo. A Tab 9 mostra login com tabela de usuários.

[ApiController]
[Route("api/auth")]
public class AuthController : ControllerBase
{
    private readonly IConfiguration _cfg;
    public AuthController(IConfiguration cfg) { _cfg = cfg; }

    public record LoginRequest(string Email, string Senha);

    [HttpPost("login")]
    public IActionResult Login([FromBody] LoginRequest req)
    {
        if (string.IsNullOrWhiteSpace(req.Email) || string.IsNullOrWhiteSpace(req.Senha))
            return Problem(type: "https://example.com/erros/validacao", title: "Requisição inválida",
                           statusCode: 400, detail: "Os campos email e senha são obrigatórios.");

        if (req.Email != "dev@loja.com.br" || req.Senha != "SenhaForte#2026")
            return Problem(type: "https://example.com/erros/naoautenticado", title: "Não autenticado",
                           statusCode: 401, detail: "E-mail ou senha incorretos.");

        // A validade vem do appsettings.json (Jwt:ExpirationMinutes), não fixa no código
        var minutos = _cfg.GetValue("Jwt:ExpirationMinutes", 60);
        var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_cfg["Jwt:Secret"]!));
        var token = new JwtSecurityToken(
            claims: new[] { new Claim(JwtRegisteredClaimNames.Sub, req.Email) },   // quem é — sem role
            expires: DateTime.UtcNow.AddMinutes(minutos),
            signingCredentials: new SigningCredentials(key, SecurityAlgorithms.HmacSha256));

        return Ok(new
        {
            tokenAcesso = new JwtSecurityTokenHandler().WriteToken(token),
            tipo = "Bearer",
            expiraEm = minutos * 60          // em segundos, como diz o contrato
        });
    }
}

👉 Tratamento de erros num lugar só: NaoEncontradoException → 404, DomainException → 400, qualquer outro erro → 500, sempre em problem+json. No 500, o detalhe vai para o log, nunca para o cliente.

LojaApi.Api/Middleware/ExceptionMiddleware.cs (RFC 7807) 
using LojaApi.Domain.Exceptions;
using System.Text.Json;

namespace LojaApi.Api.Middleware;

/// <summary>
/// Tratamento CENTRALIZADO de erros: toda exceção vira RFC 7807 (application/problem+json),
/// com os mesmos "type" do contrato da Tab 4.
///   NaoEncontradoException → 404 · DomainException → 400 · qualquer outra → 500
/// </summary>
public class ExceptionMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<ExceptionMiddleware> _log;

    public ExceptionMiddleware(RequestDelegate next, ILogger<ExceptionMiddleware> log)
    { _next = next; _log = log; }

    public async Task Invoke(HttpContext ctx)
    {
        try { await _next(ctx); }
        catch (NaoEncontradoException ex) { await Escrever(ctx, 404, "naoencontrado", "Não encontrado", ex.Message); }
        catch (DomainException ex)        { await Escrever(ctx, 400, "validacao", "Requisição inválida", ex.Message); }
        catch (Exception ex)
        {
            _log.LogError(ex, "Erro inesperado");   // o detalhe vai para o log, nunca para o cliente
            await Escrever(ctx, 500, "interno", "Erro interno", "Algo deu errado. Tente novamente.");
        }
    }

    private static Task Escrever(HttpContext ctx, int status, string slug, string title, string detail)
    {
        ctx.Response.StatusCode = status;
        ctx.Response.ContentType = "application/problem+json";
        return ctx.Response.WriteAsync(JsonSerializer.Serialize(new
        {
            type = "https://example.com/erros/" + slug,
            title,
            status,
            detail
        }));
    }
}

👉 Onde tudo se junta: registra o DbContext, liga cada interface à sua classe (injeção de dependência), configura o JWT e monta o pipeline. A ordem do pipeline importa: o tratamento de erros vem primeiro, para pegar exceções de tudo o que vem depois.

LojaApi.Api/Program.cs 
using LojaApi.Api.Middleware;
using LojaApi.Application.Services;
using LojaApi.Domain.Interfaces;
using LojaApi.Infrastructure.Data;
using LojaApi.Infrastructure.Repositories;
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.EntityFrameworkCore;
using Microsoft.IdentityModel.Tokens;
using System.Text;
using System.Text.Json;

var builder = WebApplication.CreateBuilder(args);

// ── 1) Controllers + Swagger (documentação em /swagger) ──
builder.Services.AddControllers();
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

// ── 2) EF Core + MySQL (o loja_db da Tab 5) ──
// Versão fixa do servidor (a imagem é mysql:8.4): o AutoDetect abriria uma conexão só para perguntar a versão.
var cs = builder.Configuration.GetConnectionString("DefaultConnection")
    ?? throw new InvalidOperationException("ConnectionStrings:DefaultConnection ausente no appsettings.json");
builder.Services.AddDbContext<AppDbContext>(o => o.UseMySql(cs, new MySqlServerVersion(new Version(8, 4, 0))));

// ── 3) Injeção de dependência: a porta (interface) → o adapter (classe concreta) ──
builder.Services.AddScoped<IProdutoRepository, EfProdutoRepository>();
builder.Services.AddScoped<IProdutoService, ProdutoService>();

// ── 4) JWT Bearer: confere assinatura e validade de cada token ──
var secret = builder.Configuration["Jwt:Secret"]!;
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = false, ValidateAudience = false,      // didático: sem emissor/audiência
            ValidateLifetime = true, ValidateIssuerSigningKey = true,
            IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secret)),
            ClockSkew = TimeSpan.FromMinutes(1)
        };
        // Sem token (ou inválido): o padrão é 401 com corpo VAZIO.
        // O contrato pede problem+json, então escrevemos o corpo aqui.
        o.Events = new JwtBearerEvents
        {
            OnChallenge = async ctx =>
            {
                ctx.HandleResponse();
                ctx.Response.StatusCode = 401;
                ctx.Response.ContentType = "application/problem+json";
                await ctx.Response.WriteAsync(JsonSerializer.Serialize(new
                {
                    type = "https://example.com/erros/naoautenticado",
                    title = "Não autenticado",
                    status = 401,
                    detail = "Envie o header Authorization: Bearer <token>."
                }));
            }
        };
    });
builder.Services.AddAuthorization();

// ── 5) Pipeline: a ORDEM importa ──
var app = builder.Build();
app.UseMiddleware<ExceptionMiddleware>();   // 1º: pega exceções de tudo que vem depois
app.UseSwagger();
app.UseSwaggerUI();
// (sem UseHttpsRedirection: a API roda em http — porta 5000 no dotnet run e 8080 no Docker)
app.UseAuthentication();                    // quem é você? (lê o token)
app.UseAuthorization();                     // você pode? ([Authorize])
app.MapControllers();
app.Run();

using LojaApi.Domain.Entities;
using LojaApi.Domain.Interfaces;
using LojaApi.Domain.ValueObjects;
using Microsoft.AspNetCore.Mvc.Testing;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.DependencyInjection.Extensions;
using Moq;
using Xunit;

namespace LojaApi.Tests;

/// <summary>
/// Testes HTTP: a API cumpre o CONTRATO da Tab 4?
/// O WebApplicationFactory sobe a API inteira EM MEMÓRIA (sem porta, sem MySQL):
/// controllers, JWT, middleware de erros — tudo de verdade. Só a PORTA
/// IProdutoRepository vira um mock, para não precisar do banco.
/// </summary>
public class ApiHttpTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly WebApplicationFactory<Program> _factory;
    private readonly Mock<IProdutoRepository> _repo = new();

    public ApiHttpTests(WebApplicationFactory<Program> factory)
    {
        _factory = factory.WithWebHostBuilder(b => b.ConfigureServices(s =>
        {
            s.RemoveAll<IProdutoRepository>();   // tira o EfProdutoRepository (MySQL)…
            s.AddSingleton(_repo.Object);       // …e põe o dublê no lugar
        }));
    }

    /// <summary>Faz o login de verdade (POST /api/auth/login) e devolve um cliente com o token.</summary>
    private async Task<HttpClient> ClienteLogado()
    {
        var http = _factory.CreateClient();
        var login = await http.PostAsJsonAsync("/api/auth/login",
            new { email = "dev@loja.com.br", senha = "SenhaForte#2026" });
        var corpo = await login.Content.ReadFromJsonAsync<Dictionary<string, object>>();
        http.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", corpo!["tokenAcesso"].ToString());
        return http;
    }

    /// <summary>Confere que a resposta é problem+json e devolve o "type" do erro.</summary>
    private static async Task<string?> TypeDoErro(HttpResponseMessage r)
    {
        Assert.Equal("application/problem+json", r.Content.Headers.ContentType?.MediaType);
        var corpo = await r.Content.ReadFromJsonAsync<Dictionary<string, object>>();
        return corpo?["type"]?.ToString();
    }

    [Fact(DisplayName = "🌐 GET /api/produtos é público → 200")]
    public async Task Listar_SemToken_200()
    {
        _repo.Setup(r => r.ListarAsync(0, 20))
             .ReturnsAsync([Produto.Reconstituir(1, "Teclado", new Dinheiro(349.90m), 15)]);

        var r = await _factory.CreateClient().GetAsync("/api/produtos?page=0&size=20");

        Assert.Equal(HttpStatusCode.OK, r.StatusCode);
        Assert.Contains("Teclado", await r.Content.ReadAsStringAsync());
    }

    [Fact(DisplayName = "🌐 POST sem token → 401 naoautenticado")]
    public async Task Criar_SemToken_401()
    {
        var r = await _factory.CreateClient().PostAsJsonAsync("/api/produtos",
            new { nome = "Mouse", preco = 10, estoque = 1 });

        Assert.Equal(HttpStatusCode.Unauthorized, r.StatusCode);
        Assert.EndsWith("/naoautenticado", await TypeDoErro(r));
        _repo.Verify(x => x.SalvarAsync(It.IsAny<Produto>()), Times.Never);   // nem chegou ao banco
    }

    [Fact(DisplayName = "🌐 Login com senha errada → 401")]
    public async Task Login_SenhaErrada_401()
    {
        var r = await _factory.CreateClient().PostAsJsonAsync("/api/auth/login",
            new { email = "dev@loja.com.br", senha = "errada" });

        Assert.Equal(HttpStatusCode.Unauthorized, r.StatusCode);
        Assert.EndsWith("/naoautenticado", await TypeDoErro(r));
    }

    [Fact(DisplayName = "🌐 POST válido com token → 201 + Location")]
    public async Task Criar_ComToken_201()
    {
        _repo.Setup(x => x.SalvarAsync(It.IsAny<Produto>()))
             .ReturnsAsync((Produto p) => Produto.Reconstituir(7, p.Nome, p.Preco, p.Estoque));
        var http = await ClienteLogado();

        var r = await http.PostAsJsonAsync("/api/produtos", new { nome = "Mouse", preco = 89.90, estoque = 3 });

        Assert.Equal(HttpStatusCode.Created, r.StatusCode);
        Assert.EndsWith("/api/produtos/7", r.Headers.Location?.ToString());
    }

    [Fact(DisplayName = "🌐 POST com nome de 1 letra → 400 validacao")]
    public async Task Criar_NomeInvalido_400()
    {
        var http = await ClienteLogado();

        var r = await http.PostAsJsonAsync("/api/produtos", new { nome = "M", preco = 10, estoque = 1 });

        Assert.Equal(HttpStatusCode.BadRequest, r.StatusCode);
        Assert.EndsWith("/validacao", await TypeDoErro(r));
    }

    [Fact(DisplayName = "🌐 GET /api/produtos/999 → 404 naoencontrado")]
    public async Task Obter_Inexistente_404()
    {
        _repo.Setup(x => x.BuscarPorIdAsync(999)).ReturnsAsync((Produto?)null);

        var r = await _factory.CreateClient().GetAsync("/api/produtos/999");

        Assert.Equal(HttpStatusCode.NotFound, r.StatusCode);
        Assert.EndsWith("/naoencontrado", await TypeDoErro(r));
    }
}

⑥ 🐳 Empacotar a API em Docker

O Dockerfile multi-stage compila com a imagem do SDK (grande) e roda com a imagem só de runtime (pequena). Multi-stage (docs)

Dockerfile 
# ── ESTÁGIO 1: BUILD — imagem com o SDK completo (compila e publica) ──
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish LojaApi.Api -c Release -o /out

# ── ESTÁGIO 2: RUNTIME — só o necessário para rodar (imagem bem menor) ──
FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /out .
# Dentro do container a API escuta na 8080 (padrão das imagens .NET 8+)
EXPOSE 8080
ENTRYPOINT ["dotnet", "LojaApi.Api.dll"]
.dockerignore 
# Sem isto, bin/ e obj/ do seu PC entram no container e quebram o restore.

⑦ 🔁 CI/CD: testes a cada push (GitHub Actions + GitLab CI)

A cada push ou Pull Request, um robô compila e roda os 29 testes; se algo quebrar, o PR fica vermelho. O que é CI/CD, pipeline e runner está explicado na Tab 3-G, parte ⑧. Aqui estão os arquivos de verdade deste projeto:

name: ci-dotnet                        # nome do workflow
on:                                     # gatilhos (triggers)
  pull_request: { branches: [main] }    # roda em todo PR p/ main
  push: { branches: [main] }            # roda ao mergear na main
jobs:
  build-test:
    runs-on: ubuntu-latest              # máquina (runner) Ubuntu
    steps:
      - uses: actions/checkout@v4                  # 1. baixa o código

      - run: dotnet test                           # 4. roda os testes (vermelho = pipeline falha)

📑 O que é uma ADR? Uma ADR (Architecture Decision Record) é a "ata" de uma decisão técnica: o problema (Contexto), o que foi decidido (Decisão), as outras opções (Alternativas), o que melhora e o preço aceito (Consequências) e em que ponto ela está (Status). Para que serve, quando escrever e um modelo para copiar: Tab 4, parte ⑦. Os números pulam porque a numeração é única no guia inteiro — a lista completa está na Tab 10.
ADR-003 · Clean Architecture em projetos .csproj 🔷 C#Aceita

Contexto: regra de negócio misturada com banco e HTTP dificulta testar e trocar tecnologia.

Decisão: projetos Domain, Application, Infrastructure, Api e Tests, com referências só para dentro.

Alternativas consideradas: um projeto só (rejeitada: nada impede o acoplamento); pastas por tecnologia (rejeitada).

Consequências: (+) testes sem banco, troca de persistência sem tocar no domínio (Tab 9-B); (−) mais arquivos no começo.

Status: Aceita · Stakeholders: Backend C#, Arquitetura.

ADR-017 · Domínio rico (DDD) com Value Object e Domain Event 🔷 C#Aceita

Contexto: as regras do produto (nome, preço, estoque) precisam valer sempre, venham de onde vierem.

Decisão: Produto com setters privados e fábricas Criar/Reconstituir; Dinheiro como record; ProdutoCriadoEvent registrado só depois de salvar (com o id real).

Alternativas consideradas: entidade anêmica com validação no controller (rejeitada); CQRS (adiado).

Consequências: (+) regra num lugar só, testável; (−) mais código no domínio.

Status: Aceita · Stakeholders: Backend C#.

ADR-018 · EF Core + Pomelo sobre o schema da Tab 5 🔷 C#Aceita

Contexto: o loja_db já existe, criado pelo init-sql da Tab 5 (com CHECKs e chaves).

Decisão: EF Core 9 + Pomelo 9 (versões fixas), mapeando as colunas existentes; sem migrations nesta aba.

Alternativas consideradas: Dapper (rejeitada: mais SQL à mão); migrations do EF (adiada: o schema é da Tab 5).

Consequências: (+) um banco para Java (Tab 6) e C#; (−) mudança de schema exige combinar com a Tab 5.

Status: Aceita · Stakeholders: Backend C#, DBA.

ADR-019 · Só autenticação e erros RFC 7807, como no contrato 🔷 C#Aceita

Contexto: o contrato da Tab 4 só pergunta "está logado?" e define os erros em problem+json.

Decisão: [Authorize] sem roles nas escritas; ExceptionMiddleware com 400/404/500 e OnChallenge para o 401 — todos com os type do contrato.

Alternativas consideradas: roles ([Authorize(Roles="ADMIN")], rejeitada: o contrato da Tab 4 só pergunta "está logado?" — ADR-005); erros em formato próprio (rejeitada).

Consequências: (+) o mesmo .http serve para o mock e para a API real; (−) qualquer usuário logado pode escrever (aceitável no estudo).

Status: Aceita · Stakeholders: Backend, QA, Segurança.
