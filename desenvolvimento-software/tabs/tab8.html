🗺️ Bounded Contexts aplicados ao contrato

Bounded Context (DDD): fronteira onde um modelo de domínio vale. Fora dela, o mesmo nome pode significar outra coisa. No contrato, cada contexto vira um grupo de tags + prefixo de path, com schemas próprios — nada de "Produto" do Catálogo vazando como "Item" do Pedido sem conversão.

ContextoResponsabilidadePrefixoTagsRoles principais
📦 CatálogoProdutos, categorias, preço vigente, reserva de estoque/api/catalogo/…CatalogoCATALOGO_ADMIN (escrita) · leitura pública
🛒 PedidosCarrinho→checkout, status do pedido, orquestra reservas/api/pedidos/…PedidosPEDIDOS_USER (criar/cancelar o próprio pedido)
🧾 ClientesCadastro, endereços de entrega/api/clientes/…ClientesCLIENTES_ADMIN (escrita/leitura)
🔌 Interno (service-to-service)Reserva de estoque · validação de endereçodentro dos prefixos acimaInternoPEDIDOS_SERVICE (token de serviço)
🏬
Analogia do shopping: cada loja (contexto) tem seu balcão, seu catálogo e suas regras. O Pedido é o "cliente que circula": consulta o Catálogo, confirma o Endereço com Clientes — mas não mexe no caixa das lojas: chama os balcões certos, na ordem certa.

📜 Um YAML ou vários? (decisão de contrato)

  • Adotado: um único openapi-multicontexto.yaml com tags por contexto e prefixos de path. Vantagens: 1 fonte única, 1 Prism, 1 Swagger UI organizado por tags, refs compartilhadas (ProblemDetails, Endereco).
  • Alternativa rejeitada: 1 YAML por contexto + N Prisms. Mais isolamento, mas duplica infra e dificulta refs cruzadas (ver ADR-009).
  • Regra de ouro: schema de um contexto não referencia entidade interna de outro — só DTOs de fronteira (ex.: ItemPedido guarda produtoId + snapshot de precoUnitario, não o Produto inteiro).

🔑 JWT com roles por contexto

O claim role vira roles (lista). Cada operação declara no contrato qual role exige (security por operação). Tokens de serviço (PEDIDOS_SERVICE) são emitidos por login machine-to-machine (didático: mesmo endpoint, credencial de serviço).

RoleQuem recebeLibera
ADMINdev/admin globaltudo (fallback de gestão)
CATALOGO_ADMINtime de catálogoPOST/PUT/DELETE em /api/catalogo/**
PEDIDOS_USERcliente logadocriar/listar/cancelar os próprios pedidos
CLIENTES_ADMINtime de cadastroCRUD em /api/clientes/**
PEDIDOS_SERVICEAPI de Pedidos (token de serviço)endpoints internos: reservar estoque, ler endereços

Exemplo de payload: { "sub": "api-pedidos", "roles": ["PEDIDOS_SERVICE"], "exp": … }. No Swagger UI, cada operação mostra o cadeado com a role exigida.

🔌 Integração entre contextos: HTTP síncrono (e seus riscos)

  • Como: Pedidos chama Catálogo (POST …/reservar) e Clientes (GET …/enderecos) via HTTP com token PEDIDOS_SERVICE, dentro da mesma transação de negócio (saga-lite: se a reserva falhar, o pedido nem é criado).
  • Por que síncrono aqui: didático e simples de testar (curl/Prism); consistência imediata na criação do pedido.
  • Riscos: acoplamento temporal (Catálogo fora → Pedido falha), latência somada, falha em cascata.
  • Mitigações mínimas: timeout curto (2s), retry só p/ GET idempotente, e mensagem de erro RFC 7807 com type específico (…/erros/dependencia-indisponivel). Evolução futura: eventos assíncronos (fora de escopo agora).

🔢 Versionamento aditivo vs breaking (ADR-011)

  • Aditivo (não quebra): novo path, novo campo opcional, nova tag → publica sem mudar versão.
  • Breaking (quebra): remover campo, mudar tipo, endurecer validação → sobe prefixo /v2/… e mantém /v1/… vivo até o fim do sunset.
  • No contrato: hoje sem prefixo (v1 implícito); o ADR registra gatilhos e procedimento.

TOKEN_USER=$(curl -s -X POST http://localhost:4011/api/auth/login \
  -H "Content-Type: application/json" \

TOKEN_SVC=$(curl -s -X POST http://localhost:4011/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"svc-pedidos@loja.internal","senha":"SenhaForte#2026"}' | jq -r '.tokenAcesso')
# ── 2) Catálogo: leitura pública (200 sem token) ──
curl -i http://localhost:4011/api/catalogo/produtos?page=0&size=10
# ── 3) Interno: reservar estoque COM token de serviço (200) ──
curl -i -X POST http://localhost:4011/api/catalogo/produtos/101/reservar \

curl -i -X POST http://localhost:4011/api/catalogo/produtos/101/reservar \

curl -i -X POST http://localhost:4011/api/pedidos \

📑 ADRs desta aba (padrão AWS)

ADR-009 · Contrato único com tags por contextoAceita

Contexto: 3 bounded contexts precisam de contrato claro sem duplicar infra de mock/docs.

Decisão: um openapi-multicontexto.yaml com tags por contexto e prefixos de path; schemas de fronteira sem vazamento de entidades internas.

Alternativas consideradas: 1 YAML por contexto + N Prisms (rejeitada: duplicação e refs cruzadas difíceis); monolito de schemas sem tags (rejeitada: ilegível).

Consequências: (+) 1 fonte única, Swagger UI organizado; (−) exige disciplina de prefixos/tags.

Status: Aceita · Stakeholders: Backend, Frontend, QA.

ADR-010 · Roles JWT por contexto (+ token de serviço)Aceita

Contexto: autorização precisa refletir fronteiras de contexto e chamadas machine-to-machine.

Decisão: claim roles (lista); roles CATALOGO_ADMIN, PEDIDOS_USER, CLIENTES_ADMIN, PEDIDOS_SERVICE, ADMIN; security por operação no contrato.

Alternativas consideradas: scopes finos por operação (adiada: complexidade); role única ADMIN (rejeitada: tudo-ou-nada).

Consequências: (+) autorização declarativa e testável; (−) gestão de roles exige procedimento de onboarding.

Status: Aceita · Stakeholders: Backend, Segurança, SRE.

ADR-011 · Versionamento aditivo com gatilhos de breaking changeAceita

Contexto: contrato multi-contexto evolui com vários times consumindo.

Decisão: mudanças aditivas sem versão; breaking changes sobem prefixo /v2 com sunset mínimo de 90 dias; matriz de compatibilidade revisada em PR.

Alternativas consideradas: versionar desde já (/v1) (rejeitada: cerimônia sem consumo externo ainda); sem política (rejeitada).

Consequências: (+) evolução sem fricção; (−) exige checagem disciplinada de breaking changes.

Status: Aceita · Stakeholders: Backend, Frontend, Arquitetura.

ADR-012 · Integração síncrona HTTP entre contextos (saga-lite)Aceita

Contexto: checkout precisa de reserva de estoque e endereço válidos no momento da criação.

Decisão: chamadas HTTP síncronas com token PEDIDOS_SERVICE, timeout 2s, erros 409/503 tipificados em RFC 7807; sem eventos assíncronos nesta fase.

Alternativas consideradas: eventos + eventual consistency (adiada: complexidade de reconciliação); banco compartilhado (rejeitada: quebra fronteiras).

ADR-013 · Pedidos: comandos em vez de CRUD (sem PUT/DELETE)Aceita

Contexto: Pedido é agregado com máquina de estados (CRIADO→RESERVADO→CONFIRMADO→ENVIADO/CANCELADO); PUT/DELETE deixariam mudar status "por fora" e apagar registro de auditoria. Catálogo e Clientes, sem máquina de estados, mantêm CRUD completo (PUT/DELETE/desativar).

Decisão: mudanças de estado de Pedido via comandos POST (/cancelar, futuramente /confirmar); sem PUT/DELETE em /api/pedidos; "remoção" = cancelamento (soft), preservando auditoria/legal.

Alternativas consideradas: PUT com status editável (rejeitada: quebra invariantes); DELETE físico (rejeitada: perda de auditoria); PATCH parcial (adiado).

Consequências: (+) invariantes e trilha de auditoria garantidas; (−) clientes aprendem endpoints de comando.

Status: Aceita · Stakeholders: Backend, QA, Jurídico/Compliance.
