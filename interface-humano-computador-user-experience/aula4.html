🧰 Glossário de ferramentas (leia uma vez!)
  • IHC (Interação Humano-Computador): a área que estuda como pessoas e sistemas se comunicam — e como tornar essa conversa fácil, segura e eficiente.
  • Interface: o “ponto de encontro” entre a pessoa e o sistema: telas, botões, menus, sons, gestos.
  • UX (experiência do usuário) vs UI (interface do usuário): UI é a “pele” (botões, cores); UX é a experiência completa (antes, durante e depois do uso).
  • Usabilidade: quão bem o usuário atinge seu objetivo com eficácia (funciona?), eficiência (rápido/pouco esforço?) e satisfação (fica feliz?).
  • Protótipo: versão simplificada da ideia para testar antes de construir (do rascunho no papel ao clique no Figma).
  • Figma / Miro: Figma = programa grátis de desenhar e prototipar interfaces; Miro = quadro branco colaborativo para mapas e oficinas.

01 — Estilos de interface: linguagem de comando e linguagem natural

🌍 No mundo real
  • Linguagem de comando: o antigo DOS (“C:\> copy a.txt b:\”) e o terminal do Linux hoje — técnicos digitam ordens exatas.
  • Linguagem natural: “Alexa, que horas são?”, “Ok Google, liga para a mamãe” — você fala como fala com gente.
🛠️ Nas ferramentas — explicado
  • Terminal (Linux/Windows): o “prompt” onde se digita comandos; é a linguagem de comando pura.
  • Assistentes de voz (Alexa, Google): interpretadores de linguagem natural — por trás, transformam sua fala em comandos.
🔤 Mini-dicionário
  • Estilo de interface: o “idioma” da conversa usuário↔sistema (comando, natural, menu, formulário, manipulação direta).
  • Linguagem de comando: o usuário digita instruções com sintaxe exata; rápido para experts, árido para novatos.
  • Linguagem natural: o usuário escreve/fala como com uma pessoa; flexível, porém ambígua para a máquina.
📖 Conceitos + analogias
  • Comando: 💡 como pedir café em código: “CAFÉ(1, SEM_AÇÚCAR)” — exato e veloz para quem sabe, mas um “;” errado e nada sai. Vantagens: poder, velocidade, flexibilidade para experts. Problemas: memorizar sintaxe, erros frequentes, assusta iniciantes.
  • Natural: 💡 como pedir ao garçom: “me vê um cafezinho?” — qualquer pessoa consegue, mas o garçom às vezes confirma: “sem açúcar, certo?”. Vantagens: não exige treino. Problemas: ambiguidade, o sistema pode entender errado, respostas imprevisíveis.
🎤 Plano de testes
  1. Passo 0 — entender a tela: um “sistema” com dois modos (comando / natural) e um campo para digitar.
  2. Teste 1 — comando errado. Clicar: modo comando; digite “copiar o arquivo” e execute. Vê: erro de sintaxe. Significa: na linguagem de comando a máquina não “adivinha”: ou a sintaxe é exata, ou nada acontece — por isso ela pune novatos.
  3. Teste 2 — comando certo. Clicar: digite exatamente cp relatorio.txt pasta/. Vê: sucesso imediato. Significa: para o expert, é o estilo mais rápido e poderoso: uma linha faz o que no mouse levaria 5 cliques.
  4. Teste 3 — linguagem natural. Clicar: modo natural; digite “por favor, copia o relatório pra pasta”. Vê: o sistema interpreta e pede confirmação. Significa: a linguagem natural é flexível (aceitou “pra”, “por favor”), mas é ambígua — por isso o sistema prudente confirma antes de agir.

02 — Seleção de menu, formulário e manipulação direta

🌍 No mundo real
  • Menu: o totem do fast-food: você reconhece o lanche na foto em vez de lembrar o código do pedido.
  • Formulário: o cadastro do site: campos rotulados, validação que avisa “este e-mail parece errado”.
  • Manipulação direta: arrastar o arquivo para a lixeira; dar zoom com dois dedos — ação contínua com resultado visível na hora.
🛠️ Nas ferramentas — explicado
  • Google Forms: criador de formulários com validação e mensagens de erro prontas.
  • Figma: permite prototipar menus e testar o “arrastar” antes de programar.
🔤 Mini-dicionário
  • Seleção de menu: o usuário escolhe entre opções visíveis — reconhecer em vez de lembrar. Diretrizes: poucos itens por tela, rótulos curtos e claros, agrupamento lógico, consistência.
  • Preenchimento de formulário: o usuário preenche campos; exige rótulos claros, validação com mensagens úteis e correção fácil de erros.
  • Manipulação direta: objetos visíveis, ação contínua e rápida, feedback imediato e reversível (“desfazer”).
🎤 Plano de testes
  1. Passo 0 — entender a tela: três estações: dois menus lado a lado, um formulário com validação e um arquivo para arrastar à lixeira.
  2. Teste 1 — menus. Clicar: “qual menu segue as diretrizes?”. Vê: o veredito comparando os dois. Significa: menu bom tem poucos itens, rótulos curtos e grupos lógicos; menu “lista telefônica” sobrecarrega a memória e esconde o que importa.
  3. Teste 2 — formulário. Clicar: “enviar” deixando nome vazio e e-mail sem @. Vê: mensagens de erro claras, campo a campo. Significa: formulário bem projetado não castiga: diz o que faltou e onde, em linguagem humana — o usuário corrige em segundos.
  4. Teste 3 — manipulação direta. Clicar/arrastar: leve o arquivo até a lixeira (ou use o botão). Vê: o arquivo some na hora e aparece “desfazer”. Significa: ver o objeto, agir e ver o resultado imediatamente (com reversibilidade) é o que torna a manipulação direta intuitiva — ninguém precisa de manual para arrastar.

03 — Padrões de interface e suas etapas

🌍 No mundo real
  • Você já sabe usar sem nunca ter visto: lupa = busca, carrinho = compras, ☰ = menu, “você está aqui” = trilha. Isso é um padrão: solução reaproveitada que todo mundo aprendeu uma vez só.
🛠️ Nas ferramentas — explicado
  • Bibliotecas de padrões (Material Design, Apple HIG): catálogos prontos de componentes padronizados para o designer não reinventar a roda.
🔤 Mini-dicionário
  • Padrão de interface: solução comprovada e reutilizável para um problema recorrente de interação.
  • Etapas dos padrões: (1) observar o contexto/problema, (2) identificar o padrão adequado, (3) aplicá-lo ao projeto, (4) avaliar com usuários.
🎤 Plano de testes
  1. Passo 0 — entender a tela: um jogo de adivinhação: aparece a necessidade do usuário e três candidatos a padrão.
  2. Teste 1 — jogar as rodadas. Clicar: na resposta de cada rodada. Vê: acerto/erro com explicação. Significa: padrões economizam aprendizado: o usuário transfere a experiência de outros sites; por isso quebrar um padrão “para ser criativo” costuma ser erro de design.
  3. Teste 2 — as etapas. Clicar: no botão “ver etapas”. Vê: observar → identificar → aplicar → avaliar. Significa: padrão não é “copiar e colar”: primeiro entendo o contexto, escolho o padrão certo, adapto e só então valido com usuários.

1) Um padrão de interface é…

2) O padrão “trilha” (breadcrumb) serve para…

3) A primeira etapa no uso de padrões é…

04 — Human-Centered Design: conceito e as três lentes

🌍 No mundo real
  • O fracasso bonito: produtos tecnologicamente incríveis que ninguém usou porque ignoraram as pessoas — o cemitério está cheio deles.
  • HCD: começar pelas pessoas (desejos, limites, contexto) e só depois pela tecnologia.
🛠️ Nas ferramentas — explicado
  • ISO 9241-210: a norma que define o “design centrado no ser humano” — o documento oficial da ideia.
  • Miro: quadro para oficinas de HCD (mapas de empatia, jornadas).
🔤 Mini-dicionário
  • HCD: abordagem que coloca as necessidades, capacidades e contexto das pessoas no centro de cada decisão de projeto.
  • As três lentes: 💗 desejabilidade (as pessoas querem/precisam?), ⚙️ viabilidade técnica (conseguimos construir?), 💰 viabilidade econômica (é sustentável como negócio?). O sucesso mora na interseção das três.
🎤 Plano de testes
  1. Passo 0 — entender a tela: escolha uma ideia de produto e depois “olhe” por cada lente (3 círculos).
  2. Teste 1 — ideia que passa. Clicar: “carregador solar de celular” e as três lentes. Vê: ✅ nas três. Significa: as pessoas querem, a tecnologia existe e o negócio fecha — a interseção das três lentes é o “ponto doce” do HCD.
  3. Teste 2 — ideia que falha. Clicar: “óculos que substituem o celular (hoje)”. Vê: uma lente ❌. Significa: basta UMA lente falhar para o produto morrer: tecnologia cara demais, ou ninguém quer, ou o negócio não fecha — por isso o HCD exige olhar pelas três.

Escolha uma ideia e depois clique nas lentes 💗 ⚙️ .

05 — Aplicação do HCD: etapas da metodologia

🌍 No mundo real
  • Receita iterativa: como provar uma sopa várias vezes antes de servir — o HCD projeta, prova com usuários, ajusta e prova de novo.
🔤 Mini-dicionário — as 4 etapas (ISO 9241-210)
  • 1. Compreender o contexto de uso: quem são as pessoas, onde e como usarão.
  • 2. Especificar requisitos: o que o produto precisa atender para essas pessoas.
  • 3. Produzir soluções de design: protótipos, do rascunho ao clicável.
  • 4. Avaliar contra os requisitos: testes com usuários; o resultado alimenta a volta ao começo (iteração).
🎤 Plano de testes
  1. Passo 0 — entender a tela: as 4 etapas embaralhadas; clique na ordem correta.
  2. Teste 1 — ordenar. Clicar: contexto → requisitos → design → avaliação. Vê: as etapas empilhando na ordem. Significa: começar pelo contexto evita o erro clássico de desenhar “achando” que sabe o que o usuário precisa.
  3. Teste 2 — errar de propósito. Clicar: “produzir design” primeiro. Vê: o alerta de ordem errada. Significa: prototipar antes de entender o contexto é construir a resposta para uma pergunta que ninguém fez — desperdício de tempo e dinheiro.
  4. Teste 3 — a iteração. Clicar: ao completar, leia o aviso final. Vê: “avaliar devolve ao começo”. Significa: HCD não é linha reta, é espiral: cada rodada de avaliação melhora a solução até atender aos requisitos.

06 — Kit de ferramentas HCD e considerações

🌍 No mundo real
  • Caixa de ferramentas: o HCD tem uma ferramenta para cada momento: entender (entrevistas), sentir (mapa de empatia), organizar (card sorting), testar (teste de usabilidade).
🔤 Mini-dicionário — o kit
  • Personas: personagens fictícios mas realistas que personificam o usuário típico.
  • Mapa de empatia: o que o usuário vê, ouve, pensa, sente, dores e ganhos.
  • Card sorting: usuários agrupam cartões para revelar a organização mental (base dos menus).
  • Protótipo: versão simplificada para testar ideias barato. Teste de usabilidade: usuários reais executando tarefas reais enquanto você observa.
🎤 Plano de testes
  1. Passo 0 — entender a tela: jogo de casar: aparece a necessidade e três ferramentas.
  2. Teste 1 — jogar as rodadas. Clicar: na ferramenta certa. Vê: acerto/erro com o porquê. Significa: cada ferramenta responde uma pergunta diferente: persona = “quem é?”, empatia = “o que sente?”, card sorting = “como organiza?”, teste = “funciona na prática?”.
  3. Teste 2 — fechar a aula. Clicar: abra o 🗺️ mapa e a 📝 cola rápida abaixo. Vê: o fio condutor da unidade. Significa: estilos de interface são o “vocabulário” da conversa usuário↔sistema; padrões são as “frases prontas” que funcionam; e o HCD é a “gramática” que garante que tudo seja escrito a partir das pessoas.
🗺️ Mapa da aula (visão geral)

Estilos de interface (comando, natural, menu, formulário, manipulação direta) → Padrões (soluções prontas: observar → identificar → aplicar → avaliar) → HCD (pessoas no centro; lentes 💗⚙️💰) → Método (contexto → requisitos → design → avaliar, em espiral) → Kit (personas, empatia, card sorting, protótipo, teste de usabilidade).

📝 Cola rápida (uma linha por termo)
  • Comando: sintaxe exata; rápido p/ expert, árido p/ novato.
  • Natural: fala como gente; flexível, porém ambígua.
  • Menu: reconhecer > lembrar; poucos itens, rótulos curtos.
  • Formulário: rótulos claros + erros explicados campo a campo.
  • Manipulação direta: objetos visíveis, feedback imediato, reversível.
  • Padrão: solução comprovada reutilizável (lupa, carrinho, ☰).
  • HCD: pessoas primeiro; lentes = desejabilidade, técnica, econômica.
  • Etapas HCD: contexto → requisitos → design → avaliar (iterar).
  • Kit: personas, mapa de empatia, card sorting, protótipo, teste de usabilidade.
