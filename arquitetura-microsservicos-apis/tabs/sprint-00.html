💡 Conceito: o que é um monólito

🧱 Monólito

Um monólito é um sistema publicado como uma única unidade: um processo, um deploy e, normalmente, um banco de dados compartilhado por todas as partes. Ele pode ser bem organizado por dentro (em módulos), mas tudo sobe, escala e cai junto.

Monólito não é sinônimo de código ruim. Grandes produtos começaram assim, e muitos continuam assim, com sucesso. O problema aparece quando o contexto muda: time maior, partes com ritmos de mudança diferentes, partes que precisam escalar sozinhas.

✅ Vantagens

  • Simples de desenvolver e depurar: uma chamada de método, não uma chamada de rede.
  • Transação única: o banco garante consistência entre os módulos.
  • Um deploy, um lugar para monitorar.
  • Desempenho: sem latência de rede entre as partes.
  • Ótimo para começar: domínio ainda instável, time pequeno.

⚠️ Custos (que crescem com o tempo)

  • Deploy acoplado: mudar uma linha do Extrato exige publicar tudo.
  • Escala tudo ou nada: para escalar o Extrato, escala o sistema inteiro.
  • Falha em cascata: uma parte lenta ou quebrada derruba o fluxo inteiro.
  • Acoplamento silencioso: módulos mexem nas tabelas uns dos outros.
  • Times esbarrando: muitos times no mesmo código e no mesmo ciclo de release.
🏠
Analogia: o monólito é uma casa com um único quadro de luz. É simples de instalar e de entender, e um único disjuntor desarma tudo quando algo dá curto. A analogia vale até aqui: ela explica o acoplamento de falhas. A partir daqui ela engana: uma casa não precisa "escalar um cômodo", e trocar um quadro de luz não exige mudar o jeito como os cômodos conversam; em software, dividir o sistema muda a comunicação entre as partes.
🛑 Quando NÃO migrar para microsserviços: time pequeno; domínio ainda mudando toda semana; sem automação de deploy, monitoramento e testes; ou quando a dor real é código desorganizado (isso se resolve com um monólito modular, tema da Sprint 1). Microsserviços não são a evolução obrigatória: são uma troca de problemas.
📝 A decisão de 2019: ADR 0001

Um ADR (Architecture Decision Record) registra uma decisão de arquitetura: o contexto, o que foi decidido, as alternativas e as consequências. O arquivo completo está em docs/adr/0001-comecar-com-monolito.md no repositório.

ADR 0001 · Começar a PagUai como um monólito aceita · 2019

Contexto: 4 pessoas desenvolvedoras, nenhum cliente, hipótese de negócio ainda não validada.

Decisão: uma aplicação ASP.NET Core, um banco PostgreSQL, um deploy, com pastas por módulo.

Alternativa rejeitada: microsserviços desde o início. Com o domínio instável, as fronteiras entre serviços quase certamente estariam erradas, e mudar fronteira entre serviços é caro.

Consequências: MVP em 3 meses e operação simples; com o crescimento, deploy acoplado, escala tudo ou nada e falhas em cascata.

💡 Repare: a decisão foi correta para 2019. Uma decisão de arquitetura se avalia pelo contexto em que foi tomada, não pelo que sabemos hoje.

0 Preparar o ambiente

Você precisa de Git e Docker (com Docker Compose). O .NET 10 SDK é opcional, só para rodar fora do Docker. Com menos de 8 GB de RAM, prefira o GitHub Codespaces.

  1. Faça um fork de Cloud-Ai-Generative/paguai (botão Fork no GitHub).
  2. Clone o seu fork e entre na pasta:
    terminal
    git clone https://github.com/SEU-USUARIO/paguai.git
cd paguai
git checkout sprint-00
  3. Verifique a sua máquina:
    Linux ou macOS
    ./scripts/check-env.sh
    Windows (PowerShell)
    pwsh ./scripts/check-env.ps1
✅ Resultado esperado: todos os itens com [OK] e a mensagem "Tudo pronto!".
☁️ Sem Docker na máquina? No seu fork, clique em Code → Codespaces → Create codespace on main. O ambiente já vem com Docker e .NET 10.

1 Subir a PagUai

terminal, na pasta paguai
docker compose up -d --build
docker compose ps
✅ Resultado esperado: três contêineres em execução: paguai-api, paguai-postgres (healthy) e paguai-mailpit.

Confira se a API e o banco estão no ar:

terminal
curl -i http://localhost:8080/health
✅ Resultado esperado: HTTP/1.1 200 OK e {"status":"saudavel","banco":"ok"}. Se não responder, veja o ✋ Errou? abaixo.

2 Explorar a API no Scalar

Abra http://localhost:8080. Você cai no Scalar, a documentação interativa gerada a partir do contrato OpenAPI da API.

  1. Execute GET /contas e copie o id da Ana Clara Mendes.
  2. Execute POST /transferencias com o corpo abaixo (troque o id):
    corpo da requisição (JSON)
    {
  "contaOrigemId": "COLE_AQUI_O_ID_DA_ANA",
  "chavePixDestino": "loja.geraldo@paguai.local",
  "valor": 150.00
}
    ✅ Resultado esperado: 201 Created com "status": "Concluida".
  3. Repita com "valor": 6000.00.
    ✅ Resultado esperado: 201 Created, mas com "status": "ReprovadaAntifraude": o antifraude reprova valores acima de R$ 5.000. O saldo da Ana não muda.
💡 Prefere o VS Code? O arquivo requests/paguai.http tem as mesmas requisições prontas para a extensão REST Client.

3 Ver os e-mails e o extrato

  1. Abra o Mailpit em http://localhost:8025.
    ✅ Resultado esperado: dois e-mails do PIX de R$ 150: "Você enviou R$ 150,00..." para a Ana e "Você recebeu R$ 150,00..." para a loja do Seu Geraldo.
  2. No Scalar, copie o id da Loja do Seu Geraldo e execute GET /contas/{id}/extrato.
    ✅ Resultado esperado: um lançamento de crédito de 150,00 e o saldo atual da loja.

4 Sentir a dor: a notificação derruba o PIX

No diagrama D-02, a notificação roda dentro da transação. Vamos ver o que isso significa quando o serviço de e-mail falha.

  1. No docker-compose.yml, troque Notificacoes__SimularFalha: "false" por "true" e aplique:
    terminal
    docker compose up -d
  2. Repita o PIX de R$ 150 da Ana e, em seguida, consulte GET /contas/{id} da Ana.
    ✅ Resultado esperado: a transferência responde 500 ("Falha simulada no serviço de notificações.") e o saldo da Ana não muda. Um problema no e-mail impediu o pagamento.
  3. Volte o valor para "false" e rode docker compose up -d de novo.

🔬 Aprofundamento opcional
1. Encontrar o acoplamento no código

Abra no VS Code e observe:

  • src/PagUai.Api/Infra/PagUaiDbContext.cs: um único DbContext com as tabelas de todos os módulos.
  • src/PagUai.Api/Modulos/Transferencias/TransferenciaService.cs: o serviço chama o antifraude, grava as tabelas do Extrato e envia as notificações, tudo na mesma transação.
  • src/PagUai.Api/Modulos/Cobrancas/CobrancasEndpoints.cs: o módulo de Cobranças usa por dentro o serviço de Transferências.
2. Antifraude lento, sistema lento

No docker-compose.yml, mude Antifraude__LatenciaMs de "300" para "3000", rode docker compose up -d e repita um PIX. Toda transferência passa a levar mais de 3 segundos. Imagine isso numa Black Friday: é o gancho das Sprints 6 e 9.

3. Rodar os testes automatizados

Com o .NET 10 SDK e o Docker em execução:

terminal

São 8 testes: 4 de unidade (regras do antifraude) e 4 de integração, que sobem um PostgreSQL de verdade com Testcontainers. Um deles, Falha_na_notificacao_desfaz_a_transferencia, documenta a dor da fase 4.

✋ Errou? Casos comuns desta sprint
port is already allocated (porta 8080, 5432 ou 8025 ocupada)

Outro programa ou contêiner usa a porta. Descubra qual: sudo ss -ltnp | grep :8080 (Linux), lsof -i :8080 (macOS), netstat -ano | findstr :8080 (Windows) e docker ps. Pare o processo ou suba a PagUai em outra porta: PAGUAI_API_PORT=8081 docker compose up -d.

Depois de liberar a porta, a API não acha o banco (Resource temporarily unavailable)

O contêiner da API ficou com a rede incompleta depois da primeira falha. Recrie tudo: docker compose down e depois docker compose up -d. Só religar o contêiner não resolve.

fatal: detected dubious ownership in repository

Você está no terminal como root, mas a pasta pertence ao seu usuário. Saia do root (exit) e rode os comandos com o seu usuário. Trabalhar como root no dia a dia causa esse e outros problemas de permissão.

curl /health não responde nada

A API ainda está subindo ou caiu. Rode docker compose ps e docker compose logs api --tail 40. Espere aparecer Application started.

Aparece "fail: Failed executing DbCommand ... __EFMigrationsHistory" na primeira vez

Normal. Na primeira execução a tabela de controle das migrations ainda não existe; o EF Core registra como erro e cria a tabela logo em seguida. Confira se depois aparece Dados fictícios iniciais inseridos.

WARN buildx Docker CLI plugin not found

Só um aviso: o build funciona. Para eliminá-lo no Linux: sudo apt install docker-buildx-plugin.
