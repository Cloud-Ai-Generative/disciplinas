📞 Síncrona e assíncrona

Na comunicação síncrona, quem chama espera a resposta para continuar (requisição e resposta, como HTTP). Na assíncrona, quem chama avisa que algo aconteceu e segue em frente; quem se interessa reage depois (eventos e mensagens, tema da Sprint 3).

Síncrona (HTTP)Assíncrona (mensagens)
Acoplamento no tempoOs dois precisam estar no ar ao mesmo tempoQuem recebe pode estar fora do ar; a mensagem espera
LatênciaSoma a de cada chamada da cadeiaQuem chama não espera; o efeito acontece depois
ConsistênciaResposta imediataEventual: por um tempo, as partes podem discordar
DepuraçãoMais simples: uma cadeia de chamadasMais difícil: o fluxo se espalha no tempo
Na PagUai, nesta sprintO Extrato consulta Contas e PagamentosAinda não; a notificação vira mensagem na Sprint 3
📱
Analogia: síncrona é uma ligação telefônica; assíncrona é uma mensagem de texto. A analogia vale até aqui: ela explica quem precisa estar disponível e quando. A partir daqui ela engana: ela sugere que a mensagem "sempre chega". Sem um broker confiável e sem confirmação de recebimento, uma mensagem pode se perder ou chegar duas vezes, como você vai ver na Sprint 3.
⚠️ Armadilha comum no mercado: achar que assíncrono é "mais rápido". Ele é mais desacoplado, e o trabalho termina depois; ele não fica mais rápido. E é mais difícil de depurar.

📜 API, Web Service e contrato

Uma API é a forma combinada de um sistema usar o outro. Web Services é o nome que ficou associado às APIs em SOAP e XML (tema da Sprint 4); hoje, a maioria das APIs entre serviços usa HTTP e JSON. O que as duas têm em comum é o contrato: o acordo público sobre rotas, parâmetros, formatos de dados e erros. O padrão mais usado para descrever contratos HTTP é o OpenAPI; os erros seguem o Problem Details (RFC 9457).

🎯 API First: o contrato antes do código

API First é tratar a API como um produto: o contrato é desenhado e combinado com quem vai consumir, antes da implementação. Com o contrato aprovado, os times trabalham em paralelo: o front-end usa um mock gerado do contrato, e o back-end implementa o serviço, que é verificado contra o mesmo contrato.

Design-first (contract-first)Code-first
Como nasce o contratoEscrito primeiro, revisado com quem consomeGerado a partir do código
Quem consome participaAntes da implementaçãoDepois que a API existe
Trabalho em paraleloSim, com mock do contratoQuem consome espera o código
Risco principalContrato e código divergirem (resolvido com teste de contrato)O contrato muda sem querer quando o código muda
Na PagUaiO serviço de Extrato (porta 8082)O monólito (porta 8081), que é legado

🌳 Strangler Fig

O nome vem da figueira estranguladora, que cresce em volta de uma árvore até substituí-la. No software, um proxy (aqui, um gateway) fica na frente do sistema antigo e desvia, rota por rota, o tráfego para os serviços novos. O sistema antigo continua atendendo o resto. Cada rota desviada pode voltar atrás se der problema, e o código antigo só é apagado quando o novo estiver confiável.

⚠️ Armadilha comum no mercado: extrair o serviço mas manter o mesmo banco compartilhado, com o serviço novo lendo as tabelas do antigo. É um monólito distribuído. Na PagUai, o Extrato não lê o banco: ele usa a API de Pagamentos, que é o dono dos dados.

4 Falhas parciais: quem cai, quem continua ⏱️ 20 min

🔮 Preveja: se o serviço de Extrato cair, o que acontece com o PIX? E se o monólito travar, o que acontece com o extrato?
O PIX continua; o extrato cai. Com o Extrato parado, o gateway responde 502 só na rota do extrato, e o PIX, que é do monólito, funciona. Mas o contrário não vale: o Extrato depende do monólito. Se o monólito estiver fora, o Extrato responde 503; se estiver lento ou travado, o Extrato fica esperando, porque ninguém configurou um timeout.
  1. Derrube o Extrato e teste as duas rotas:
    terminal
    docker compose stop extrato
curl -si http://localhost:8080/contas/COLE_O_ID_DA_ANA/extrato | head -1
    PowerShell
    docker compose stop extrato
curl.exe -si http://localhost:8080/contas/COLE_O_ID_DA_ANA/extrato | Select-Object -First 1
    Depois faça um PIX da Ana no Scalar e religue: docker compose start extrato.
    ✅ Resultado esperado: o extrato responde 502 Bad Gateway, mas o PIX responde 201. Na Sprint 0, um deploy do Extrato derrubou o checkout; agora, o Extrato fora do ar não derruba o pagamento.
  2. Agora congele o monólito e meça o tempo do extrato:
    terminal
    docker compose pause api
curl -s -o /dev/null -w "%{http_code} em %{time_total}s\n" --max-time 30 http://localhost:8080/contas/COLE_O_ID_DA_ANA/extrato
docker compose unpause api
    PowerShell
    docker compose pause api
curl.exe -s -o /dev/null -w "%{http_code} em %{time_total}s\n" --max-time 30 http://localhost:8080/contas/COLE_O_ID_DA_ANA/extrato
docker compose unpause api
    ✅ Resultado esperado: nenhuma resposta em 30 segundos (o curl desiste com 000). O Extrato está no ar, mas pendurado esperando o monólito: o padrão do .NET espera até 100 segundos. Cada consulta presa ocupa recursos, e numa Black Friday elas se acumulam.
🤔 Para pensar: quanto tempo o Extrato deveria esperar antes de desistir? E o que ele deveria responder ao app nesse caso? É a dor proposital que a Sprint 9 resolve com timeout, retentativa e circuit breaker.

ADR 0004 · Como extrair o Extrato: Strangler Fig, gateway e contrato aceita · Sprint 2

Proposta e aprovação: proposto pelo(a) arquiteto(a) Arquiteto(a), com Lívia (front-end), Joana e Rafa; aprovado por Helena Rocha, Coordenadora de Arquitetura.

Contexto: o ADR 0003 decidiu extrair o Extrato primeiro. O app e o portal do lojista já usam GET /contas/{id}/extrato do monólito, então a troca precisa ser invisível para quem consome e reversível se o serviço novo falhar.

Decisão: um gateway (YARP) passa a ser a porta de entrada e desvia só a rota do extrato para o serviço novo; a configuração Strangler__Extrato permite voltar ao Extrato antigo sem mudar código. O serviço nasce contract-first: o contrato foi combinado com a Lívia na Sala de Contrato, publicado como mock (Prism) e verificado no código por testes de contrato e pelo lint no CI. O Extrato não tem banco: consulta Contas e Pagamentos pela API do monólito.

Tema do contratoDecisão
Valores em dinheiroNúmero com duas casas decimais, como o app já lê; texto fica como candidato para a Sprint 7
SaldoDentro do extrato, com o momento da consulta (saldoEm)
PaginaçãoCursor opcional; sem limite, até 100 lançamentos
PeríodoPadrão de 30 dias e máximo de 90, com 422
ErrosProblem Details (RFC 9457) com um type por erro; 503 quando uma dependência cair
VersãoSem prefixo: só mudanças que não quebram
SegurançaDeclarada no contrato como vulnerabilidade proposital até a Sprint 11

Alternativas consideradas: trocar a URL no app (rejeitada: não há como voltar atrás sem nova versão do app); desviar só uma parte do tráfego, canary (válida; adiada até haver métricas por versão, Sprint 10); o Extrato com banco próprio alimentado por eventos (adiada: depende da mensageria, Sprint 3); contrato gerado do código (rejeitada para um serviço novo: o consumidor só participaria depois).

Consequências: um deploy ou uma falha do Extrato não derruba mais o PIX. Em troca, cada consulta faz três chamadas HTTP ao monólito, e o Extrato depende dele: com o monólito fora, responde 503; com o monólito lento, fica esperando, porque ainda não há timeout (dor proposital, Sprint 9). O Extrato antigo será apagado do monólito na Sprint 3.

4. Cursor ou página: por que o extrato usa cursor

Abra src/PagUai.Api/Modulos/Pagamentos/Interno/ServicoDePagamentos.cs, método ListarMovimentosAsync. A consulta continua depois do último item da página anterior (data e id), em vez de pular N linhas. Assim, um PIX novo que chega enquanto a pessoa navega não empurra os itens nem faz a próxima página repetir um lançamento. E o banco usa o índice (conta_id, data) sem contar a tabela inteira.

✋ Errou? Casos comuns desta sprint
502 Bad Gateway no extrato

O serviço de Extrato está parado ou ainda subindo, e o gateway não tem para onde mandar a rota. Veja docker compose ps e docker compose logs extrato --tail 40. Para voltar ao Extrato antigo, use a fase 5.

503 com dependencia-indisponivel no extrato

O Extrato está no ar, mas não consegue falar com o monólito. Veja docker compose logs api --tail 40. Se você usou docker compose pause api, rode docker compose unpause api.

port is already allocated na porta 8081, 8082 ou 4010

Outro programa usa a porta. Suba em outra, por exemplo: PAGUAI_EXTRATO_PORT=9082 docker compose up -d. As variáveis estão no começo do docker-compose.yml.

O gateway não sobe e o log fala em Strangler:Extrato

O valor de Strangler__Extrato está errado. Use exatamente "servico" ou "monolito", sem acento.

O mock responde 404 ou não sobe

Confira se usou --profile mock e se a rota é exatamente /contas/{id}/extrato. Os logs ficam em docker compose logs mock.

O curl com pause fica parado e não volta

Esse é o efeito esperado da fase 4: sem timeout, o Extrato espera o monólito. Use sempre --max-time 30 no curl e, ao terminar, docker compose unpause api.
