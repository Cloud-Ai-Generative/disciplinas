☁️ Tecnologias e nuvem

Cada tecnologia da disciplina tem uma Ficha: o que é, por que usamos no laboratório, quais opções existem no mercado e como escolher. As fichas não dão veredito: a melhor opção depende de cada caso.

💡 Por que o laboratório não usa a nuvem? Para fins didáticos: tudo roda na sua máquina, sem conta em nuvem, sem cartão de crédito e sem custo, e você vê por dentro como cada peça funciona. A nuvem aparece como comparação, nos desenhos e nestas fichas.

🔧 Ficha da tecnologia: C# e .NET 10 (ASP.NET Core)

O que é: C# é a linguagem; o .NET é a plataforma que executa o código; o ASP.NET Core é a parte do .NET para criar APIs web. Usamos as Minimal APIs, que declaram as rotas com pouco código. O .NET 10 é uma versão LTS, com suporte longo.

Por que usamos aqui: é multiplataforma (roda em Windows, macOS e Linux), gratuito e de código aberto, e tem bibliotecas maduras para tudo o que a disciplina usa: gRPC, SignalR, GraphQL, mensageria e observabilidade.

Onde roda na nuvem: o .NET não depende de provedor. Em contêineres, ele roda em qualquer um deles. Algumas opções:

AWSAzureGoogle Cloud
Amazon ECS ou Amazon EKS (contêineres), AWS Lambda (funções)Azure App Service, Azure Container Apps ou AKSCloud Run ou GKE

Outras opções no mercado: Java (Spring Boot), Go, Node.js, Python. Todas constroem microsserviços.

Critérios para decidir:

  • O que o time já domina e o que o mercado da região contrata.
  • Bibliotecas e integrações de que o sistema precisa.
  • Consumo de memória e tempo de inicialização, que pesam em contêineres e funções.

🔧 Ficha da tecnologia: PostgreSQL

O que é: banco de dados relacional de código aberto. Guarda os dados em tabelas, com transações que acontecem por inteiro ou são desfeitas por inteiro.

Por que usamos aqui: roda num contêiner na sua máquina, é gratuito e é o mesmo motor oferecido como serviço gerenciado pelos três grandes provedores.

AWSAzureGoogle Cloud
Amazon RDS for PostgreSQL ou Amazon Aurora (compatível com PostgreSQL)Azure Database for PostgreSQL (servidor flexível)Cloud SQL for PostgreSQL ou AlloyDB

O que muda: no serviço gerenciado, o provedor cuida de backup, atualização e da reserva em outra zona; você paga pelo serviço e tem menos controle sobre o servidor. No contêiner, você controla tudo e cuida de tudo.

Critérios para decidir:

  • Quem vai operar backup, atualização e alta disponibilidade.
  • Custo do serviço gerenciado frente ao tempo do time.
  • Recursos específicos de que o sistema precisa (extensões, versões).

🔧 Ficha da tecnologia: Docker e Docker Compose

O que é: o Docker empacota uma aplicação com tudo de que ela precisa numa imagem e a executa como contêiner. O Docker Compose sobe vários contêineres juntos, descritos num arquivo YAML.

Por que usamos aqui: um único comando sobe a API, o banco e o Mailpit, igual em qualquer máquina. Acaba o "na minha máquina funciona".

Opções no mercado: o Compose é uma ferramenta para a máquina do desenvolvedor. Em produção, os contêineres rodam num serviço que os executa e num registro que guarda as imagens:

AWSAzureGoogle Cloud
ExecutarAmazon ECS ou Amazon EKSAzure Container Apps ou AKSCloud Run ou GKE
Guardar imagensAmazon ECRAzure Container RegistryArtifact Registry

Critérios para decidir:

  • Quantos serviços e réplicas o sistema tem (a partir de certo ponto, um orquestrador como o Kubernetes, tema da Sprint 8).
  • Quanto o time quer operar a infraestrutura ou deixar com o provedor.
  • Como cada serviço é cobrado: por máquina, por contêiner ou por requisição.

🔧 Ficha da tecnologia: Mailpit

O que é: um servidor de e-mail de teste. Ele recebe os e-mails por SMTP e mostra numa página web, sem entregar nada para ninguém de verdade.

Por que usamos aqui: você vê as notificações da PagUai sem configurar uma conta de e-mail e sem risco de mandar mensagens para pessoas reais.

Opções no mercado (envio real):

AWSAzureGoogle Cloud
Amazon SESAzure Communication Services (e-mail)Sem serviço próprio; a documentação indica parceiros, como o SendGrid

Critérios para decidir:

  • Volume de e-mails e preço por envio.
  • Recursos de entregabilidade (para o e-mail não cair no spam).
  • Onde o resto do sistema roda.

🔧 Ficha da tecnologia: Scalar e OpenAPI

O que é: o OpenAPI é o padrão que descreve o contrato de uma API (rotas, parâmetros, respostas e erros). O Scalar lê esse contrato e gera uma página para ler a documentação e testar as chamadas.

Por que usamos aqui: vem junto com a API, sem instalar nada: basta abrir http://localhost:8080.

Outras opções: Swagger UI e Redoc (código aberto), além do arquivo .http e do curl. Na nuvem, os gateways de API costumam ter um portal para quem consome a API:

AWSAzureGoogle Cloud
Console do Amazon API Gateway, que permite testar chamadasPortal do desenvolvedor do Azure API ManagementPortal integrado do Apigee

Critérios para decidir:

  • Quem vai usar a documentação: o próprio time ou parceiros externos.
  • Se a API precisa de cadastro de consumidores, chaves e planos de uso (Sprint 13).

🔧 Ficha da tecnologia: testes de arquitetura (NetArchTest)

O que é: um teste de arquitetura verifica regras de dependência no código compilado, por exemplo: "nenhum tipo do módulo Cobranças pode depender da pasta Interno de Pagamentos". O NetArchTest é uma biblioteca .NET que lê os assemblies e permite escrever essas regras como testes comuns.

Por que usamos aqui: todos os módulos da PagUai estão no mesmo projeto, então o compilador não impede um módulo de usar o interior de outro. Com poucas linhas, o teste transforma a fronteira em regra verificada a cada build, e a mensagem de erro diz qual tipo violou a regra.

Outras opções no mercado:

OpçãoComo funciona
ArchUnitNETBiblioteca .NET inspirada no ArchUnit, com uma linguagem de regras mais ampla (camadas, ciclos, convenções de nome)
ArchUnitA biblioteca original, para Java
Um projeto (.csproj) por móduloA fronteira é verificada pelo compilador: um módulo só enxerga o projeto de contratos do outro; exige manter mais projetos e referências
Analisadores e revisão de códigoRegras no build (analisadores Roslyn) ou combinadas no time e conferidas no Pull Request

Onde roda na nuvem: testes de arquitetura não dependem de provedor: rodam no pipeline de integração contínua, junto com os outros testes.

GitHubAWSAzureGoogle Cloud
GitHub Actions (usado na PagUai)AWS CodeBuild, orquestrado pelo AWS CodePipelineAzure PipelinesCloud Build

Critérios para decidir:

  • Quão forte a fronteira precisa ser: verificada por teste ou impedida pelo compilador.
  • Quantos módulos e times existem, e o custo de manter a estrutura de projetos.
  • Que outras regras o time quer verificar (camadas, ciclos, nomes), e se a biblioteca as expressa.
